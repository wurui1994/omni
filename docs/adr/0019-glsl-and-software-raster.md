### 这两个着色器定下了「最小可用的 GLSL 子集」

这是读那份 benchmark 最要紧的收获 —— 要走通它，需要的 GLSL **只有这些**：

所以第一刀的门可以就是「跑通 `FRAG_SIMPLE`」，第二刀「跑通 `FRAG_COMPLEX`」——

## 量：读 llvmpipe —— 借什么、不借什么

读过的：`lp_limits.h`（全）、`lp_bld_interp.h`（全）、`lp_bld_interp.c` 头 200 行、
`lp_rast_tri_tmp.h` 头 120 行、`lp_state_fs.c` 的文件头。**没读**的：`lp_bld_nir.c`
那一整摊（NIR → LLVM IR）、纹理采样、`lp_linear*`、`lp_scene`/`lp_setup` 的分箱。
下面每条都带出处，好回查。

### 量到的形状

**一、瓦片是 64×64，光栅化是分层的。** `lp_limits.h:39` `TILE_ORDER 6` → `TILE_SIZE 64`。
`lp_rast_tri_tmp.h` 里两级：`do_block_16` 拿一个 **16×16** 块，按每条边的边函数
（`plane[j].dcdx`/`dcdy`/`eo`）一次算出 16 个 **4×4** 子块的「全在内 / 全在外 / 骑边」
（`build_masks_32` 出 `outmask` 与 `partmask`，`outmask == 0xffff` 直接 return）；
骑边的那些交给 `do_block_4`，它出一个 **16 位掩码**（4×4 个像素各一位），
再调 `lp_rast_shade_quads_mask_sample`。

所以 llvmpipe 的「快」有一半在这儿：**大多数像素根本不逐个测**，整块接受或整块丢掉。

**二、片元着色器的执行单位是 2×2 的 quad，四个像素按 SoA 摆。**
`lp_bld_interp.c:53-87` 那段注释说得很死：一个 block 是 2×2 个 quad、一个 quad 是 2×2 个
像素；四个像素的绿通道躺在**同一个向量寄存器**里 —— `{g0,g1,g2,g3}`。
`quad_offset_x/y[16]`（`:117`）就是那 16 个像素在块内的坐标。

**三、插值是 `a = a0 + x*dadx + y*dady`，一条 fmuladd 两次。**
`interp_attrib_linear` 就这三行。系数（`a0`/`dadx`/`dady`）是 setup 那一步按三角形算好的，
插值这一步只做仿射求值。`lp_bld_interp.h` 头上那句更要紧：**只有第一个 quad 做乘法，
后面的 quad 全靠加法**（沿 x 走一步就加 `dadx*2`）。

`enum lp_interp` 只有六种：`CONSTANT`、`COLOR`、`LINEAR`、`PERSPECTIVE`、`POSITION`、
`FACING`。`COLOR` 按 flatshade 状态化成 `CONSTANT` 或 `PERSPECTIVE` 之一 —— 也就是说
**「插值方式」是编 shader 变体时就定死的常量，不是运行期分支**。

**四、透视除法「每 quad 一次」这条优化 mesa 自己关着。**
`lp_bld_interp.c:103-114`：本来想在 quad 左上角算一次 `1/w`、其余三个像素用线性近似，
注释写着 “Ironically, this actually makes things slower —— 除法单元闲着，乘法单元反而饱和”，
于是 `PERSPECTIVE_DIVIDE_PER_QUAD 0`。**这是一条现成的教训**：别照着「省除法」的直觉做。

**五、整条片元管线是 JIT 出来的一个 C 可直接调的函数。**
`lp_state_fs.c` 文件头列的顺序：early depth test → 片元着色器 → alpha test →
depth/stencil test → blending。它还点明一处复杂性的来源：**各阶段用的精度与类型不同**
（着色器用 float，深度与混色用最贴近缓冲格式的类型），而 SIMD 寄存器宽度固定，
于是「类型不同 ⇒ 一次算的像素数不同 ⇒ 大类型那几段要多生成几份实例」。

**六、变体是有上限、按状态做键的缓存。** `lp_limits.h:72` `LP_MAX_VARIANTS_PER_FS 16`、
`:84` `LP_MAX_SETUP_VARIANTS 64`，注释说 setup 变体由「片元着色器的输入签名 + 一小撮
光栅化状态（如 flatshade）」决定，很多着色器共用一个。

### 借

- **分层光栅化 + 边函数掩码**（`do_block_16`/`do_block_4` 那两级）。这是与语言无关的算法，
  也是性能的大头。第一刀就借。
- **2×2 quad 当执行单位**。第一刀哪怕是一次算一个片元，也要**按 quad 组织循环** ——
  因为 `dFdx`/`dFdy` 与纹理 LOD 天生要 quad，而且后面 SoA 化就是把这个循环换个内核。
- **`a0`/`dadx`/`dady` 的仿射插值形式**，包括「一个 quad 一次乘、后面全加」这条。
- **变体按状态做键**。我们这边没有 LLVM JIT，但「一份 GLSL + 一撮状态 → 一份编好的代码」
  这个缓存结构照借（我们的 `incr` 那一路已经有缓存的骨架）。
- **管线阶段的次序与 early-z 的位置**。这是正确性的一部分，不是优化。

### 不借

- **LLVM 与 gallivm 那一整层**。整个工程的前提是不用 LLVM —— 我们有自己的 x64/arm64 后端，
  这条线正好是它们的第一个「非 C 前端」用户。
- **NIR / TGSI 两套中间表示**。mesa 有历史包袱（`tgsi_to_nir`、`nir_to_tgsi_info`），
  我们直接 GLSL → 自己的 IR。
- **AoS 与 SoA 两条并行的路**（`lp_bld_blend_aos.c`、`lp_linear*` 那一族快路）。
  那是二十年攒下来的特例，第一刀一条路走通再说。
- **多重采样**（`MULTISAMPLE` 那些 `#ifdef`）、**stencil**、**双源混色**、
  **纹理采样**、**几何/计算着色器**。两档尺子（`benchmark.py`、`pretty_render.py`）
  一个都用不到。
- **透视除法每 quad 一次**。mesa 量过是负优化，直接跳过。

## 决策一：GLSL 先接到 MIR，一次一个片元；但循环按 quad 组织

这是「还没定的」第 2 条的答案。三个候选：

- (a) GLSL → **现有的标量 MIR**，一次算一个片元
- (b) 先给 MIR 长出**向量那一格**（SoA、typed vector），后端学 NEON/SSE，再接 GLSL
- (c) 另起一个着色器专用的小 IR，向量化当成它到 MIR 的一个 pass

**选 (a)，理由是「先有能量的东西」：**

- (b) 是这条线上最大的一笔改动（MIR 的类型系统、两个后端的向量指令、寄存器分配），
  而它换来的是**倍数**上的性能 —— 可我们现在连一个能跑出像素的实现都没有，
  没有基线的倍数是空话。llvmpipe 那边 SIMD 是 2010 年就有的事，但它的**结构**
  （quad 循环 + 每通道一个向量）本身在标量下也成立：把 `{g0,g1,g2,g3}` 换成
  循环四次，逻辑一字不改。
- (c) 多一层 IR 就多一层要维护的不变量，而 GLSL 的语义（标量/向量、swizzle、内建）
  离 MIR 并不远。真需要一层，那也该是**在 MIR 之上加向量单元**，不是旁边另立一套。
- (a) 立刻能拿到两条腿（JS 与 native）跑同一份 GLSL，`fbo.read()` 那口径下的
  三个数与像素图都能量 —— 也就是**尺子立刻能用**。

**为了不把 (b) 堵死，第一刀必须守住两条形状：**

1. 片元着色器编成一个**「吃一个片元、吐一个颜色」的函数**，它的输入由一个显式的
   「插值」步骤提供（`a0 + x*dadx + y*dady`），不允许在着色器体里直接摸像素坐标以外的东西。
   这样 SoA 化就是「把这个函数的参数与返回值从标量换成 4 宽向量」，而不是重写。
2. 遍历顺序**按 quad**（2×2），不按扫描线。理由在上面第二条量里。

什么时候动 (b)：等第一档尺子（`FRAG_SIMPLE`/`FRAG_COMPLEX` 五个尺寸）在两条腿上都有数
之后，拿那组数与 llvmpipe 的比，**用差距决定值不值得**。这一条写在这儿，是为了将来不必
靠回忆来判断。

## 决策二：像素比对的口径，量法先定下来

第 3 条还不能定（还没有实现能出图），但**量法**现在就能定，免得将来事后挑一个宽松的：

## 落地：第一刀第一片 —— 语法表与五份尺子源码

只做**语法**，一行降级都没有。`src/core/frontend-glsl/glsl.grammar`，走的是与 jancy 那条线
同一条路（`.grammar` 是数据 + GLR 引擎，类型定向的那一半留给将来的 `lower.js`）。

三件事值得写下来：

**一、这张表是干净的 LR —— 0 处冲突。** 206 个状态、`(prefer …)` 一处都没有。
GLSL 在这个子集里没有 C 那种「要先知道名字是不是类型」的真歧义，因为**类型全是关键字**。
jnc 那份有 3 处真歧义靠 `prefer` 压，这份一处都不需要 —— 有歧义就是我写错了。

**二、`(prec X)` 必须紧跟在 RHS 之后**（`glr/grammar.js:133` 那个 while 只在动作之前扫）。
我第一版写成 `(-> ("-" expr) (neg $2) (prec UNARY))`，`(prec UNARY)` 落在动作后面等于没写：
表里多出 **23 处冲突**，而且 `-a * b` 分成 `(neg (mul a b))` —— 一元负号变得比乘法还松。
`a + b * c` 那两条断言是绿的，因为它们不涉及一元。挪到动作前面之后冲突归零。
**这类错不会让门直接红，只会让图变成另一张画。**

**三、`discard` 收进语法，但不实现。** 不收的话 `discard;` 会被当成「一个叫 `discard` 的
变量」悄悄分析成 `(expr-stmt (name discard))`（量过）。语法里有一条 `(discard)` 之后，
「这一刀不收」这句话由降级那一侧明着说 —— 靠语法碰巧不认，等于把错误藏进一个合法形状里。

`layout` 反过来：关键字表里每个词都得是某条规则用到的终结符（不然构表就骂），
而 `layout(location = N)` 这一刀不收，于是它**不在**关键字表里。

## 落地：第一刀第二片 —— 类型检查与名字解析

`src/core/frontend-glsl/check.js`。出来的是一棵**带类型的树**，不是在原树上挂属性 ——
降级那一侧要的是「每个节点的类型已经定了」，让它再算一遍等于把同一套规则写两遍，
而两遍必然会分叉。

四处决定，都写在文件里：

**一、`stage` 由调用方给，不猜。** 猜是能猜的（看有没有 `gl_Position`），但猜错的那一次会把
「顶点里写了 `gl_FragCoord`」变成「哦这是一份片元着色器」，错误就此消失。内建变量因此是
**分档的两张表**：`gl_VertexID`/`gl_Position` 只在顶点档，`gl_FragCoord`/`gl_FragDepth` 只在
片元档。用错了报的不是「没见过这个名字」，而是「它是片元着色器的内建变量，而这是一份顶点
着色器」——差一句话，查起来差很多。

**二、隐式转换只有一条：`int` -> `float`**（规范 4.1.10，`ivecN` -> `vecN` 也在里头）。
别的一律骂。悄悄转的话 `float f = someVec3;` 会变成「取第一格」——那是能跑的错。

**三、内建函数按**形状**分类，不是一条条重载**：`gen1`（`sin`/`abs`…）、`gen2`（第二个参数
可以是标量，`min(vec3, float)` 合法）、`gen3`（`clamp`/`mix`/`smoothstep`）、`len`、`dot2`、
`cross`。「第二个可以是标量」不是我编的，是规范 8.3 里那几组重载；而 `sin(x, y)` 那种不存在。

**四、`discard` 在这儿骂。** 语法里那条 `(discard)` 就是为了让这句话有地方说 —— 语法不收的话
`discard;` 会被当成「一个叫 `discard` 的变量」悄悄收下。

### 一处真错误，门当场抓到

比较运算（`< > <= >=`）第一版写的是「回两边提升出来的那个类型」，于是 `i < 20` 的类型是 `int`。
结果 `for (int i = 0; i < 20; i++)` 被条件那道检查骂成 **「整数不能当条件」** —— 报错离题，
而真正的错在两百行之外。比较**回 bool**，与两边是什么无关。这一格现在门里单列一条。

- 五份尺子源码都过，而且**接口摸出来的形状对**：`pretty.frag` 是 2 个 uniform
  （`u_res:vec2`、`u_time:float`）、1 个 varying（`v_uv:vec2:smooth`）、1 个 const、

## 量：降级要接的那一层长什么样（第三片开工前）

决策一说的是「接 MIR」。动手前先量了**核心方言**（`sexpr/lower.js`，jancy 与 asy 都降到它，
五条腿从它出发），因为如果 GLSL 降到方言而不是直接降到 MIR，JS 与 C 两条腿是**白得的**。
量出来三条，其中一条推翻了我原来的打算。

**一、方言已经有向量那一格。** `(vec real 4)`、`(splat T E)`、`(vlit T E…)`、`(lane E N)`、
`(hsum E)`（`tests/sexpr/cases/03-simd.sx`）。也就是说决策一里「将来 SoA 化要给 MIR 加向量」
这件事，在方言这一层**已经有了第一阶段**。这不改变决策一（第一刀仍然一次一个片元），
但它把「以后怎么接」从「要新造一格」变成「要接上已有的那一格」。

**二、`rmath` 的名单比我以为的宽得多，可代价写在明处。**
我原本按 `01-core.sx` 里那句注释以为只有七个（sqrt/fabs/floor/ceil/round/fmod/pow），
于是准备「自己写 sin/cos 多项式」。**读代码发现不是**：`RMATH` 现在有 26 条，
sin/cos/tan/exp/log/atan2/hypot 全在（`sexpr/lower.js:101`），判据是
「C99 math.h 与 ECMA-262 Math 的**交集**」，实现只是转手宿主的库。

代价在 `src/runtime/omni_math.c` 的头注里，是量过的数：20 万个输入上
sin/cos/tan/atan/exp/log 的 120 万个结果里 **51.1 万个位不同**，按 `%.15g` 印出来 31.7 万个
字符串不同；拿 `bc -l`（scale=45）当参考，**libm 与 V8 谁都不是正确舍入**（macOS libm 的 sin
在 400 个输入里 28 个差 1 ULP，V8 22 个，还不是同一批）。

对这条线的意思很直接：**GLSL 那两份尺子重度用 `sin`/`cos`，所以 JS 腿与 C 腿之间
本来就不可能逐字节相同**。这不是我们的实现问题，是宿主数学库的事实。于是：

- 「五条腿逐字节相同」这条纪律对 GLSL 这一路**不适用**，走 `tests/asy/tol/` 那一节的口径
  （腿与腿之间只要求最后一位十进制差不超过 1）——**先例已经有了，不必新立规矩**
- 与决策二正好同向：像素比对本来就是容差的。两处容差是同一个来源

**三、方言的 `real` 是 double，GLSL 的 `float` 是 32 位。** 这是一处**真差别**，写在明处：
llvmpipe 那边整条片元管线是 float32（`lp_bld_type.c` 的 `type.width = 32`），我们按 double 算
再落成 8 位颜色。方向上这只会让我们**更准**，但「更准」在逐像素比对里同样是差别。
所以第三片落地时要顺手量一格：同一份 `FRAG_SIMPLE`，double 算与 float32 算的 8 位输出差几格。
若是 0，这件事就此了结；若不是 0，那就得在算完之后**每一步都截回 float32**（llvmpipe 就是
那样，因为它的向量类型就是 float32）。

### 于是第三片的形状定了

- GLSL 带类型的树 -> **核心方言**（不是直接到 MIR）。理由：JS 与 C 两条腿白得，
  而用户要的正是这两条腿的性能对照。
- `vecN` 拆成 N 个 `real`（决策一：一次一个片元，标量）。**不用方言的 `(vec real 4)`** ——
  那一格是「一次算 4 个片元」用的，不是「一个 vec4」用的。混用会把两件事搅在一起。
- 内建函数走 `rmath`，`fract`/`mix`/`clamp`/`smoothstep`/`length`/`normalize` 这些
  GLSL 特有的在降级里展开成方言的算术（它们都是几行算术，不必是内建）。
- 门的口径：容差，不是逐字节。理由在上面第二条。

## 落地：第一刀第三片 —— 降到核心方言，两条腿都跑起来了

`src/core/frontend-glsl/lower.js`。出来的是**核心方言文本**（与 jnc/asy 同一个出口），
于是 JS 腿与 C 腿一行没写就有了。

四处形状：

**一、每个中间结果都绑一个 `let`（三地址式）。** 不绑的话「一个向量表达式被 N 个分量各用
一次」会把它算 N 遍 —— `vec2(cos(a), sin(a)) * (0.55 + 0.15*sin(u_time+fi))` 里那个标量因子
会被算两次。既错（副作用）又慢，而这条线是要量性能的。

**二、片元着色器编成一个签名定死的函数**：

```
(fn glsl_frag ((frag_x real) (frag_y real) (<uniform 的每一格> real…)) glsl_v4 …)
```

uniform 走**参数**而不是全局 —— 这个函数没有隐藏输入，将来 SoA 化要换的只有参数与返回值的
类型（决策一那两条形状里的第一条）。`gl_FragCoord` 只给 `.xy` 两格真值，`.z`/`.w` 是 0/1
（这一档没有深度、没有透视）。

**三、`vecN` 拆成 N 个 `real`；只有「回向量的函数」用结构体。** 参数是**摊平**的
（`vec2 p` -> `p_0`、`p_1`），因为方言的参数表本来就能有多个；只有返回值躲不开，
于是 `(struct glsl_v3 (c0 real) (c1 real) (c2 real))`，调用处当场拆成 N 格。
一次调用一个 `(new)` —— 将来嫌它慢，办法是把这类函数内联，不是改这一层的形状。

**四、`min`/`max`/`smoothstep` 落成 `let` + `if`。** 方言没有表达式级的条件
（没有 `? :`），所以这三个（以及将来的 `clamp`/`step`）只能是语句。`smoothstep` 照规范 8.3
展开：`t = clamp((x-e0)/(e1-e0), 0, 1); return t*t*(3-2t)`。

### 一处真错误，门当场抓到

`for (int i = 0; …)` 写两遍 —— GLSL 里各是一层作用域，可 `for` 落成方言的 `while` 之后
`(let i_0 …)` 摆在 `while` **外面**，于是同一层里声明了两次，方言当场骂
`'i_0' 在这一层已经声明过了`。修法是局部量名字**一函数一份唯一**（重名的第二个起加个号）。
`bench-complex.frag` 正好有两个 `for`，所以这一格是被尺子逼出来的，不是我想到的。

### 门：`tests/glsl/lower.js` 11/0

- `FRAG_SIMPLE` 在 **JS 腿与 C 腿**上各跑 12 个像素、48 个数，**一致到容差**。
  容差不是逐字节：`cos` 是超越函数，libm 与 V8 在最后一位分叉（量过的数在上一节）。
  口径照 `tests/asy/tol/`。
- 48 个数与**门自己独立算的同一个公式**一致。这**不是 oracle**（真尺子是 llvmpipe）——
  它查的是「降级没有把公式改掉」：少一次乘、swizzle 取错一格、uniform 接错一格，这条都会红。
- `FRAG_COMPLEX`（第一档第二份，含两个 `for`、两个自定义函数、20+10 次 SDF）也跑得动。
- 6 条「还没接的要明着骂」：矩阵、三元、varying、`mix`、`if`、顶点着色器。

### 还缺什么才能与 llvmpipe 比图

这一片只到「一个像素一个函数」。还差：把画布扫一遍（**按 quad**，决策一第二条）、

不然「与 llvmpipe 比」是句空话。

## 落地：第一刀第四片 —— 把画布按 quad 扫一遍

`glslRenderMain` / `glslProgram`（同一份 `lower.js`）。库 + 这一段 = 一个能跑的方言程序。

**顺序是 llvmpipe 的最内两层**（`lp_bld_interp.c:53-87` 那张图）：一个 2×2 quad 里四个像素
按「左上 右上 左下 右下」，quad 之间按行。为什么现在就要这个顺序（一次明明只算一个片元）：
`dFdx`/`dFdy` 与纹理 LOD 天生要 quad，而 SoA 化就是把这个循环的**内核**换掉 ——
顺序现在定死，将来换内核时图不会变。

宽高不是 2 的倍数时，边上那些格子**照样算、但不印** —— llvmpipe 也是这样（边上的 quad
用掩码丢掉几个像素，而不是缩小 quad）。门里用 6×5 就是为了压这一格。

**印文本不写 PNG**：方言这一层没有文件 IO（只有 `print`），而这是**故意**的 ——
一门中间语言不该长出文件系统。于是一个像素五个 `print`（`x y r g b`），PNG 由外面拼。
代价写在明处：`print` 的开销在小画布上就盖过着色器本身，所以**性能对照不能走这条路**，
那要另一个不印东西的 main（第五片）。

一格实现上的小事，也记着：一个像素五个 `print`，没有拼成一行 —— 方言的 `+` 是「同型相加」，
`int + string` 不在它的规矩里，绕过去只会让这段更难看。

### 门：`tests/glsl/render.js` 5/0

- 6×5 印出 150 个数，30 个像素**每个正好一次**、没有出界的
- 次序**就是** quad 次序（逐个比，不是抽查）
- 30 个像素的 8 位值与门自己算的 `round(clamp(v,0,1)*255)` 相同
- **C 腿与 JS 腿的 8 位像素逐字节相同**。这一条值得单列：`cos` 在两条腿上只到容差
  （上一节那些量过的数），但 8 位那一步把最后一位的差**抹掉了** —— 于是在**像素**这一层
  两条腿反而是逐字节的。这是一个好消息：将来与 llvmpipe 比图时，我们自己这几条腿之间
  不必先谈容差。

## 落地：第一刀第五片 —— 量性能那一段（不判快慢，判「量的是同一件事」）

`glslBenchMain` / `glslBenchProgram`。**一个字节都不印**，只在最后印一个校验和。

两处理由，都得写下来：

- **为什么不拿第四片那条路量**：那一段一个像素五个 `print`，量出来的是 `print` 的耗时不是
  着色器的（128×128 上前者就盖过后者）。
- **为什么要有校验和**：不攒一个用得到的结果，整个循环会被后端当死代码扔掉 ——
  那时量出来的是「什么都不做要多久」。攒的是每个像素三格 8 位值的和，与第四片印出来的
  那些数一一对应。

门里那条最要紧的断言就是这一点：**同一尺寸下校验和正好等于印出来那些 8 位值之和**。
一个量错东西的 benchmark 比没有 benchmark 更坏。另外还查「迭代 3 遍的校验和正好是 3 倍」——
循环没被折叠掉的证据。

### 门：`tests/glsl/bench.js` 4/0

**这一门不判快慢**（写死一个毫秒数只会在别的机器上骗人）。耗时只当**参考**印出来：

那是与 llvmpipe 对照时才需要的口径，等 mesa 那一头解决了一起做。

## 落地：第一刀第六片 —— 第二档的降级（除了插值）

第二档（`pretty_render.py`）语法与类型检查上一片就收了，这一片把**降级**补上：
`mat2` 与四种矩阵乘、三元 `? :`、`if`/`else`/`while`、
`mix`/`clamp`/`step`/`sign`/`fract`/`normalize`/`dot`/`distance`/`cross`/
`inversesqrt`/`radians`/`degrees`。

四处要紧的，每一条都能悄悄错：

**一、矩阵是列优先**（规范 5.6）：`mat2(a,b,c,d)` 的第 0 列是 `(a,b)`，所以
第 `col` 列第 `row` 行是下标 `col*N + row`。**记错就是转置** —— `rot(a)` 变成反方向的旋转，
一个数都不会 NaN，只有对着图才看得出来。门里那两条（`mat2*vec2` 与 `vec2*mat2`）
挑的数就是为了分开这件事：拿 `mat2(0,1,-1,0)` 乘 `(1,0)`，列优先得 `(0,1)`、
行优先得 `(0,-1)`——差一个符号。

**二、`matN(x)` 是对角线填 `x`**，不是每格都填（规范 5.4.2）。填成四个 1 的话
`mat2(1.0)` 就不是单位阵了。

**三、`mix` 照规范写 `x*(1-a) + y*a`**，不写成 `x + (y-x)*a`。两者代数上相等，
浮点下不等价：`a == 1` 时前者精确回 `y`，后者不一定。门里第二格就是 `a=1`。

**四、三元的两支各自的中间量留在自己那一支里。** GLSL 的 `? :` 只算一支，
把两支的 `let` 都提到 `if` 外面就变成两支都算 —— 不只是慢：`1.0/z` 那种在不该走的
那一支里可能是除零。门里那条探针就是 `z > 0.0 ? 1.0/z : 7.0`（`z` 是 0）。
反过来 `if` 语句的条件**可以**提出去，因为它本来就要算一次。

`if` 落成方言的 `(if c (do …) (do …))`，`while` 走 `condIn`（条件每轮重算，
所以要求它降出来是一条表达式）。

### 还剩什么

- **插值（varying）**：`in vec2 v_uv` 还是明着骂。这是第二档里唯一的真活 ——
  要 `a0`/`dadx`/`dady` 那一套（llvmpipe 的 `lp_bld_interp.c`），而那要先有
  「三角形 setup」这一步。它值一片。
- **顶点着色器**：同上，插值的另一半。
- 纹理、结构体、数组、`switch`、`do`：两份尺子里一个都没有。
  （`m[0]` 与 `continue` 从前也在这一行上，第十七、十八片接上了；
  下标里还挡着的只有**动态**那一种。）

## 量：`gl_FragCoord.y` 与缓冲行序（写 PNG 之前必须知道的一格）

第四片那个扫描循环把「行号」直接当成 `gl_FragCoord.y - 0.5`。**这一格是对的，但理由要写下来**，
因为它决定写 PNG 时要不要翻转：

- GLSL 330 规范 7.2：`gl_FragCoord` 是**窗口相对**坐标，原点在**左下**
  （除非用 `layout(origin_upper_left)`，两份尺子都没用）。
- 尺子自己的代码印证了这一点：`pretty_render.py:136-137`

  ```python
  img = Image.frombytes("RGBA", size, data)
  img = img.transpose(Image.FLIP_TOP_BOTTOM)
  ```

  `fbo.read()` 出来的第 0 行是**最下面**那一行，所以要翻一次才是给人看的图。

于是三件事对齐了：我们循环里的 `qy = 0` 是**画布最下面**那一行、`gl_FragCoord.y` 从下往上长、
将来写 PNG 时**要翻一次**（或者写的时候按倒序写行）。三者只要有一处记反，图就是上下颠倒的 ——
而颠倒的图每个像素的值都"对"，逐像素比对**照样全红**，那时候最难查的是「到底谁反了」。

## 落地：第一刀第七片 —— 顶点着色器与插值（第二档齐了）

`glslTriProgram`（同一份 `lower.js`）：顶点 + 片元 + setup + 插值，一整条。

**形状照 llvmpipe 那条分界**（ADR-0019「量：读 llvmpipe」第三条）：
「一个三角形一次」的 setup 算 `a0`/`dadx`/`dady`（一条方言函数 `glsl_plane`，三点定平面），
「一个片元一次」的求值就是 `a = a0 + x*dadx + y*dady`。片元入口因此多了 varying 参数 ——
**插值不在片元函数里**，与 `lp_bld_interp.c` 是独立一块同一个道理。

四处决定：

**一、透视校正做全，不限制 `w = 1`。** 标准做法：插 `a/w` 与 `1/w`，片元处相除。
两份尺子的 `gl_Position.w` 都是 1，此时它**精确**退化成线性插值 —— 所以本来可以偷懒
写线性、再写一句「w 必须是 1」。做全的理由是那句限制迟早要还，而代价只是多插一个 `oow`。

**二、三档插值方式是编译期定死的常量**，运行期没有分支（与 `enum lp_interp` 一样）：
`smooth` 除 `oow`、`noperspective` 不除、`flat` 直接取**第三个顶点**
（GL 4.x 默认的 provoking vertex 是 last）。

**三、顶点那一侧的函数名加前缀 `glsl_v_`。** 顶点与片元是两份源码，里头的辅助函数**可以同名**
（两边各有一个 `sdCircle` 很正常），并到一个方言模块里就撞了。

**四、这一段不做覆盖判定。** 两份尺子都是「一个三角形铺满整个视口」，所以每个像素都在里头。
真正的边函数掩码（`do_block_16`/`do_block_4`）是下一片。**写在明处**：现在喂一个不铺满的
三角形，它会把外面也画上。

### 门：`tests/glsl/interp.js` 6/0

- **varying 插得对，而且期望值是手算的**：全屏三角形上 `v_uv = p*0.5+0.5` 在三个顶点是
  `(0,0)/(2,0)/(0,2)`，窗口坐标是 `(0,0)/(2W,0)/(0,2H)` —— 插出来精确等于
  `gl_FragCoord.xy / 分辨率`。24 个像素逐个比。
- `flat` 全取第三个顶点。
- **透视校正不是摆设**：`w` 不全为 1 时 `smooth` 与 `noperspective` **必须不同**；
  `w` 全为 1 时两者**逐字节相同**。后一条是定义，前一条是「那一下除法真的在做」的证据 ——
  少了它，把 `smooth` 写成线性也能全绿。
- 两条腿的 8 位像素相同（含 `sin` 与插值）。
- **第二档那份完整的着色器跑通**：`pretty-vert.vert` + `pretty.frag`（hex 网格 + 发光圆 +
  `hsv2rgb` + 色调曲线 + `pow`）8×8，像素和 11489（查「不是一片全黑」——那是插值或 uniform
  接错时最常见的样子）。

第二档到这儿**齐了**。剩下的是真正的光栅化（覆盖判定）与与 llvmpipe 比图。

<!-- ADR-0019 第七片-END -->

## 落地：第一刀第八片 —— 覆盖判定（光栅化真了）

前七片都假设「一个三角形铺满画布」。这一片把覆盖判定接上：三条边函数，逐像素三次叉积，
**三条都 `>= 0` 才着色** —— 不覆盖的像素连片元函数都不调。

公式与符号约定写在 `lower.js` 里，这里只记要紧的两条：

**一、`e` 与 `area` 必须同源。** 用叉积：`e_j(p) = cross(b-a, p-a)`，而
`area = cross(v1-v0, v2-v0)` 就是同一个叉积 —— 于是「面积为正 ⇒ 内部 e 为正」自动成立。
第一版我把 `e` 写成 `(x-xa)*(yb-ya) - …`（反的），全屏三角形上三条边函数**全为负**，
一个像素都没画，门当场全红。

值得记的是**如果当时只有「全屏三角形能画」这一条门**，我很可能把 `>=` 改成 `<=` 蒙过去，
而那在另一种绕向上又是错的。所以这一片的门里专门有一条「绕向反过来画的是同一片像素」。

**二、`sgn` 那一格（绕向）是必要的**，不是保险：顺时针的三角形三条边函数整体反号，
少了它会被判成「全在外」，一个像素都不画。llvmpipe 是在 setup 里把三角形拧成固定绕向
（`lp_setup_tri.c`），一回事。

**还没做的两处，写在明处**：

- **边上的归属规则**还不是 GL 的 top-left（现在 `>= 0` 含边）。只有两个三角形共享一条边时
  才看得出来 —— 那条边上的像素会画两遍。**（第九片补上了。）**
- **分层加速**（llvmpipe 的 `do_block_16`/`do_block_4`：16×16 块一次判 16 个 4×4 子块的
  全内/全外/骑边）还没做。现在是逐像素三次叉积 —— **正确但没有加速**。
  分层是性能优化，等有了基线再说值不值（与决策一同一个道理）。

### 门：`tests/glsl/raster.js` 4/0

- **半覆盖**（clip `(-1,-1) (1,-1) (-1,1)`，8×8 上盖 36/64）：画的是**哪些**像素逐个比，
  期望集合由门**自己**用叉积算（独立实现，不抄降级那一侧）。门里还有一句「这个探针要有
  区分度」——盖 0 个或盖满 64 个都算门坏了。
- 绕向反过来画的是同一片 36 个像素。
- 全屏三角形照旧铺满 64 个（前七片的门靠的就是它，这是回归）。
- 不覆盖的像素连片元都不调：片元里写一个必然除零的算式，印出来的像素数正好等于覆盖数。

<!-- ADR-0019 第八片-END -->

## 落地：第一刀第九片 —— 边上的归属规则（不重不漏）

第八片的覆盖判定在边上用 `>= 0`，于是两个共享一条边的三角形会把那条线**各画一遍**。
这一片补上归属规则：`in_j = (e_j > 0) || (tl_j && e_j == 0)`，其中
`tl_j = (sdy > 0) || (sdy == 0 && sdx < 0)`（`sdx`/`sdy` 是那条边的方向，乘过绕向 `sgn`）。

两处要紧的：

**一、判据必须对边的方向是奇的。** 方向反过来 `tl` 就反过来 —— 于是两个共享边的三角形
（绕向都归一之后，那条边在两边的方向正好相反）里**恰好一个**认领它。不重不漏因此是
这个判据的性质，不是碰巧。

**二、`sdx`/`sdy` 要乘 `sgn`。** 绕向归一化只改了 `e` 的符号、没改边的方向；不跟着乘的话，
同一片像素在两种绕向下会得到不同的归属 —— 而第八片那条「绕向反过来画的是同一片」正好压它。

**这一片刻意不声称与 GL 一致。** GL 的 top-left 规则说的是「哪一侧归谁」，而验证它要一台有
GL 的机器（ADR 待办第 12 条）。这一片能保证的是**不重不漏** —— 那是填充规则的定义性性质，
不用 GL 也验得了。与 GL 差一个整体翻转的可能性**留着，写在这儿**：真要对上，
量一次 llvmpipe 的输出就知道，而那时候改的只有 `tl` 那一行。

### 门：`tests/glsl/raster.js` 4/0 → 5/0

新增那一条是**方块拼接**：两个三角形共享斜边拼成 8×8，`36 + 28 = 64`，**交集为空、并集铺满**。
第八片那时候这条会红（斜边上那 8 个像素两边都画）。

`coverOf`（门自己那份独立实现）也跟着实现同一套规则 —— 它查的是「实现符合设计」；
「设计对不对」由方块那一条查。

## 量：这台机器上取得到什么尺子

决策二说尺子是 llvmpipe，而前面几片一直写着「本机是 macOS，取不到」。**这一次真去量了**，
结论比之前写的乐观：

- `python3 -c "import moderngl"` —— **在**（moderngl 5.12、PIL 也在）
- `moderngl.create_standalone_context()` —— **建得起来**，`GL_RENDERER` 是
  **`Apple M1`**、`GL_VERSION` 是 `4.1 Metal - 90.5`。也就是说本机取得到**真 GPU 的 GL**，
  而且 4.1 core 正好收 `#version 330 core`。
- `docker` 的 CLI 在，但 daemon（OrbStack）**没起** —— llvmpipe 那条路还是断的。

于是这条线上多了一台**能用的尺子**：硬件 GL。它不是 llvmpipe，但**规范规定的那些格上
它一样管用**：覆盖判定、填充规则、插值、透视、`gl_FragCoord` 的原点、缓冲行序、
8 位量化。只有 `sin`/`cos`/`smoothstep` 那种实现自由度上两者才可能分岔 ——
而那正是决策二要量的「容差」。

**「取不到尺子」这句话是我没量就写下的。** 记在这儿，因为它耽误了好几片
（前九片全是自证，本来第一片就能有外部 oracle）。

## 落地：第一刀第十片 —— 与真 GL 比像素，**最大差 0**

`tests/glsl/gl_ref.py`（尺子那一侧：moderngl 渲一份 vert/frag，逐像素印 `x y r g b`）
+ `tests/glsl/oracle.js`（比）。

**结果：三份用例、16×16、最大逐通道差 `0`。**

- `bench-simple`（第一档）
- `bench-complex`（第一档，30 个 SDF、两个 `for`、两个自定义函数）
- `pretty`（第二档，varying + `mat2` + `hsv2rgb` + 色调曲线 + `pow`）

也就是说这一整条 —— 顶点着色器、裁剪空间到窗口坐标、三角形 setup、透视校正插值、
覆盖判定、边上的归属、quad 扫描、8 位量化，以及 `sin`/`cos`/`pow`/`smoothstep` 的数值 ——
与 Apple M1 的 GL **逐字节相同**。

顺带把两件之前「写在明处的不确定」定下来了：

- **`gl_FragCoord` 的原点与缓冲行序对了**：差一个翻转的话 16×16 上会有大片不同（图上下颠倒）。
- **填充规则与 GL 同侧**（第九片写着「差一个整体翻转的可能性留着」）：全屏三角形上
  斜边不在画布里，所以这一条严格说还只是**弱证据**；强证据要一个斜边穿过画布的三角形，
  记在待办里。

### 容差为什么定 1 而不是 0

门里 `TOL = 1`。第十二片把画布加大之后，这个 1 **不是保险了，是真的会用到**（量出来的）：

- 64×64（4096 像素 / 12288 通道）：`bench-simple` 0 差、`half` 0 差、
  `bench-complex` **2 个通道差 1**、`pretty` **1 个通道差 1**
- 128×128 `bench-complex`（16384 像素 / 49152 通道）：**3 个通道差 1**，其余全同

16×16 上量到全 0，是**样本太少没踩到** —— 这一条本身就是「小画布的绿是弱绿」的证据。

差 1 的来历有两层，都写下来：

- 8 位量化把 `round(v*255)` 的边界放大 —— `v` 差 `1e-9` 也可能让整数差 1；
- 超越函数（`sin`/`cos`/`smoothstep` 里的乘除）在 GPU 与 libm/V8 之间差 1 ULP 是常态
  （`src/runtime/omni_math.c` 头注里那 51.1 万个位不同的量就是这件事）。

所以 `TOL = 1` 是「量出来的 0/1 + 一格已知的实现自由度」，不是拍的。门每次把**实测最大差**
与**差 1 的通道数**都印出来 —— 这两个数往上走的那一天会被看见。

没有 `python3 + moderngl` 的机器上整组**跳过**（印 skip 并说明），不假过。

## 落地：第一刀第十一片 —— 填充规则的方向，量出来了（而且是反的）

第九片实现了「边上的样本归一个三角形」，并明写着「与 GL 差一个整体翻转的可能性留着」。
第十片用的三份用例都是**全屏三角形**（斜边在画布外），所以那个可能性一直没被碰到。

这一片加了一份**斜边穿过画布**的用例（`half-vert.vert` + `half.frag`，clip
`(-1,-1) (1,-1) (-1,1)`，16×16 上斜边正好经过 16 个像素中心）。第一趟就红了：

```
超差 48 个通道（共 408 个），最大差 191
最坏那一处 15,0 通道2：尺子 0 / 我们 191
```

48 = 16 个像素 × 3 通道 —— **正好是斜边上那 16 个**。GL 判它们**在外**，我们判在内。
于是把判据翻过来：`tl = (sdy < 0) || (sdy == 0 && sdx > 0)`。

三件事因此同时成立：

- `oracle` 四份用例全部 **最大差 0**（含这一份 120 个像素）；
- `raster` 那五条**照旧全绿** —— 判据仍然是**奇函数**，所以「不重不漏」不受方向影响
  （方块拼接从 `36 + 28` 变成 `28 + 36`，和还是 64）；
- 第九片那句「留着的可能性」被量掉了。

**这一格对齐的是本机那台 GL**（Apple M1）。GL 规范只要求「边上的样本恰好归一个三角形」，
没规定归哪个 —— 所以 llvmpipe 那边要再量一次。写在 `lower.js` 的注释里与这儿。

值得记的是这一片证明了第九片那句自我怀疑是对的：**当时没有把「与 GL 同侧」当成已知**，
而是明写「还没量」。三片之后量到的结果正是反的。

## 落地：第一刀第十二片 —— 把画布加大，容差从「保险」变成「量出来的」

第十片只比 16×16，全 0 差。**那是弱绿** —— 样本太少。这一片把 oracle 提到 64×64
（4096 像素 / 12288 通道），另加一档 128×128 的 `bench-complex`（49152 通道）。

结果（也就是上面那节容差的来历）：

- 64×64：`bench-simple` 0 差、`half` 0 差、`bench-complex` **2 个通道差 1**、`pretty` **1 个**
- 128×128 `bench-complex`：**3 个通道差 1**，其余全同

门现在把**最大差**与**差 1 的通道数**都印出来。整门 1.4 秒（我们那一侧 128×128 要印
8 万行，再往上就是在量 `print` 而不是量像素了 —— 那是第五片那条 bench 路的事）。

## 落地：第一刀第十三片 —— 第一张性能对照表

`tests/glsl/gl_bench.py`（GL 那一侧，照 `benchmark.py` 的口径：warmup 一帧 + N 帧，
**每帧含 `fbo.read()`**）+ `tests/glsl/perf.js`（我们这一侧 + 印表）。
**这不是门**（不判快慢），是一支可重复的尺；默认不进 `run.js`。

**怎么把「进程启动 + 编译」摊出去**：两趟差值 `t(2N) - t(N) = N 帧的净渲染时间`。
固定开销（node 启动、方言降级、C 腿那边 clang 编译）在两趟里一样，减掉就没了 ——
比「跑一趟然后猜编译占多少」诚实。另外还核对「校验和成倍数」，不成倍数就说明两趟画的
不是同一件事，那个差值不能用。

本机（Apple M1）量到的第一组数，`bench-complex.frag`（30 个 SDF）：

- **128²**：我们 JS `26.0ms`（0.6 MPix/s）、我们 C `11.3ms`（1.5 MPix/s）、
  真 GL `0.419ms`（39.1 MPix/s）
- **256²**：我们 JS `186.3ms`（0.4 MPix/s）、我们 C `93.7ms`（0.7 MPix/s）、
  真 GL `0.646ms`（101.4 MPix/s）

三条读法：

1. **C 腿比 JS 腿快约 2 倍。** 同一份方言、同一套算术 —— 差的是后端。
2. **真 GL 快 60～280 倍。** 这是预期的：我们是**标量、一次一个片元**（决策一），
   而对面是硬件光栅化器。这张表的用处不是比大小，是**以后每一步优化能不能量出来**。
3. **一处待查的异常**：像素数 4 倍（128²→256²），我们 JS 的时间涨了 **7.2 倍**（超线性），
   C 腿 8.3 倍。真 GL 只涨 1.5 倍（它在 128² 上根本没吃饱）。超线性那一格得查 ——
   可能是 GC、可能是我这个差值法在 `N=3` 时噪声太大。**记下来，不猜。**

## 落地：第一刀第十四片 —— 那处「超线性」是量法的噪声，不是实现的问题

第十三片记了一处待查：像素数 4 倍而我们的时间涨 7～8 倍。**去量了，不是实现的事。**

### 怎么量出来的

把帧数**钉成同一个数**再跑（`OMNI_GLSL_N`），同一档在不同帧数下的值：

- 128² JS：`26.0` / `31.7` / `39.5` ms（N=8 / 3 / 6）—— 波动 **50%**
- 256² JS：`186.3` / `165.7` / `173.7` ms —— 波动 12%
- 而且 N=3 时 C 腿量出 **−49.0ms**（负数）

负数是决定性的一条：`t(2N) - t(N)` 里两趟的**固定开销抖动**（进程启动、V8 预热、
clang 那一趟）比净渲染时间还大。128² 一帧才十几毫秒，而抖动有几十毫秒 ——
**小画布上这个差值法根本不成立**，量出来的斜率是噪声。

### 修法与修完的数

两处：

- **每趟跑 3 次取最小**。噪声是**单向**的（别的进程、GC、频率调节只会让某一趟变慢，
  不会让它变快），所以最小值最接近「没被打扰的那一趟」。取平均会把噪声算进斜率。
- **帧数加大**（128² 从 8 提到 24），让净时间远大于抖动。

修完（同一台机器、同一份 `bench-complex.frag`）：

- **128²**：我们 JS `34.9ms`（0.5 MPix/s）、我们 C `24.6ms`（0.7 MPix/s）、真 GL `0.391ms`（41.9）
- **256²**：我们 JS `141.5ms`（0.5 MPix/s）、我们 C `96.8ms`（0.7 MPix/s）、真 GL `0.593ms`（110.5）

**MPix/s 两个尺寸完全一样**（JS 0.5/0.5、C 0.7/0.7），时间比 `141.5/34.9 = 4.05`、
`96.8/24.6 = 3.93` —— 像素数正好 4 倍，**是线性的**。超线性不存在。

整趟 37 秒（3 次 × 两趟 × 两个尺寸 × 两条腿），所以 `perf.js` 不进 `run.js`。

### 记下来的教训

第十三片那张表**结论没错**（C 快 2 倍、GL 快两个数量级），但它**多说了一句**
「有一处超线性」——而那句是量法的产物。写下「待查、不猜」是对的；如果当时顺手解释成
「大概是缓存」，就会留下一条假知识。

## 落地：第一刀第十五片 —— 量出「框架 vs 着色器」，于是分层加速**现在不值得做**

待办里排着「分层加速」（llvmpipe 的 `do_block_16`/`do_block_4`）。动手之前先量一件事：
**框架占多少**。办法是加一份 `trivial.frag`（一行算术都没有，只写一个常数），
它的时间就是「扫画布 + 覆盖判定 + 插值 + 8 位量化 + 调用」——**框架那一半**；
`bench-complex` 减掉它就是**着色器那一半**。

量到的（Apple M1）：

- **128² JS**：`trivial` 1.3ms、`bench-complex` 39.1ms —— 框架占 **3.3%**
- **256² JS**：`trivial` 7.0ms、`bench-complex` 156.0ms —— 框架占 **4.5%**
- **128² C**：`trivial` 1.0ms、`bench-complex` 24.5ms —— 约 **4%**

**于是分层加速最多能省 3～5%。现在不做。** 它在 llvmpipe 那边值，是因为那边的片元是
SIMD（一次 8 个像素），框架占比高得多；在我们这个**标量**实现里，时间几乎全在着色器里。
要提速就得动着色器那一半 —— 也就是决策一里那条「等有了基线再定」的 SoA/向量化。
**基线现在有了，那条路的理由也有了。**

### 一处不可信的数，写在明处

`trivial` 在 **C 腿 256²** 上量出 `0.1ms`（524 MPix/s）—— 那是 1.5ns/像素，不可能。
原因是 `trivial` 的结果与像素**无关**，而校验和累加的是常数，所以 clang 大概把整个
循环折成了闭式（常数 × 像素数）。**JS 腿那两个数（1.3 / 7.0ms）是可信的**（V8 没做这一步），
上面那个「框架占 3～5%」的结论就是拿 JS 腿算的。

这也提醒一件事：第五片给 bench 加校验和是为了防止死代码消除，但「校验和本身可被折叠」
是另一回事 —— 真正与像素相关的着色器（`bench-complex`）不会被折，所以那一档的数没问题。

<!-- ADR-0019 第十五片-END -->

## 量：SoA 要方言长出什么（下一刀的入口）

第十五片量出「时间 95% 以上在着色器里」，于是下一步是 SoA（一次算 4 或 8 个片元）。
动手之前**先量方言那一格的边界**（`sexpr/lower.js` 的 `vecExpr` 与 `binExpr`，
注释里写得很清楚，是刻意的「第一阶段」）：

**有的**：

- `(vec elem N)`，`elem` 只能 `int`/`real`，`N ∈ {2, 4, 8}`
- `(splat T E)`、`(vlit T E…)`、`(lane E N)`（`N` 必须是字面量）、`(hsum E)`
  （`hsum` 的求值顺序**写死成严格左到右**，因为浮点加法不结合）

**没有的**（源码里明着挡住，注释说「要先在六个执行器上定好语义，第一阶段不做，
所以在这里挡住而不是给错答案」）：

- 向量上只有 `+ - * /`；**比较、select、shuffle 都没有**
- `rmath` **只收 `real`**，不收向量
- `print` 不收向量（要看就 `(lane v k)` 逐道印）

### 于是 SoA 要三样，而且优先级分得开

1. **向量比较 → 掩码类型**（`vec<bool,N>`）。GLSL 侧 `min`/`max`/`clamp`/`step`/
   `smoothstep`/三元/`if` 全都要它 —— 在 SoA 下这些不能再落成 `if` 语句
   （四个片元的分支可能不同），必须变成掩码。**绕不过去。**
2. **`select`**（`(vsel mask a b)`）。与 1 是一对：有了掩码才能选。**绕不过去。**
3. **`rmath` 的向量版**。这一样**可以先绕**：拆成 `lane` 取四道、各调一次标量
   `rmath`、再 `vlit` 重组。收益打折（`sin`/`cos` 是 `bench-complex` 里的大头），
   但它不阻塞 SoA 的骨架。

所以下一刀的形状是：**先给方言加 1 与 2**（那是动六条腿的事，要单独一刀、单独的门），
再回来把 `glsl_frag` 的参数与返回值从 `real` 换成 `(vec real 4)`。

决策一当时写的「SoA 化就是把这个循环的内核换掉」——现在能说得更准：**换内核之前，
方言得先有掩码与 select**。这一句是量出来的，不是估的。

### 那一刀要动哪几处（量过的施工图）

`VecSplat`/`VecLit`/`VecLane`/`VecHSum` 与 `Bin(vec)` 的**消费者一共七处**
（`grep -c 'VecSplat|VecLane|VecLit|VecHSum'`）：

- `sexpr/lower.js` —— 造（方言 → OIR），也是「挡住比较与 select」那两句的所在
- `hir/types.js` —— 类型与零值（`vec` 的零值是 `VecSplat(elem 的零)`）
- `mir/from_oir.js` —— OIR → MIR，下游是 x64 / arm64 / wasm / `interp --mir`
- `backend-c/emit.js`、`backend-js/emit.js`、`backend-llvm/emit.js`（后者 23 处提到 vec）
- `interp/eval.js` + `interp/builtin.js`

所以「动六条腿」这句话量准了：**七个文件**，而且每一处都要为 `vec<bool,N>` 这个新类型
决定表示（C 那边大概是整数掩码、LLVM 那边是 `<N x i1>`、JS 那边是数组）。
这正是那两句注释说的「要先在六个执行器上定好语义」——不是随手能加的一格。

### `vec<bool,N>` 的表示：有依据的草案（下一刀开工前要定的那一格）

量了两条腿现有的 `vec` 表示（这是决定掩码怎么表示的依据）：

- **JS 腿**：`vec` 就是**数组**。`VecSplat` → `$vsplat(v, N)`、`VecLit` → `[a,b,c,d]`、
  `VecLane` → `v[k]`（`backend-js/emit.js:485-489`，注释说下标是降级期定死的字面量，
  所以没有边界检查那条路）。
- **C 腿**：`vec` 是**逐形状生成的结构体** + `_splat` 助手（`backend-c/emit.js:945-949`）。
  刻意不用复合字面量，理由写在注释里：那样会把子表达式求值 N 次，而 `(lane E N)` 的 `E`
  可能有副作用。

于是草案是「**掩码沿用同一套壳子，只换元素类型**」：

- JS：还是数组，每道是 `true`/`false`
- C：还是那套逐形状结构体，每道与**标量 `bool` 同一个表示**
  （那一刀的第一步是量清楚 `backend-c` 里标量 `bool` 落成什么 C 类型 —— 现在没量，不猜）
- LLVM：`<N x i1>`（那条腿本来就有 23 处 vec 代码，跟着它的套路）
- MIR / interp：还没量，属于那一刀的头几步

沿用壳子的好处是**七处消费者里有五处只需要多认一个元素类型**，不必新造一族类型。
`vsel` 则是三个同型参数（`mask`、`a`、`b`）的逐道选择，形状上与 `bin` 同级。

## 量：向量在五条腿上分别落成什么 —— 于是 SoA 只在一条腿上兑得出钱

上一节把「掩码 + select 要动哪七处」摊开了，但它默认了一句没量的话：**加了向量指令就会更快**。
动手前把「向量在每条腿上落成什么」逐条读了一遍，结论把待办 17/18 的**理由**换掉了。

- **JS 腿**（`backend-js`）：向量就是一个 **JS 数组**。四道加法是四次 `Array` 取下标 + 四次
  标量加，外加一个新数组。比四个独立的 `let` **更慢**（多一层间接与一次分配）。
- **C 腿**（`backend-c`）：`src/core/hir/types.js:287-291` 写得很直白 ——
  向量是**逐形状生成的结构体** `omni_vec_real_4`，即**标量化**：

  > 「C 备选路径上向量是**标量化**的（ADR-0014 决策 6 唯一许可的合法化），所以这里不是
  > `double __attribute__((vector_size(32)))` 之类的编译器扩展 —— 那会把「两条腿逐位相同」
  > 的责任交给 clang 的自动向量化，而它不保证求值顺序。」

  这不是偷工，是**刻意**的：逐位相同优先于快。
- **MIR 解释器**：也是数组（`mir/interp.js:595-620`）。
- **native 两条腿**（`x64/from_mir.js`、`arm64/from_mir.js`）：`lanes`/`VSPLAT`/`VINS`/`VEXT`
  一处都搜不到 —— **完全不收向量**。所以「native 发真 SIMD」这条路不是「优化」，
  是**从零实现一个后端能力**。
- **LLVM 腿**：这是唯一一条**原生**的。`backend-llvm/emit.js:1109` 与 `ty()` 发的是
  `<N x double>` / `<N x i64>`，splat 是 `insertelement` + 全零掩码 `shufflevector`
  （`emit.js:1555-1561`，注释里写明「clang 发的就是这个形状」）。为了求值顺序确定，
  它**刻意不发** `llvm.vector.reduce.fadd`（规约顺序由目标决定），hsum 在 OIR→MIR
  那一步就展成「逐道 VEXT + 左到右 ADD 链」；i64 的 `/` 也标量化（除零与
  `INT64_MIN/-1` 要走标量签名的 `@omni_ll_div`）。

**顺手量了一下三条能跑 GLSL 的腿有多快**（`bench-complex.frag`、128²、
`t(48)-t(24)` 差值、每档取 3 次最小，与第十三/十四片同一口径）：

- `bench-complex`：JS **39.2 ms/帧**、C **24.6 ms/帧**、**LLVM 23.8 ms/帧**
- `trivial`（框架那一半）：JS 1.25 ms/帧、LLVM 0.42 ms/帧、C 量出 0（clang 把循环折成闭式，
  第十三片记过这件事）

三条腿的输出校验和逐字节相同（3802640 / 7605280 成 2 倍），所以量的是同一件事。
LLVM 腿比 JS 腿快 1.65×，而且它**本来就是 `tests/sexpr/run.js` 五条腿之一**
（`run-llvm`）—— 只是 GLSL 这一族的门还只跑 JS 与 C 两条。

**于是：**

1. 给方言加向量比较与 `select` 是**语义补全**（把决策一里明着挡住的那一格填上），
   不是性能那一半的入口。做它的理由是「方言的向量这一格只做了一半」，不是「会更快」。
2. SoA 真要兑出钱，得**同时**满足两件事：GLSL 走 **LLVM 腿**，且那一腿的向量类型
   一路活到 `<4 x double>`。前者现在就能试（上面的数就是），后者已经成立。
   所以下一刀的顺序应该是**先把 LLVM 腿接进 GLSL 的门**，再谈 SoA。
3. 「把 GLSL 编到 native」是另一条更长的路：那两条腿得先长出向量寄存器分配。
   在 ADR-0014 的框架里这是新的一格，不属于本 ADR。

还有一个与向量无关、量到就该记的提速方向：`rmath` 的 `sin`/`cos`/`exp` 走的是 **libm 调用**
（`src/runtime/omni_math.c`），而 `bench-complex` 里全是三角函数。多项式近似能省下调用与
精度冗余 —— 但它会**改结果的位**，而「两条腿逐位相同」是我们的红线，
所以这条路要先回答「多项式近似算谁的语义」，不能顺手做。

## 落地：第一刀第十七片 —— `continue` 接上了（那一圈只走一趟的 while）

`for` 落成方言的「init + while + 体尾 step」，而 **`continue` 在这种展开里会跳过 step**。
第三片起这一格是明着骂的（`glslNyi`），理由写着「这一档一份尺子都没用到 `continue`」。
现在把它接上，形状是：

```
(while COND (do (while (bool true) (do BODY (brk)))
                STEP))
```

体外套一圈**只走一趟**的 while，于是

- 体里的 `continue` = 那一圈的 `(brk)` —— 跳到 step **前面**，step 照走
- 体里的 `break` 要跨过那一圈：`(brk 2)`（方言的 `(brk N)` 是往外数第 N 层，第四十刀）

**只在这一层的体里真有 `continue` 时才套**（`glslOwnContinue`：扫语句但不进嵌套的
`for`/`while` —— GLSL 的 `continue` 永远指最里那一层）。不这么挑的话每个 `for` 都多一层
while：白付的代价，而且一串门的字节对账会无谓地动。

`while` 那一侧不用套：它没有 step，`continue` 直接是方言的 `(cont)`。

### 门：每一条都带逃生阀

`tests/glsl/lower.js` 的 T2 加了四条，都是能手算的数：

- `for + continue`：`k < 3` 时 continue，累加 3+4+5 = **12**，循环转 **6** 轮
- `for + break` 跨过那一圈：i=0 加 0、i=1 continue、i=2 加 2、i=3 break -> **2**，转 4 轮
- `while + continue`：1+2+4+5+6 = **18**
- 嵌套（里外两层都有 continue）：i∈{0,2} × j∈{0,2} = **4** 次

每一条都塞了一个**逃生阀**（`if (g > 100) break;`）。理由：「continue 跳过 step」这个错
在 `for` 上的表现是**死循环**，没有逃生阀这道门会**挂住**而不是红 ——
挂住的门比红的门难查得多。有了它，坏实现给出的是一组明显不同的数
（第一条会是 `s=0, i=101`），而不是一次超时。

`tests/glsl/run.js` 8/8 组绿，`oracle` 与真 GL 的最大差仍是 0/1。
`NYI` 那张表里 `continue` 那一条删了 —— 它现在该绿，留着就是在钉一个已经不成立的事实。

## 落地：第一刀第十八片 —— `m[0]` 取列（顺带补了一格 `glslCompTy`）

- `v[K]` 取一格：在 `check.js` 里直接回一个 `swizzle`（`idx: [K]`），

- 下标**必须是整数字面量**。动态下标要方言里有真数组才做得对，这一刀没有，

（「这一刀不收 `m[0]`」），于是**整条用例根本没跑**。矩阵的分量一律是 float，

## 落地：第一刀第十九片 —— `do while` 与 `switch`（穿落、中间的 default 都对）

方言里这两条**都没有**，所以是「落成什么」的问题，不是「转发一下」的问题。

`do while` 落成永真的 while + 体尾判条件：

```
(while (bool true) (do BODY <C 的中间量> (if (un "!" C) (do (brk)))))
```

条件摆在**体尾**，于是它可以带中间量 —— 比 `while` 那条宽松（那条得挤成一条表达式，
见 `condIn`）。体里有 `continue` 时照 `for` 的办法套一圈只走一趟的 while：
`continue` 要跳到**判条件之前**，不是跳过判条件。这一格错了 `k=2` 那条用例会死循环。

`switch` 落成「只走一趟的 while + 一个匹配标志位」：

```
(while (bool true) (do
  <选择子>
  (let none bool (un "!" <任一标签命中>))       ;; 只有带 default 时才要
  (let m bool (bool false))
  (if (bin "||" (var m) <本组标签命中>) (do (set m (bool true)) <本组的体>))
  …
  (brk)))
```

三件事一次落清：**穿落**靠 `m`（一组匹配上就置真，后面每组的条件都带 `(var m)`）；
**`break`** 就是那一圈的 `(brk)`；**`default` 摆在中间**也对 —— 它的条件是
「一个标签都没命中」，那一格在进任何组**之前**先算（`none`），不受 `m` 影响。

### 顺手把 break/continue 的落点改成「数层」

从前那一格是 `{ wrapped }` 一个布尔，只够表达「for 套了一圈」。`switch` 一进来就不够了：
`switch` 里的 `break` 归 switch，`continue` 归外面那层循环。所以改成记**方言循环的层**：

- `loop` 一层真循环、`wrap` 给 `continue` 套的那一圈、`switch` 给 `break` 套的那一圈
- `break` 往外找最近的 `loop`/`switch`，`continue` 往外找最近的 `loop`/`wrap`
- 数出来第几层就是 `(brk N)` / `(cont N)`；第 1 层不写号，**从前那些门降出来的方言一个字没动**

`glslOwnContinue` 也跟着补一格：**要进 `switch`**（里头的 continue 不是它的），
但仍然不进 `for`/`while`/`do while`。

## 落地：第一刀第二十片 —— 位运算、移位、`^^`、六种复合赋值

语法这一层几乎不要钱（多九个 token、四档优先级、二十条产生式），要紧的是两格**语义**：

**一、优先级照规范 5.1 那张表，不替人纠错。** 位运算三层（`|` < `^` < `&`）都比 `==` 低，
移位比加减低 —— 于是 `a & b == c` 是 `a & (b == c)`，写代码得加括号。这与 C 同一个坑，
但规范就这么定的，前端不该悄悄改一档优先级去「帮」人。

**二、`1 << 31` 在方言里是 2147483648，在 GL 上是 -2147483648。** GLSL 的 `int` 是
32 位二补数，方言的 `int` 是 64 位。这一格不能装看不见，落法是**截回 32 位**：

```
(bin ">>" (bin "<<" v (int 32)) (int 32))
```

`(x << 32) >> 32` 靠的是右移是**算术**右移。这不是猜的 —— 三条腿各跑了一遍：
JS 腿的 BigInt、C 腿的 `int64_t >>`、LLVM 腿的 `ashr`，`1 << 31` 都出 -2147483648。

`& | ^ >>` 不必截（在 int32 范围里闭）；`~x` 也不必（`~x = -x-1`，范围内进范围内），
所以方言里没有一元 `~` 这件事顺手也解决了：落成 `x ^ -1`。

**还没做的一格，写在明处**：`+ - *` 的 32 位溢出回绕**没有**做。它与 `uint` 的无符号语义
是同一格活（施工图 A5），要一起做，不然会出现「乘法回绕了、加法没回绕」这种半截语义。

`^^` 是 GLSL 有 C 没有的**逻辑**异或，落成 bool 上的 `!=` —— 顺带绕开了短路那摊事
（`&&`/`||` 在这一层仍然是明着骂的，见 `bin` 里那句 `glslNyi`）。

## 落地：第一刀第二十一片 —— 非方阵 `matCxR`

类型的形状从 `{k:'mat', n}` 改成 `{k:'mat', cols, rows}`。这不是「加一种类型」，
是**把一个本来就该有两格的东西从一格改成两格** —— 从前只有方阵，所以一个 `n` 够用，
而 `n` 到底是列数还是行数在方阵上分不出来。

摊平次序没动：**永远列优先**，第 c 列占 `c*rows .. c*rows+rows-1`。于是：

- `m[c]` 取出来的是一列，长度是**行数** —— `mat2x3[0]` 是 `vec3`，不是 `vec2`
- `matCxR * vecC` 出 `vecR`；`vecR * matCxR` 出 `vecC`
- `matAxB * matCxD` 要 A == D（左边的列数 = 右边的行数），出 `matCxB`
- `matCxR(x)` 只在 `col == row` 那几格填 x：`mat3x2(2.0)` 是 (0,0) 与 (1,1) 两格

语法那侧九个 `matCxR` 关键字，动作全落成 `(ty-mat C R)`；`mat2` 也摊成 `(ty-mat 2 2)`，
于是 `mat2x2` 与 `mat2` 是**同一个类型**，不是两个（这一条门里单查了一条）。

## 落地：第一刀第二十二片 —— 向量比较那一族（而且它**不用**等方言的掩码）

**这一片推翻了待办 18 的一半说法。** 那一条写着「向量比较要方言先长出掩码与 `select`，
六条腿一起动」。量一遍就知道不对：GLSL 这一层的向量**本来就是摊成分量的**
（一格一个方言标量，见「量：向量在五条腿上分别落成什么」），所以「逐格比出一串 bool」

## 落地：第一刀第二十四片 —— 逗号表达式与限定符

**逗号单独一层，不塞进 `expr`。** 塞进去当场是真歧义：实参表也用逗号，`f(a, b)` 就分不出
「两个实参」还是「一个逗号表达式」。规范本来就分了两层（`expression` 有逗号、
`assignment_expression` 没有，而实参用的是后者），照它写就没有歧义 ——
表建出来 296 个状态，一个冲突都没有。逗号只出现在这些地方：语句、条件、`return`、
`( )` 里、下标里。降级时左边**照样降**（`i++, j` 里的自增是要发生的），只是值丢掉。

限定符四样，都是「语法收下、语义明着说清」：

- `layout(location = N)`：号收下来只做一件事 —— **同一类里不许两个名字抢同一个号**。

  现在就该拦，不然它会一直藏着。`location` 之外的键（`binding`、`std140`…）明着骂，

- `precision highp float;`：收下**不改变任何计算** —— 这一层的 float 只有一种精度
  （方言的 real）。收它的理由是别让一整份着色器因为这一行解析失败。
- `invariant gl_Position;`：同上。它说的是「两次编译要出同样的值」，而我们本来就是

- `centroid` / `sample`：规范里这两个是**取样位置**而不是插值方式。我们只有一个取样点

## 落地：第一刀第二十五片 —— `out` / `inout` 形参

方言里**没有引用参数**，所以这一族只能从返回值那一头回来：带 out 形参的函数落成
「返回一个**专用结构体**」，字段是「返回值那几格 + 每个 `out`/`inout` 那几格」，按声明次序。
调用点拆开、写回去。

为什么是专用结构体而不是借现成的 `glsl_vN`：那几个的每一格都是 `real`
（`(struct glsl_v4 (c0 real) …)`），而 `out int` 这种要 `int` 那一格。一函数一个结构体，
字段类型逐格写清。

两侧的落法：

- 被调那头：`out` 形参**不是**方言参数，是一个从零起的局部量；`inout` 形参是方言参数，
  进来先抄一份成局部量。抄这一份不是多此一举 —— 它把语义钉成 GLSL 的
  **copy-in / copy-out** 而不是引用：写回只发生在返回那一刻。
- 掉出函数尾的那一路也要打包（`void` 函数最常见）。前面已经 `return` 过的话那一条是
  死代码 —— 无害，而**少了它就是「out 丢了」**。
- 调用点：只把 `in` 与 `inout` 那些格递进去，接住结构体，然后按声明次序把 out 那几格
  `set` 回实参的分量上。写回落在 `ref`（几个变量名）或 `swizzle`（挑出来的那几格）上。

检查那一侧多两条，都是「写回哪儿去」的问题：`out`/`inout` 的实参**必须同型**
（要写回去，隐式转换没法反着来）、必须是能写的左值（字面量、`uniform`、`const`、
内建输入、`v.xx` 这种重复格都拦）。

## 量：结构体的第一关不在降级，在**语法**（试过了，退回来了）

结构体（施工图 B13）本来以为难点在降级那一侧（「一个值的每一格类型各不相同」）。
先试了语法这一头：给 `type` 加一条 `(-> (ID) (ty-name $1))`，因为结构体名字是标识符
而不是关键字。**表建出来 297 个状态，一个冲突都没报** —— 看着像成了。

跑门：**12 组只剩 1 组绿**。红的是 `bench-simple.frag` 这些**本来好的**源码，
以及 `length 回 float`、`dot 回 float`、`没见过的函数` 那一串。原因不在表，在 GLR：

```
S(1.0)   ;; 构造：type "(" args ")"
f(1.0)   ;; 调用：ID   "(" args ")"
```

这两条在**语法上完全一样**。LR 表没有冲突，是因为 GLR 允许分叉 —— 它两条都试，
然后由别的机制挑一条，于是 `length(v)` 被挑成了「构造一个叫 length 的类型」。
一处歧义把整份语法的语义翻了。

**于是结论反过来**：结构体的第一关是「这个名字是不是类型」这件事本身 —— 那正是
C 的 typedef 难题，而这份语法的开头明写着「GLSL 在这个子集里没有那种真歧义，
所以一处 `prefer` 都没有」。要接结构体，得先决定这一格：

- 要么给语法加**一处** `prefer`（构造优先于调用，再由检查那侧兜住「这个名字不是类型」）
- 要么让词法器认类型名（像 C 的 lexer feedback），语法层不必知道
- 要么把结构体构造写成**另一种形状**（不与调用同形），但那就不是 GLSL 了

三条各自的代价没量过，所以这一片**只留量到的事实**，不做决定。退回来的代价是零
（语法与检查各改一行，门回到 12/12），而如果先按「表没冲突就是对的」写下去，
错法会藏在「哪个内建函数被当成了类型」这种地方 —— 那是最难查的一类。

**教训：LR 表没冲突 ≠ 语法没歧义。** GLR 的分叉会把冲突从建表时挪到跑的时候，
而挪过去之后它长得像「类型检查错了」。

## 决策六：性能是**验收条件**，不是「以后再说」——中间形式为它服务

这一节改的是前面十几片隐含的一个立场。第十三片写着「这张表的用处不是比大小」，
第十五片写着「分层加速现在不值得做」。**那两句在「先把语义做对」的阶段是对的，
作为长期立场是错的**：复刻 llvmpipe 的**理由**就是性能，性能不达标这件事本身没有意义。

### 尺子：llvmpipe 的数（对面），与我们现在的数

llvmpipe（mesa 的软件光栅化器，`benchmark.py` 口径，每帧含读回）：

- `1024²` Simple：**普通单核 150～300 fps** ≈ 160～315 MPix/s；**8 核 1000～1200 fps** ≈ 1050～1260 MPix/s
- `pretty_render`（800²）：单核 60～70 fps ≈ 38～45 MPix/s；8 核 300 fps ≈ 192 MPix/s

同一台机器（Apple M1）上的**硬件** GL 是上限参考：`1024²` Simple 946 fps（7936 MPix/s）、
Complex 217.6 fps（1825 MPix/s）、`pretty_render` 462 fps（296 MPix/s）。

我们现在（第十三/十四片量的，`bench-complex`、单核、标量）：

- JS 腿 **0.4～0.6 MPix/s**、C 腿 **0.7～1.5 MPix/s**

**差距是两个数量级**（对 llvmpipe 单核约 100～300 倍，对 8 核再乘 8）。这个量级不是
微优化能补的 —— 它是**形状**的差距。

### 那 100 倍在哪儿（照 llvmpipe 的实现逐条对）

1. **SoA SIMD**：llvmpipe 一条指令算 4/8 个片元（`lp_bld_*`），我们一次一个 —— 4～8 倍
2. **float32 vs float64**：它是 f32（一个 256 位寄存器 8 道），方言的 `real` 是 f64
   （4 道）—— 再 2 倍
3. **每像素的固定开销**：我们每个片元一次函数调用 + 一个 `(new glsl_v4)` + 一次覆盖判定 +
   一次 8 位量化；llvmpipe 是**每 quad 一个掩码**、结果留在寄存器里
4. **多核**：它 8 核并行，我们单线程 —— 8 倍
5. **JIT 出的是专用变体**：它按「这个着色器 + 这套状态」编一份，我们也编一份（C 腿走
   clang、LLVM 腿走 IR），所以这一格**不是**主要差距 —— 主要差距是喂给编译器的**形状**

1×2×4 就已经是 64～128 倍。也就是说：**中间形式不改，天花板就在几 MPix/s。**

### 于是：快路与备选路分开

- **快路**（要建）：GLSL -> **SoA 向量 IR**（8 道 f32）-> LLVM。要么方言长出
  `(vec f32 8)` 的全套算术 + 比较掩码 + `select`，要么 GLSL 前端**直接发 LLVM IR**
  （llvmpipe 就是后者）。这一格是**决策五那张管线表里的新一列**，不是现有列的优化。
- **备选路 / 尺子**（已经有）：现在这条「标量摊分量 -> 核心方言 -> 五条腿」保留，
  但**降级为参照实现**：差分门（`lower.js`/`render.js`/`oracle.js` 那一串）靠它，
  JS 腿与解释器腿只有它。它的价值从「主路」变成「**证明快路算得对**」——
  这正是「性能不够时，中间形式只能调整为备选路径」这句话的落法。
- **门要改**：`perf.js` 现在「不判快慢」。快路建起来之后它得有**下限**
  （先立在 llvmpipe 单核那一档的某个比例上，比如 `bench-simple` 1024² ≥ 50 MPix/s），
  低于下限就红。没有下限的性能表只是记录，不是验收。

### 第一格量完了：1024² 上我们是多少（2026-09-04，Apple M1，机器空着）

`node tests/glsl/perf.js 1024`：

- `trivial.frag`（**只有框架**：扫画布 + 覆盖判定 + 插值 + 8 位量化 + 调用）
  JS **6.85**、C **32.77**、LLVM **30.39** MPix/s；真 GL 616.62
- `bench-complex.frag`（30 个 SDF）
  JS **0.44**、C **0.70**、LLVM **0.71** MPix/s；真 GL 177.78

三条读法，第三条是新的、也是最要紧的：

1. **着色器占 98.6%**（C 腿：框架 32.77 对整份 0.70）。与第十五片在小画布上量到的一致，
   所以「要提速就得动着色器那一半」这句话在 1024² 上仍然成立。
2. **LLVM 腿与 C 腿一样快**（0.71 对 0.70）。LLVM 腿是唯一向量原生的腿，但 GLSL 这一层
   把向量摊成了分量 —— 于是那条腿的向量能力**一格都没用上**。这是「中间形式限制了上限」
   最直接的证据。
3. **框架自己就已经不够了**：即使着色器免费，C 腿的天花板是 **32.77 MPix/s**，而 llvmpipe
   单核 Simple 是 160～315 MPix/s —— **框架单独就差 5～10 倍**。第十五片那句「分层加速
   最多省 3～5%，现在不做」在**相对**意义上没错，但在**绝对**意义上误导了：
   3～5% 是相对整份时间，而框架的绝对吞吐决定了「着色器优化到极限之后能到哪儿」。

于是快路要动的是**两处**，不是一处：

- 着色器那一半：SoA（8 道 f32）+ 掩码 + `select`
- 框架那一半：每 quad 一个掩码、一次写回 8 或 16 个像素，而不是每像素一次调用 + 一个
  `(new glsl_v4)` + 一次量化

对 llvmpipe 单核的差距（complex 对 complex，按硬件 GL 上 Complex ≈ Simple/4 折算
llvmpipe complex ≈ 40～80 MPix/s）：我们 0.70，**差 60～110 倍**。

<!-- ADR-0019 决策六第一格-END -->

### 顺手量出的一格：**形状税**（每像素一次调用 + 一个 `(new glsl_v4)`）

`tests/glsl/shape_tax_a.sx` 与 `shape_tax_b.sx`：同样的算术、8388608 次，差别只在形状 ——
A 是「调一个回结构体的函数，再读四格」，B 是「内联，不调用不 new」。四次跑出来的校验和
**完全相同**（`2.11115e+11`），所以比的是同一件事。整进程 `time real`：

- **C 腿**：A `0.83s`、B `0.28s` -> 形状税 `0.55s / 8.39M` ≈ **66 ns/像素**
- **LLVM 腿**：A `0.41s`、B `0.28s` -> 形状税 `0.13s / 8.39M` ≈ **15 ns/像素**

（A 比 B 多一个函数，所以那 0.55/0.13 里含一点编译差；当成**上界**读。）

两条结论：

1. 形状税与**整个框架预算同一个量级**：框架 32.77 MPix/s = 30.5 ns/像素，而这一格
   单独就 66 ns（C 腿）。也就是说「每片元一次调用 + 一个新结构体」不是细节，是**一等开销**。
2. **同一份方言，LLVM 腿把这个形状吃得比 C 腿好 4 倍**（15 对 66 ns）。加上第一格量到的
   「LLVM 腿是唯一向量原生的腿」——快路选 LLVM 不是偏好，是这两个数指出来的。

### 第三格量完了：天花板是 175 MPix/s，而 **f32 只值 6%**

`tests/glsl/soa_ceiling.c`（**不经过我们的编译器**，clang -O2 直接量；30 个圆的 SDF 取 min
再一次 smoothstep，与 `bench-complex` 同一类；1024²、三次取最小、校验和三个变体一致）：

- **f64 标量 31.83 MPix/s**
- **f32 标量 33.69 MPix/s**（比 f64 只快 **6%**）
- **f32 × 8 道 175.32 MPix/s**（比 f64 标量快 **5.5 倍**）

三条结论，前两条都推翻了我原先的猜法：

1. **f32 不是杠杆，宽度才是。** 决策六里我把「f32 vs f64」列成 2 倍的一格 —— 量出来只有
   6%。M1 上 f64 标量与 f32 标量几乎同速（标量单元一样宽），2 倍那个说法只在
   「一个寄存器能装几道」时才成立，而那正是**向量化**这一格，不是精度这一格。
   于是「量 f32 进方言的代价」这件事**降级**：先做 8 道，精度以后再说。
2. **我们自己的开销是 45 倍。** 同一类算术：我们 C 腿 `0.70` MPix/s，纯 C 标量 f64
   `31.83` —— 差 **45 倍**，而这 45 倍**与 SIMD 无关**，全在「标量摊分量 + 每片元一次
   调用 + 一个 `(new glsl_v4)` + 框架」里。也就是说：**在动 SIMD 之前，现在这条路本身
   就先丢了 45 倍。**
3. **目标是够得着的。** 8 道 f32 的天花板 175 MPix/s，落在 llvmpipe 单核 Simple 那一档
   （160～315）里 —— 而我们量的还是 complex。所以「单核到 llvmpipe 一档」不是空想，
   前提是形状换成 SoA + 不走每片元一次调用。

于是快路的形状定下来了（决策六里那两条选项，选后者）：**GLSL 前端直接发 LLVM IR，
8 道 f32 SoA、每 quad 一个掩码**；标量方言那条退成参照实现。理由不是偏好，是这三个数：
45 倍在我们自己身上、5.5 倍在宽度上、6% 在精度上。

### 开工单第 1 步做完了：**IR 走我们自己那条编译线，178 MPix/s**

LLVM 腿的形状是 `MIR -> .ll -> clang -O2`（`cli.js:2016` 起，`OMNI_CLANG` 可覆盖）——
也就是说手写/发射出来的 `.ll` 与它走**同一条后半段**。验证办法不必手写几百行 IR：

```
clang -O2 -emit-llvm -S tests/glsl/soa_ceiling.c -o /tmp/soa.ll   # C -> IR
clang -O2 /tmp/soa.ll -lm -o /tmp/soa_ll && /tmp/soa_ll            # IR -> 可执行
```

出来 **178.30 MPix/s**（直接从 C 编是 175.32，差在噪声内）。**第 1 步的结论：目标穿得过
我们自己的编译线**，瓶颈不在运行时也不在编译选项，只在「发射器发出什么形状的 IR」。

顺手把那份 IR 里的形状摘出来，第 2 步照它发（clang 的输出就是标准答案）：

- 每个值 `<8 x float>`；标量常量是 `splat (float …)` —— **splat 之后一律同型**这条
  （开工单里定的）被 clang 自己的输出佐证了
- `min`/`max` -> `llvm.minnum.v8f32` / `llvm.maxnum.v8f32`；`sqrt` -> `llvm.sqrt.v8f32`
- 循环里的累加是 `phi <8 x float>`，不是内存
- 整数 -> 浮点：`uitofp <8 x i32> to <8 x float>`

**还量到一处要避开的坑**：那份 IR 里有一串 8 次 `extractelement`（`soa.ll:294-308`）,
来源是我 C 版里手写的 `for (l = 0; l < 8; l++) x[l] = …`。取样点**不该逐道写** ——
该用 `x0 + <0,1,2,…,7>` 一次向量加法得到。框架那一半（开工单第 3 步）就是这一格：
每 quad 的坐标、掩码、写回都要整条向量地做，逐道循环会把向量化的收益吐回去。

## 落地：快路第 2 步 —— 发射器骨架跑通，1024² 上 87.89 MPix/s（对账绿）

`src/core/frontend-glsl/emit_llvm.js`（GLSL checked AST -> 8 道 f32 的 LLVM IR）+
`tests/glsl/fast_driver.c`（驱动）+ `tests/glsl/fast.js`（对账门）。`bench-simple`：

- **对账绿**：8 个取样点 × 4 通道，与参照实现（标量 -> 方言 -> JS 腿）相对差 ≤ `1e-5`
  （容差是 f32 的有效位数留一位余量 —— 两边**本来就不同精度**，逐字节相同是错的期望）
- **1024² 上 87.89 MPix/s**（11.93 ms）。参照实现那条路的**框架天花板**是 32.77 —— 
  快路已经越过它 2.7 倍，而且这 87.89 里还带着驱动那个**逐道**量化循环（第 3 步要整批做）

三处落法值得记：

1. **ABI 全走指针**：`void glsl_frag8(ptr in, ptr out)`，`in = [x, y, uniform 每一格…]`。
   第一版把 `<8 x float>` 直接当参数传，读出来**整体错位一格** —— 32 字节向量在
   AArch64 上不是原生寄存器类型（NEON 是 16 字节），「IR 里的 `<8 x float>` 参数」与
   「C 里的 `ext_vector_type(8)` 参数」在传参上不必一致。指针没这个问题：ABI 面只剩地址。
2. **SSA 里的赋值要改「声明它的那一层」**。第一版写进当前作用域，于是 `fragColor = …`
   只改了 `main` 体那一层的副本，出了 `{}` 就丢 —— 快路输出全 0。
3. **错的实现看起来更快**：全 0 那一版量出 277 MPix/s，因为 clang 把大半计算当死代码删了。
   这正是「对账门先立、下限门后立」的理由 —— 先立下限门的话，这一版会**过**。

## 决策七：**编译耗时也是验收指标** —— clang AOT 是支路，等效路径必须是进程内 JIT

快路第 2～4 步走的是 `GLSL -> 8 道 f32 IR -> clang -O2 -> 可执行`。它把**吞吐**那一格
解掉了（132.61 MPix/s），但它**不是** llvmpipe 的等效路径，因为 llvmpipe 从来不起进程去编译：
它在自己进程里用 LLVM 的 ORC/MCJIT，按「这个着色器 + 这套状态」编一份变体。
差别不在代码质量，在**编译一次要多久**。

### 量：clang 的固定开销（同机 Apple M1）

`clang -O2 -c` 一份 IR（IR 是 `bench-simple` 的片元函数复制 N 份）：

- 空 IR（一个 `ret void`）：`0.40s`（第一次，含冷启动）
- 1 个函数（2 KB）：`0.10s`
- 10 个函数（17 KB）：`0.06s`
- 100 个函数（173 KB）：`0.25s`

读法：**固定开销 60～100 ms**（进程启动 + dyld + 完整 pipeline + 文件 IO），规模项约
2 ms/函数。也就是说「编一个着色器变体」的地板价是 **60～100 ms**。

llvmpipe 那一侧：ORC 在进程内编译一个片元变体，典型 **1～20 ms**（无进程、无文件、
只跑必要的 pass）。所以 **clang AOT 比它慢 5～50 倍**，而且这 60～100 ms 是**每个变体
都要付**的地板价。

### 于是这条差距在什么场景下要命

`/Users/wurui/Documents/GitHub/GraphEq/html/grapheq.glsl` 量了一下：**772 行**、
22 个 `for`、3 个 `struct`、8 个 `#define`、1 个 `while`、5 个 `uniform`。
一个这样的着色器就相当于上面「100 个函数」那一档的规模 —— clang 那条路要 **0.2～0.3 s**。
交互式场景里（改一个开关就换变体、或者 GraphEq 那种「用户输入公式 -> 现编一个着色器」）
这不是「慢一点」，是**卡一下**。

顺带这份着色器还量出前端的缺口：`struct` 与预处理（`#define`）都是施工图 B13/A11 那两格，
现在接不了。也就是说「真实规模的着色器」同时在**编译速度**与**语法覆盖**上都不在射程内。

### 量：真实着色器（`grapheq.glsl`）到底缺哪几格 —— 只有三格

把那 772 行里用到的内建与构造逐个数出来，与我们现在的支持面对表：

**已经有了**（第 22、23 片补的那批正好覆盖）：`max` 57 次、`min` 35、`floor` 19、`abs` 13、
`atan` 12（**含两参形** —— 第 23 片才修好的那一格）、`exp` 8、`sin`/`log` 各 7、`cosh` 6、
`cos` 6、`tan`/`sqrt`/`ceil` 各 5、`pow`/`mod` 各 3、`tanh`/`sinh` 各 2、`sign`/`not` 各 1。

**缺的只有三格**：

- **`isnan` 7 次、`isinf` 5 次**（施工图 A7 里我留的那一格：「要先有造 NaN/Inf 的办法」）。
  落法其实很短：`isnan(x)` 就是 `x != x`（一条 `fcmp une`）、`isinf(x)` 是
  `|x| > 最大有限值`。**先做这一格**：它最便宜，而且没有它这份着色器一行都跑不了。
- **`struct` 3 处**（B13）：卡在「这个名字是不是类型」，见前面那一节。
- **`#define` 8 处**（A11 预处理）。都是对象宏还是有函数宏，要读一遍才知道。

**没有**用到的（省了一大片）：采样器与 `texture`、`discard`、`switch`、`do`、`uint`/`uvec`、
非方阵、`inverse`/`transpose`/`determinant`、`dFdx`/`fwidth`、`modf`/`frexp`/`ldexp`。

也就是说「快路吃真实着色器」这件事的工作量是**三格，不是一片荒野** —— 而且其中最要紧的
`isnan`/`isinf` 是两条 `fcmp`。这条量法（拿真实源码去数，而不是照规范列清单）值得复用：
它把「完整支持 GLSL 330」这个无边界的目标，切成了「这一份要什么」。

<!-- ADR-0019 grapheq 缺口-END -->


1. **clang AOT（已有，快路 v1）**：只当**尺子与对账**用 —— 天花板 178、对账门靠它。
   它永远不该是运行时的编译路径。
2. **进程内 JIT（快路 v2）—— 这一格才是「复刻 llvmpipe」**：llvmpipe 本身就是
   「LLVM 的 JIT + SoA 向量 IR」，所以复刻它**就该用同一个机制**。机制上我们已经有了：
   `cli.js` 的 `buildJitHost()` + ORC 宿主（`src/jit/omni_jit.c`）吃任意 `.ll`
   （`tests/jit` 那条轴钉的就是它）。把 8 道 f32 的 IR 送进去即可。
3. **自研后端 + NEON（快路 v3）**：`GLSL -> 我们自己的 IR -> arm64 NEON -> 内存机器码`，
   不依赖 LLVM。**优先级低**：它是「我们自己也能写」那条线，而**复刻 llvmpipe 不等于
   自己写一个后端** —— 后者永远有时间做，前者是这一刀的目标。缺口已经量过（native
   两条腿完全不收向量），但它不该挡在 v2 前面。

### 开工单（下一片按这个顺序，先便宜的后贵的）

1. **量 v2 的编译耗时**：把驱动编成 IR、与 `frag.ll` 拼成一份带 `main` 的 `.ll`，
   分别走 `clang -O2` 与 ORC 宿主，量「编译 + 执行」与「只执行」的差 —— 得到 ORC 的
   编译耗时。**纯量测，不改实现。**
2. **把编译耗时立成门**：`tests/glsl/fast.js` 加一条「编一个变体 ≤ X ms」。X 先立在
   llvmpipe 那一档的上界（20 ms）—— clang 那条路会**红**，红得对：它本来就不是运行时路径。
3. **v2 接起来**：GLSL -> 8 道 f32 IR -> ORC 宿主，`bench-simple` 先跑通，
   与 v1 逐取样点对账（同一份 IR 换装载方式，答案不许变 —— 与 `tests/jit` 同一条纪律）。
4. **v2 吃真实着色器**：`grapheq.glsl` 那 772 行要的 `struct`（B13）与预处理（A11）
   补上；这两格现在是**语法覆盖**的缺口，不是性能的。

**v3（自研后端 + NEON）不在这张单子里** —— 见上一节第 3 条：那是「我们自己也能写」，
永远有时间；复刻 llvmpipe 不等于自己写一个后端。

<!-- ADR-0019 决策七-END -->

## 量：v2（进程内 ORC）的编译耗时 —— **9～10 ms**，与 llvmpipe 同一档

开工单第 1 步。**纯量测，一行实现都没改。**

量法：ORC 宿主（`.omni-cache/jit/*/omni-jit`，吃任意 `.ll` 并 lookup + 调用它的 `main`）
分别装载三份 IR，每份连跑 20 次取总墙钟的最小值（`/usr/bin/time -p`），相减摊掉进程启动：

- **空模块**（只有 `define i32 @main { ret i32 0 }`）：20 次 0.26 s -> **13 ms/次**
  = 进程启动 + `LLVMOrcCreateLLJIT` + 进程符号生成器。**这是基线，不是编译成本。**
- **我们的 frag IR + 手写极小驱动**（2.7 KB，其中 `emit_llvm.js` 出的 1.9 KB）：
  20 次 0.39 s -> 19.5 ms/次 -> 减基线 = **编译 ≈ 6.5 ms**
- **我们的 frag IR + clang -O2 出的取样驱动**（11.6 KB，其中驱动 9.7 KB）：
  20 次 0.45 s -> 22.5 ms/次 -> 减基线 = **编译 ≈ 9.5 ms**；同一次运行里被 JIT 的
  `main` 自报 `exec_ms 0.041`（64² = 4096 像素 -> 约 100 MPix/s，与快路 132 那一档吻合），
  也就是**执行在编译面前可以忽略**，这个差就是编译。

对账：`clang -O2 -c` 的固定开销是 **60～100 ms**（前面量过：空 IR 0.40 s 冷 / 1 函数
0.10 s / 10 函数 0.06 s / 100 函数 173 KB 0.25 s）。llvmpipe 在进程内编一个片元变体是
**1～20 ms**。所以：

> **ORC 9～10 ms 落在 llvmpipe 那一档里；clang AOT 那条路慢一个数量级。**

决策七里那个断言（「clang 的编译开销与 llvmpipe 的 JIT 不是一回事」）到这里是量实的，
不再是推断。v2 路线成立。

### 两处只有真跑起来才会发现的坑（都不是性能问题，是「能不能装载」）

1. **第一次量出来的 10 ms 是假的** —— IR 根本没解析成功。`clang -emit-llvm -S` 出的驱动
   里有 `declare void @glsl_frag8(...)`，与后面拼进来的 `define` 在**文本 IR 解析器**里
   算 `invalid redefinition`（不是链接期合并，是同一份 `.ll` 里的重复定义）。而我当时用
   `grep -E "exec_ms|^real"` 看输出，`exec_ms` 那行压根没印出来我却没追 —— **被 JIT 的
   `main` 到底跑了没有，必须由它自己印一行来证明**，光看进程时间会把「立刻报错退出」
   读成「快」。这与「快路全 0 那版量出 277 MPix/s」是同一个错的第二次现身。
2. **clang 出的 IR 带着 ORC 落不了地的函数属性**：`"probe-stack"="__chkstk_darwin"`
   （macOS 的栈探测）会让 ORC 的目标机直接 `LLVM ERROR: Unsupported stack probing method`
   而 abort。这对 v2 是个正面结论：**我们自己发射的 IR 一个函数属性都不带**，所以不踩；
   但只要以后往 v2 里塞任何 clang 产物（驱动、运行时），就得先把属性剥掉。

### 一个反直觉的数：编译成本跟 IR 字节数不成比例

我们自己那 1.9 KB 要 6.5 ms，clang 出的 9.7 KB 只再加 3 ms。成本跟的是**要生成的机器码
体量**，而我们的 frag 是 8 道 f32 全展开的密集算术 —— 一行 GLSL 摊成八份向量指令。
这条对第 2 步（立门）很关键：门的阈值该按「着色器规模」立，不该按「IR 文件大小」立。

## 落地：快路第 3、4 步 —— 量化整批做（+40%），下限门立起来了：**132.61 MPix/s**

第 3 步只改了驱动里一处：8 位量化从「每格 8 次标量循环」改成整条向量
（`__builtin_elementwise_max/min/trunc` + 一行一个向量累加器，行末再水平求和）。

- **87.89 -> 122.91 MPix/s（+40%）**，之后重复跑稳定在 **132.61**

这 40% 就是「快路第一步」那条教训的直接价格：**向量算完之后逐道去处理，等于把向量化的
收益吐回去**。着色器那一半一行没动。

第 4 步把下限门立起来（`OMNI_GLSL_FLOOR` 可覆盖，默认 100）：

- 下限 **100** 的来历：同一台机、`clang -O2` 手写 8 道 f32 的天花板是 178
  （`soa_ceiling.c`），留 40% 余量。llvmpipe 单核 Simple 是 160～315，所以这一档只是
  「进了同一个量级」，不是终点。
- 门的说法写在失败分支里：**低于下限别调下限，去查形状**。
- 顺带补上「没有 clang 就跳过整门」——快路本来就是 LLVM 那条路，但那不该让别的门连带红。

### 现在的账（同一台 M1，1024²，单核）

- 参照实现（标量 -> 方言）：`bench-complex` **0.70**、框架天花板 **32.77**
- **快路**：`bench-simple` **132.61**（对账绿，相对差 ≤ 1e-5）
- 手写 8 道 f32 的天花板：**178**（30 个 SDF 的核心，比 bench-simple 重）
- llvmpipe 单核 Simple：**160～315**；M1 硬件 GL Simple：**7936**

也就是说：**快路已经把「中间形式限制上限」这件事解掉了** —— 从 0.70 到 132.61 是
190 倍，而这 190 倍里没有一分是「算得更少」，全是形状（8 道 f32 + 不经过每片元一次
调用与一个结构体 + 整批量化）。

### 快路的开工单（下一片照这个做，不要重新设计）

**目标一句话**：`bench-simple` 在 1024² 单核上 **≥ 100 MPix/s**（天花板量到 175，留 40% 余量），
并且与标量路**逐像素对账**（容差照 `oracle.js` 那条：8 位通道差 ≤ 1）。

分四步，每步都能单独跑绿：

1. **先验证目标能穿过我们自己的工具链**（不写发射器）：手写一份 8 道 f32 的
   `bench-simple` 片元 `.ll`，用与 LLVM 腿同一条路编译执行，量 MPix/s。
   要是这一步就到不了 100，问题在运行时/编译选项，不在发射器 —— 先解决那个。
2. **发射器骨架** `src/core/frontend-glsl/emit_llvm.js`：GLSL 的 checked AST -> LLVM IR。
   只收 `bench-simple` 用到的那一档（`float`/`vecN`、算术、`length`/`min`/`max`/
   `smoothstep`/`sin`/`cos`、`for`、`uniform`、一个 `out vec4`）。表示：
   - 每个 GLSL 值 = 一个 `<8 x float>`（标量也是 —— splat 之后一律同型，省掉两套路径）
   - 分支：**没有分支**。`if`/`?:` 落成掩码 + `select`；`for` 只收常量次数（先够用）
   - 入口签名：`(x0: <8 x float>, y0: <8 x float>, uniforms…) -> {<8 x float> ×4}`
3. **框架那一半**：一次算 8 个像素、每 quad 一个掩码、量化与写回也按 8 个一批。
   这一步单独量 `trivial`，看框架从 32.77 MPix/s 抬到多少。
4. **门**：`tests/glsl/perf.js` 加下限（`bench-simple` 1024² ≥ 100 MPix/s，低于就红），
   外加一支 `tests/glsl/fast.js` 做「快路 vs 标量路逐像素对账」。**对账门先立，
   下限门后立** —— 顺序反了就会为了数字牺牲正确性。

**不在这一片里的**（写下来免得顺手做）：texture、discard、动态下标、结构体、
多渲染目标、f32 进方言（第三格量到只值 6%）、多核。
