### 这两个着色器定下了「最小可用的 GLSL 子集」

这是读那份 benchmark 最要紧的收获 —— 要走通它，需要的 GLSL **只有这些**：

所以第一刀的门可以就是「跑通 `FRAG_SIMPLE`」，第二刀「跑通 `FRAG_COMPLEX`」——

## 量：读 llvmpipe —— 借什么、不借什么

读过的：`lp_limits.h`（全）、`lp_bld_interp.h`（全）、`lp_bld_interp.c` 头 200 行、
`lp_rast_tri_tmp.h` 头 120 行、`lp_state_fs.c` 的文件头。**没读**的：`lp_bld_nir.c`
那一整摊（NIR → LLVM IR）、纹理采样、`lp_linear*`、`lp_scene`/`lp_setup` 的分箱。
下面每条都带出处，好回查。

### 量到的形状

**一、瓦片是 64×64，光栅化是分层的。** `lp_limits.h:39` `TILE_ORDER 6` → `TILE_SIZE 64`。
`lp_rast_tri_tmp.h` 里两级：`do_block_16` 拿一个 **16×16** 块，按每条边的边函数
（`plane[j].dcdx`/`dcdy`/`eo`）一次算出 16 个 **4×4** 子块的「全在内 / 全在外 / 骑边」
（`build_masks_32` 出 `outmask` 与 `partmask`，`outmask == 0xffff` 直接 return）；
骑边的那些交给 `do_block_4`，它出一个 **16 位掩码**（4×4 个像素各一位），
再调 `lp_rast_shade_quads_mask_sample`。

所以 llvmpipe 的「快」有一半在这儿：**大多数像素根本不逐个测**，整块接受或整块丢掉。

**二、片元着色器的执行单位是 2×2 的 quad，四个像素按 SoA 摆。**
`lp_bld_interp.c:53-87` 那段注释说得很死：一个 block 是 2×2 个 quad、一个 quad 是 2×2 个
像素；四个像素的绿通道躺在**同一个向量寄存器**里 —— `{g0,g1,g2,g3}`。
`quad_offset_x/y[16]`（`:117`）就是那 16 个像素在块内的坐标。

**三、插值是 `a = a0 + x*dadx + y*dady`，一条 fmuladd 两次。**
`interp_attrib_linear` 就这三行。系数（`a0`/`dadx`/`dady`）是 setup 那一步按三角形算好的，
插值这一步只做仿射求值。`lp_bld_interp.h` 头上那句更要紧：**只有第一个 quad 做乘法，
后面的 quad 全靠加法**（沿 x 走一步就加 `dadx*2`）。

`enum lp_interp` 只有六种：`CONSTANT`、`COLOR`、`LINEAR`、`PERSPECTIVE`、`POSITION`、
`FACING`。`COLOR` 按 flatshade 状态化成 `CONSTANT` 或 `PERSPECTIVE` 之一 —— 也就是说
**「插值方式」是编 shader 变体时就定死的常量，不是运行期分支**。

**四、透视除法「每 quad 一次」这条优化 mesa 自己关着。**
`lp_bld_interp.c:103-114`：本来想在 quad 左上角算一次 `1/w`、其余三个像素用线性近似，
注释写着 “Ironically, this actually makes things slower —— 除法单元闲着，乘法单元反而饱和”，
于是 `PERSPECTIVE_DIVIDE_PER_QUAD 0`。**这是一条现成的教训**：别照着「省除法」的直觉做。

**五、整条片元管线是 JIT 出来的一个 C 可直接调的函数。**
`lp_state_fs.c` 文件头列的顺序：early depth test → 片元着色器 → alpha test →
depth/stencil test → blending。它还点明一处复杂性的来源：**各阶段用的精度与类型不同**
（着色器用 float，深度与混色用最贴近缓冲格式的类型），而 SIMD 寄存器宽度固定，
于是「类型不同 ⇒ 一次算的像素数不同 ⇒ 大类型那几段要多生成几份实例」。

**六、变体是有上限、按状态做键的缓存。** `lp_limits.h:72` `LP_MAX_VARIANTS_PER_FS 16`、
`:84` `LP_MAX_SETUP_VARIANTS 64`，注释说 setup 变体由「片元着色器的输入签名 + 一小撮
光栅化状态（如 flatshade）」决定，很多着色器共用一个。

### 借

- **分层光栅化 + 边函数掩码**（`do_block_16`/`do_block_4` 那两级）。这是与语言无关的算法，
  也是性能的大头。第一刀就借。
- **2×2 quad 当执行单位**。第一刀哪怕是一次算一个片元，也要**按 quad 组织循环** ——
  因为 `dFdx`/`dFdy` 与纹理 LOD 天生要 quad，而且后面 SoA 化就是把这个循环换个内核。
- **`a0`/`dadx`/`dady` 的仿射插值形式**，包括「一个 quad 一次乘、后面全加」这条。
- **变体按状态做键**。我们这边没有 LLVM JIT，但「一份 GLSL + 一撮状态 → 一份编好的代码」
  这个缓存结构照借（我们的 `incr` 那一路已经有缓存的骨架）。
- **管线阶段的次序与 early-z 的位置**。这是正确性的一部分，不是优化。

### 不借

- **LLVM 与 gallivm 那一整层**。整个工程的前提是不用 LLVM —— 我们有自己的 x64/arm64 后端，
  这条线正好是它们的第一个「非 C 前端」用户。
- **NIR / TGSI 两套中间表示**。mesa 有历史包袱（`tgsi_to_nir`、`nir_to_tgsi_info`），
  我们直接 GLSL → 自己的 IR。
- **AoS 与 SoA 两条并行的路**（`lp_bld_blend_aos.c`、`lp_linear*` 那一族快路）。
  那是二十年攒下来的特例，第一刀一条路走通再说。
- **多重采样**（`MULTISAMPLE` 那些 `#ifdef`）、**stencil**、**双源混色**、
  **纹理采样**、**几何/计算着色器**。两档尺子（`benchmark.py`、`pretty_render.py`）
  一个都用不到。
- **透视除法每 quad 一次**。mesa 量过是负优化，直接跳过。

## 决策一：GLSL 先接到 MIR，一次一个片元；但循环按 quad 组织

这是「还没定的」第 2 条的答案。三个候选：

- (a) GLSL → **现有的标量 MIR**，一次算一个片元
- (b) 先给 MIR 长出**向量那一格**（SoA、typed vector），后端学 NEON/SSE，再接 GLSL
- (c) 另起一个着色器专用的小 IR，向量化当成它到 MIR 的一个 pass

**选 (a)，理由是「先有能量的东西」：**

- (b) 是这条线上最大的一笔改动（MIR 的类型系统、两个后端的向量指令、寄存器分配），
  而它换来的是**倍数**上的性能 —— 可我们现在连一个能跑出像素的实现都没有，
  没有基线的倍数是空话。llvmpipe 那边 SIMD 是 2010 年就有的事，但它的**结构**
  （quad 循环 + 每通道一个向量）本身在标量下也成立：把 `{g0,g1,g2,g3}` 换成
  循环四次，逻辑一字不改。
- (c) 多一层 IR 就多一层要维护的不变量，而 GLSL 的语义（标量/向量、swizzle、内建）
  离 MIR 并不远。真需要一层，那也该是**在 MIR 之上加向量单元**，不是旁边另立一套。
- (a) 立刻能拿到两条腿（JS 与 native）跑同一份 GLSL，`fbo.read()` 那口径下的
  三个数与像素图都能量 —— 也就是**尺子立刻能用**。

**为了不把 (b) 堵死，第一刀必须守住两条形状：**

1. 片元着色器编成一个**「吃一个片元、吐一个颜色」的函数**，它的输入由一个显式的
   「插值」步骤提供（`a0 + x*dadx + y*dady`），不允许在着色器体里直接摸像素坐标以外的东西。
   这样 SoA 化就是「把这个函数的参数与返回值从标量换成 4 宽向量」，而不是重写。
2. 遍历顺序**按 quad**（2×2），不按扫描线。理由在上面第二条量里。

什么时候动 (b)：等第一档尺子（`FRAG_SIMPLE`/`FRAG_COMPLEX` 五个尺寸）在两条腿上都有数
之后，拿那组数与 llvmpipe 的比，**用差距决定值不值得**。这一条写在这儿，是为了将来不必
靠回忆来判断。

## 决策二：像素比对的口径，量法先定下来

第 3 条还不能定（还没有实现能出图），但**量法**现在就能定，免得将来事后挑一个宽松的：

## 落地：第一刀第一片 —— 语法表与五份尺子源码

只做**语法**，一行降级都没有。`src/core/frontend-glsl/glsl.grammar`，走的是与 jancy 那条线
同一条路（`.grammar` 是数据 + GLR 引擎，类型定向的那一半留给将来的 `lower.js`）。

三件事值得写下来：

**一、这张表是干净的 LR —— 0 处冲突。** 206 个状态、`(prefer …)` 一处都没有。
GLSL 在这个子集里没有 C 那种「要先知道名字是不是类型」的真歧义，因为**类型全是关键字**。
jnc 那份有 3 处真歧义靠 `prefer` 压，这份一处都不需要 —— 有歧义就是我写错了。

**二、`(prec X)` 必须紧跟在 RHS 之后**（`glr/grammar.js:133` 那个 while 只在动作之前扫）。
我第一版写成 `(-> ("-" expr) (neg $2) (prec UNARY))`，`(prec UNARY)` 落在动作后面等于没写：
表里多出 **23 处冲突**，而且 `-a * b` 分成 `(neg (mul a b))` —— 一元负号变得比乘法还松。
`a + b * c` 那两条断言是绿的，因为它们不涉及一元。挪到动作前面之后冲突归零。
**这类错不会让门直接红，只会让图变成另一张画。**

**三、`discard` 收进语法，但不实现。** 不收的话 `discard;` 会被当成「一个叫 `discard` 的
变量」悄悄分析成 `(expr-stmt (name discard))`（量过）。语法里有一条 `(discard)` 之后，
「这一刀不收」这句话由降级那一侧明着说 —— 靠语法碰巧不认，等于把错误藏进一个合法形状里。

`layout` 反过来：关键字表里每个词都得是某条规则用到的终结符（不然构表就骂），
而 `layout(location = N)` 这一刀不收，于是它**不在**关键字表里。

## 落地：第一刀第二片 —— 类型检查与名字解析

`src/core/frontend-glsl/check.js`。出来的是一棵**带类型的树**，不是在原树上挂属性 ——
降级那一侧要的是「每个节点的类型已经定了」，让它再算一遍等于把同一套规则写两遍，
而两遍必然会分叉。

四处决定，都写在文件里：

**一、`stage` 由调用方给，不猜。** 猜是能猜的（看有没有 `gl_Position`），但猜错的那一次会把
「顶点里写了 `gl_FragCoord`」变成「哦这是一份片元着色器」，错误就此消失。内建变量因此是
**分档的两张表**：`gl_VertexID`/`gl_Position` 只在顶点档，`gl_FragCoord`/`gl_FragDepth` 只在
片元档。用错了报的不是「没见过这个名字」，而是「它是片元着色器的内建变量，而这是一份顶点
着色器」——差一句话，查起来差很多。

**二、隐式转换只有一条：`int` -> `float`**（规范 4.1.10，`ivecN` -> `vecN` 也在里头）。
别的一律骂。悄悄转的话 `float f = someVec3;` 会变成「取第一格」——那是能跑的错。

**三、内建函数按**形状**分类，不是一条条重载**：`gen1`（`sin`/`abs`…）、`gen2`（第二个参数
可以是标量，`min(vec3, float)` 合法）、`gen3`（`clamp`/`mix`/`smoothstep`）、`len`、`dot2`、
`cross`。「第二个可以是标量」不是我编的，是规范 8.3 里那几组重载；而 `sin(x, y)` 那种不存在。

**四、`discard` 在这儿骂。** 语法里那条 `(discard)` 就是为了让这句话有地方说 —— 语法不收的话
`discard;` 会被当成「一个叫 `discard` 的变量」悄悄收下。

### 一处真错误，门当场抓到

比较运算（`< > <= >=`）第一版写的是「回两边提升出来的那个类型」，于是 `i < 20` 的类型是 `int`。
结果 `for (int i = 0; i < 20; i++)` 被条件那道检查骂成 **「整数不能当条件」** —— 报错离题，
而真正的错在两百行之外。比较**回 bool**，与两边是什么无关。这一格现在门里单列一条。

- 五份尺子源码都过，而且**接口摸出来的形状对**：`pretty.frag` 是 2 个 uniform
  （`u_res:vec2`、`u_time:float`）、1 个 varying（`v_uv:vec2:smooth`）、1 个 const、
  5 个函数（`sdCircle:float/2`、`sdHex:float/2`、`rot:mat2/1`、`hsv2rgb:vec3/1`、`main:void/0`）。

- 23 条**具体类型**：swizzle 的三种字母表、向量与标量两个方向、`int` 提升、比较回 bool、

- 20 条**该拒的**，而且比的是**报错里的关键词**，不是「抛了就算过」：`vec2` 没有 `.z`、
  `xyzw` 与 `rgba` 混用、构造少一格与多一格、向量宽度不一样、`%` 不对 float、

## 量：降级要接的那一层长什么样（第三片开工前）

决策一说的是「接 MIR」。动手前先量了**核心方言**（`sexpr/lower.js`，jancy 与 asy 都降到它，
五条腿从它出发），因为如果 GLSL 降到方言而不是直接降到 MIR，JS 与 C 两条腿是**白得的**。
量出来三条，其中一条推翻了我原来的打算。

**一、方言已经有向量那一格。** `(vec real 4)`、`(splat T E)`、`(vlit T E…)`、`(lane E N)`、
`(hsum E)`（`tests/sexpr/cases/03-simd.sx`）。也就是说决策一里「将来 SoA 化要给 MIR 加向量」
这件事，在方言这一层**已经有了第一阶段**。这不改变决策一（第一刀仍然一次一个片元），
但它把「以后怎么接」从「要新造一格」变成「要接上已有的那一格」。

**二、`rmath` 的名单比我以为的宽得多，可代价写在明处。**
我原本按 `01-core.sx` 里那句注释以为只有七个（sqrt/fabs/floor/ceil/round/fmod/pow），
于是准备「自己写 sin/cos 多项式」。**读代码发现不是**：`RMATH` 现在有 26 条，
sin/cos/tan/exp/log/atan2/hypot 全在（`sexpr/lower.js:101`），判据是
「C99 math.h 与 ECMA-262 Math 的**交集**」，实现只是转手宿主的库。

代价在 `src/runtime/omni_math.c` 的头注里，是量过的数：20 万个输入上
sin/cos/tan/atan/exp/log 的 120 万个结果里 **51.1 万个位不同**，按 `%.15g` 印出来 31.7 万个
字符串不同；拿 `bc -l`（scale=45）当参考，**libm 与 V8 谁都不是正确舍入**（macOS libm 的 sin
在 400 个输入里 28 个差 1 ULP，V8 22 个，还不是同一批）。

对这条线的意思很直接：**GLSL 那两份尺子重度用 `sin`/`cos`，所以 JS 腿与 C 腿之间
本来就不可能逐字节相同**。这不是我们的实现问题，是宿主数学库的事实。于是：

- 「五条腿逐字节相同」这条纪律对 GLSL 这一路**不适用**，走 `tests/asy/tol/` 那一节的口径
  （腿与腿之间只要求最后一位十进制差不超过 1）——**先例已经有了，不必新立规矩**
- 与决策二正好同向：像素比对本来就是容差的。两处容差是同一个来源

**三、方言的 `real` 是 double，GLSL 的 `float` 是 32 位。** 这是一处**真差别**，写在明处：
llvmpipe 那边整条片元管线是 float32（`lp_bld_type.c` 的 `type.width = 32`），我们按 double 算
再落成 8 位颜色。方向上这只会让我们**更准**，但「更准」在逐像素比对里同样是差别。
所以第三片落地时要顺手量一格：同一份 `FRAG_SIMPLE`，double 算与 float32 算的 8 位输出差几格。
若是 0，这件事就此了结；若不是 0，那就得在算完之后**每一步都截回 float32**（llvmpipe 就是
那样，因为它的向量类型就是 float32）。

### 于是第三片的形状定了

- GLSL 带类型的树 -> **核心方言**（不是直接到 MIR）。理由：JS 与 C 两条腿白得，
  而用户要的正是这两条腿的性能对照。
- `vecN` 拆成 N 个 `real`（决策一：一次一个片元，标量）。**不用方言的 `(vec real 4)`** ——
  那一格是「一次算 4 个片元」用的，不是「一个 vec4」用的。混用会把两件事搅在一起。
- 内建函数走 `rmath`，`fract`/`mix`/`clamp`/`smoothstep`/`length`/`normalize` 这些
  GLSL 特有的在降级里展开成方言的算术（它们都是几行算术，不必是内建）。
- 门的口径：容差，不是逐字节。理由在上面第二条。

## 落地：第一刀第三片 —— 降到核心方言，两条腿都跑起来了

`src/core/frontend-glsl/lower.js`。出来的是**核心方言文本**（与 jnc/asy 同一个出口），
于是 JS 腿与 C 腿一行没写就有了。

四处形状：

**一、每个中间结果都绑一个 `let`（三地址式）。** 不绑的话「一个向量表达式被 N 个分量各用
一次」会把它算 N 遍 —— `vec2(cos(a), sin(a)) * (0.55 + 0.15*sin(u_time+fi))` 里那个标量因子
会被算两次。既错（副作用）又慢，而这条线是要量性能的。

**二、片元着色器编成一个签名定死的函数**：

```
(fn glsl_frag ((frag_x real) (frag_y real) (<uniform 的每一格> real…)) glsl_v4 …)
```

uniform 走**参数**而不是全局 —— 这个函数没有隐藏输入，将来 SoA 化要换的只有参数与返回值的
类型（决策一那两条形状里的第一条）。`gl_FragCoord` 只给 `.xy` 两格真值，`.z`/`.w` 是 0/1
（这一档没有深度、没有透视）。

**三、`vecN` 拆成 N 个 `real`；只有「回向量的函数」用结构体。** 参数是**摊平**的
（`vec2 p` -> `p_0`、`p_1`），因为方言的参数表本来就能有多个；只有返回值躲不开，
于是 `(struct glsl_v3 (c0 real) (c1 real) (c2 real))`，调用处当场拆成 N 格。
一次调用一个 `(new)` —— 将来嫌它慢，办法是把这类函数内联，不是改这一层的形状。

**四、`min`/`max`/`smoothstep` 落成 `let` + `if`。** 方言没有表达式级的条件
（没有 `? :`），所以这三个（以及将来的 `clamp`/`step`）只能是语句。`smoothstep` 照规范 8.3
展开：`t = clamp((x-e0)/(e1-e0), 0, 1); return t*t*(3-2t)`。

### 一处真错误，门当场抓到

`for (int i = 0; …)` 写两遍 —— GLSL 里各是一层作用域，可 `for` 落成方言的 `while` 之后
`(let i_0 …)` 摆在 `while` **外面**，于是同一层里声明了两次，方言当场骂
`'i_0' 在这一层已经声明过了`。修法是局部量名字**一函数一份唯一**（重名的第二个起加个号）。
`bench-complex.frag` 正好有两个 `for`，所以这一格是被尺子逼出来的，不是我想到的。

### 门：`tests/glsl/lower.js` 11/0

- `FRAG_SIMPLE` 在 **JS 腿与 C 腿**上各跑 12 个像素、48 个数，**一致到容差**。
  容差不是逐字节：`cos` 是超越函数，libm 与 V8 在最后一位分叉（量过的数在上一节）。
  口径照 `tests/asy/tol/`。
- 48 个数与**门自己独立算的同一个公式**一致。这**不是 oracle**（真尺子是 llvmpipe）——
  它查的是「降级没有把公式改掉」：少一次乘、swizzle 取错一格、uniform 接错一格，这条都会红。
- `FRAG_COMPLEX`（第一档第二份，含两个 `for`、两个自定义函数、20+10 次 SDF）也跑得动。
- 6 条「还没接的要明着骂」：矩阵、三元、varying、`mix`、`if`、顶点着色器。

### 还缺什么才能与 llvmpipe 比图

这一片只到「一个像素一个函数」。还差：把画布扫一遍（**按 quad**，决策一第二条）、
写 PNG、以及在 llvmpipe 那边跑同一份 shader 取图。前两件是第四片，第三件要一台有 mesa 的
机器（本机是 macOS，`benchmark.py` 那条 surfaceless EGL 路走不通）—— 这一格得先解决，
不然「与 llvmpipe 比」是句空话。

## 落地：第一刀第四片 —— 把画布按 quad 扫一遍

`glslRenderMain` / `glslProgram`（同一份 `lower.js`）。库 + 这一段 = 一个能跑的方言程序。

**顺序是 llvmpipe 的最内两层**（`lp_bld_interp.c:53-87` 那张图）：一个 2×2 quad 里四个像素
按「左上 右上 左下 右下」，quad 之间按行。为什么现在就要这个顺序（一次明明只算一个片元）：
`dFdx`/`dFdy` 与纹理 LOD 天生要 quad，而 SoA 化就是把这个循环的**内核**换掉 ——
顺序现在定死，将来换内核时图不会变。

宽高不是 2 的倍数时，边上那些格子**照样算、但不印** —— llvmpipe 也是这样（边上的 quad
用掩码丢掉几个像素，而不是缩小 quad）。门里用 6×5 就是为了压这一格。

**印文本不写 PNG**：方言这一层没有文件 IO（只有 `print`），而这是**故意**的 ——
一门中间语言不该长出文件系统。于是一个像素五个 `print`（`x y r g b`），PNG 由外面拼。
代价写在明处：`print` 的开销在小画布上就盖过着色器本身，所以**性能对照不能走这条路**，
那要另一个不印东西的 main（第五片）。

一格实现上的小事，也记着：一个像素五个 `print`，没有拼成一行 —— 方言的 `+` 是「同型相加」，
`int + string` 不在它的规矩里，绕过去只会让这段更难看。

### 门：`tests/glsl/render.js` 5/0

- 6×5 印出 150 个数，30 个像素**每个正好一次**、没有出界的
- 次序**就是** quad 次序（逐个比，不是抽查）
- 30 个像素的 8 位值与门自己算的 `round(clamp(v,0,1)*255)` 相同
- **C 腿与 JS 腿的 8 位像素逐字节相同**。这一条值得单列：`cos` 在两条腿上只到容差
  （上一节那些量过的数），但 8 位那一步把最后一位的差**抹掉了** —— 于是在**像素**这一层
  两条腿反而是逐字节的。这是一个好消息：将来与 llvmpipe 比图时，我们自己这几条腿之间
  不必先谈容差。

## 落地：第一刀第五片 —— 量性能那一段（不判快慢，判「量的是同一件事」）

`glslBenchMain` / `glslBenchProgram`。**一个字节都不印**，只在最后印一个校验和。

两处理由，都得写下来：

- **为什么不拿第四片那条路量**：那一段一个像素五个 `print`，量出来的是 `print` 的耗时不是
  着色器的（128×128 上前者就盖过后者）。
- **为什么要有校验和**：不攒一个用得到的结果，整个循环会被后端当死代码扔掉 ——
  那时量出来的是「什么都不做要多久」。攒的是每个像素三格 8 位值的和，与第四片印出来的
  那些数一一对应。

门里那条最要紧的断言就是这一点：**同一尺寸下校验和正好等于印出来那些 8 位值之和**。
一个量错东西的 benchmark 比没有 benchmark 更坏。另外还查「迭代 3 遍的校验和正好是 3 倍」——
循环没被折叠掉的证据。

### 门：`tests/glsl/bench.js` 4/0

**这一门不判快慢**（写死一个毫秒数只会在别的机器上骗人）。耗时只当**参考**印出来：
本机 128×128（16384 个片元，含进程启动与编译）js 107ms、c 152ms。两条腿的校验和相同。

C 腿比 JS 腿慢**不是**「C 生成的代码慢」——这一趟里 C 那条腿要 clang 编一遍再跑，
而 JS 那条腿是 V8 直接吃。量真正的执行时间要把编译摊出去（跑多遍、或者只计执行段），
那是与 llvmpipe 对照时才需要的口径，等 mesa 那一头解决了一起做。

## 落地：第一刀第六片 —— 第二档的降级（除了插值）

第二档（`pretty_render.py`）语法与类型检查上一片就收了，这一片把**降级**补上：
`mat2` 与四种矩阵乘、三元 `? :`、`if`/`else`/`while`、
`mix`/`clamp`/`step`/`sign`/`fract`/`normalize`/`dot`/`distance`/`cross`/
`inversesqrt`/`radians`/`degrees`。

四处要紧的，每一条都能悄悄错：

**一、矩阵是列优先**（规范 5.6）：`mat2(a,b,c,d)` 的第 0 列是 `(a,b)`，所以
第 `col` 列第 `row` 行是下标 `col*N + row`。**记错就是转置** —— `rot(a)` 变成反方向的旋转，
一个数都不会 NaN，只有对着图才看得出来。门里那两条（`mat2*vec2` 与 `vec2*mat2`）
挑的数就是为了分开这件事：拿 `mat2(0,1,-1,0)` 乘 `(1,0)`，列优先得 `(0,1)`、
行优先得 `(0,-1)`——差一个符号。

**二、`matN(x)` 是对角线填 `x`**，不是每格都填（规范 5.4.2）。填成四个 1 的话
`mat2(1.0)` 就不是单位阵了。

**三、`mix` 照规范写 `x*(1-a) + y*a`**，不写成 `x + (y-x)*a`。两者代数上相等，
浮点下不等价：`a == 1` 时前者精确回 `y`，后者不一定。门里第二格就是 `a=1`。

**四、三元的两支各自的中间量留在自己那一支里。** GLSL 的 `? :` 只算一支，
把两支的 `let` 都提到 `if` 外面就变成两支都算 —— 不只是慢：`1.0/z` 那种在不该走的
那一支里可能是除零。门里那条探针就是 `z > 0.0 ? 1.0/z : 7.0`（`z` 是 0）。
反过来 `if` 语句的条件**可以**提出去，因为它本来就要算一次。

`if` 落成方言的 `(if c (do …) (do …))`，`while` 走 `condIn`（条件每轮重算，
所以要求它降出来是一条表达式）。

### 还剩什么

- **插值（varying）**：`in vec2 v_uv` 还是明着骂。这是第二档里唯一的真活 ——
  要 `a0`/`dadx`/`dady` 那一套（llvmpipe 的 `lp_bld_interp.c`），而那要先有
  「三角形 setup」这一步。它值一片。
- **顶点着色器**：同上，插值的另一半。
- `m[0]`（矩阵取列）与 `continue`：两句 `glslNyi`，位置写在 `lower.js` 里。

### 门：`tests/glsl/lower.js` 17/0

第二档九条，每条给一个**能手算**的答案（不是抄实现的输出）。加上原来第一档那四条、

## 量：`gl_FragCoord.y` 与缓冲行序（写 PNG 之前必须知道的一格）

第四片那个扫描循环把「行号」直接当成 `gl_FragCoord.y - 0.5`。**这一格是对的，但理由要写下来**，
因为它决定写 PNG 时要不要翻转：

- GLSL 330 规范 7.2：`gl_FragCoord` 是**窗口相对**坐标，原点在**左下**
  （除非用 `layout(origin_upper_left)`，两份尺子都没用）。
- 尺子自己的代码印证了这一点：`pretty_render.py:136-137`

  ```python
  img = Image.frombytes("RGBA", size, data)
  img = img.transpose(Image.FLIP_TOP_BOTTOM)
  ```

  `fbo.read()` 出来的第 0 行是**最下面**那一行，所以要翻一次才是给人看的图。

于是三件事对齐了：我们循环里的 `qy = 0` 是**画布最下面**那一行、`gl_FragCoord.y` 从下往上长、
将来写 PNG 时**要翻一次**（或者写的时候按倒序写行）。三者只要有一处记反，图就是上下颠倒的 ——
而颠倒的图每个像素的值都"对"，逐像素比对**照样全红**，那时候最难查的是「到底谁反了」。

## 落地：第一刀第七片 —— 顶点着色器与插值（第二档齐了）

`glslTriProgram`（同一份 `lower.js`）：顶点 + 片元 + setup + 插值，一整条。

**形状照 llvmpipe 那条分界**（ADR-0019「量：读 llvmpipe」第三条）：
「一个三角形一次」的 setup 算 `a0`/`dadx`/`dady`（一条方言函数 `glsl_plane`，三点定平面），
「一个片元一次」的求值就是 `a = a0 + x*dadx + y*dady`。片元入口因此多了 varying 参数 ——
**插值不在片元函数里**，与 `lp_bld_interp.c` 是独立一块同一个道理。

四处决定：

**一、透视校正做全，不限制 `w = 1`。** 标准做法：插 `a/w` 与 `1/w`，片元处相除。
两份尺子的 `gl_Position.w` 都是 1，此时它**精确**退化成线性插值 —— 所以本来可以偷懒
写线性、再写一句「w 必须是 1」。做全的理由是那句限制迟早要还，而代价只是多插一个 `oow`。

**二、三档插值方式是编译期定死的常量**，运行期没有分支（与 `enum lp_interp` 一样）：
`smooth` 除 `oow`、`noperspective` 不除、`flat` 直接取**第三个顶点**
（GL 4.x 默认的 provoking vertex 是 last）。

**三、顶点那一侧的函数名加前缀 `glsl_v_`。** 顶点与片元是两份源码，里头的辅助函数**可以同名**
（两边各有一个 `sdCircle` 很正常），并到一个方言模块里就撞了。

**四、这一段不做覆盖判定。** 两份尺子都是「一个三角形铺满整个视口」，所以每个像素都在里头。
真正的边函数掩码（`do_block_16`/`do_block_4`）是下一片。**写在明处**：现在喂一个不铺满的
三角形，它会把外面也画上。

### 门：`tests/glsl/interp.js` 6/0

- **varying 插得对，而且期望值是手算的**：全屏三角形上 `v_uv = p*0.5+0.5` 在三个顶点是
  `(0,0)/(2,0)/(0,2)`，窗口坐标是 `(0,0)/(2W,0)/(0,2H)` —— 插出来精确等于
  `gl_FragCoord.xy / 分辨率`。24 个像素逐个比。
- `flat` 全取第三个顶点。
- **透视校正不是摆设**：`w` 不全为 1 时 `smooth` 与 `noperspective` **必须不同**；
  `w` 全为 1 时两者**逐字节相同**。后一条是定义，前一条是「那一下除法真的在做」的证据 ——
  少了它，把 `smooth` 写成线性也能全绿。
- 两条腿的 8 位像素相同（含 `sin` 与插值）。
- **第二档那份完整的着色器跑通**：`pretty-vert.vert` + `pretty.frag`（hex 网格 + 发光圆 +
  `hsv2rgb` + 色调曲线 + `pow`）8×8，像素和 11489（查「不是一片全黑」——那是插值或 uniform
  接错时最常见的样子）。

第二档到这儿**齐了**。剩下的是真正的光栅化（覆盖判定）与与 llvmpipe 比图。

<!-- ADR-0019 第七片-END -->

## 落地：第一刀第八片 —— 覆盖判定（光栅化真了）

前七片都假设「一个三角形铺满画布」。这一片把覆盖判定接上：三条边函数，逐像素三次叉积，
**三条都 `>= 0` 才着色** —— 不覆盖的像素连片元函数都不调。

公式与符号约定写在 `lower.js` 里，这里只记要紧的两条：

**一、`e` 与 `area` 必须同源。** 用叉积：`e_j(p) = cross(b-a, p-a)`，而
`area = cross(v1-v0, v2-v0)` 就是同一个叉积 —— 于是「面积为正 ⇒ 内部 e 为正」自动成立。
第一版我把 `e` 写成 `(x-xa)*(yb-ya) - …`（反的），全屏三角形上三条边函数**全为负**，
一个像素都没画，门当场全红。

值得记的是**如果当时只有「全屏三角形能画」这一条门**，我很可能把 `>=` 改成 `<=` 蒙过去，
而那在另一种绕向上又是错的。所以这一片的门里专门有一条「绕向反过来画的是同一片像素」。

**二、`sgn` 那一格（绕向）是必要的**，不是保险：顺时针的三角形三条边函数整体反号，
少了它会被判成「全在外」，一个像素都不画。llvmpipe 是在 setup 里把三角形拧成固定绕向
（`lp_setup_tri.c`），一回事。

**还没做的两处，写在明处**：

- **边上的归属规则**还不是 GL 的 top-left（现在 `>= 0` 含边）。只有两个三角形共享一条边时
  才看得出来 —— 那条边上的像素会画两遍。**（第九片补上了。）**
- **分层加速**（llvmpipe 的 `do_block_16`/`do_block_4`：16×16 块一次判 16 个 4×4 子块的
  全内/全外/骑边）还没做。现在是逐像素三次叉积 —— **正确但没有加速**。
  分层是性能优化，等有了基线再说值不值（与决策一同一个道理）。

### 门：`tests/glsl/raster.js` 4/0

- **半覆盖**（clip `(-1,-1) (1,-1) (-1,1)`，8×8 上盖 36/64）：画的是**哪些**像素逐个比，
  期望集合由门**自己**用叉积算（独立实现，不抄降级那一侧）。门里还有一句「这个探针要有
  区分度」——盖 0 个或盖满 64 个都算门坏了。
- 绕向反过来画的是同一片 36 个像素。
- 全屏三角形照旧铺满 64 个（前七片的门靠的就是它，这是回归）。
- 不覆盖的像素连片元都不调：片元里写一个必然除零的算式，印出来的像素数正好等于覆盖数。

<!-- ADR-0019 第八片-END -->

## 落地：第一刀第九片 —— 边上的归属规则（不重不漏）

第八片的覆盖判定在边上用 `>= 0`，于是两个共享一条边的三角形会把那条线**各画一遍**。
这一片补上归属规则：`in_j = (e_j > 0) || (tl_j && e_j == 0)`，其中
`tl_j = (sdy > 0) || (sdy == 0 && sdx < 0)`（`sdx`/`sdy` 是那条边的方向，乘过绕向 `sgn`）。

两处要紧的：

**一、判据必须对边的方向是奇的。** 方向反过来 `tl` 就反过来 —— 于是两个共享边的三角形
（绕向都归一之后，那条边在两边的方向正好相反）里**恰好一个**认领它。不重不漏因此是
这个判据的性质，不是碰巧。

**二、`sdx`/`sdy` 要乘 `sgn`。** 绕向归一化只改了 `e` 的符号、没改边的方向；不跟着乘的话，
同一片像素在两种绕向下会得到不同的归属 —— 而第八片那条「绕向反过来画的是同一片」正好压它。

**这一片刻意不声称与 GL 一致。** GL 的 top-left 规则说的是「哪一侧归谁」，而验证它要一台有
GL 的机器（ADR 待办第 12 条）。这一片能保证的是**不重不漏** —— 那是填充规则的定义性性质，
不用 GL 也验得了。与 GL 差一个整体翻转的可能性**留着，写在这儿**：真要对上，
量一次 llvmpipe 的输出就知道，而那时候改的只有 `tl` 那一行。

### 门：`tests/glsl/raster.js` 4/0 → 5/0

新增那一条是**方块拼接**：两个三角形共享斜边拼成 8×8，`36 + 28 = 64`，**交集为空、并集铺满**。
第八片那时候这条会红（斜边上那 8 个像素两边都画）。

`coverOf`（门自己那份独立实现）也跟着实现同一套规则 —— 它查的是「实现符合设计」；
「设计对不对」由方块那一条查。

## 量：这台机器上取得到什么尺子

决策二说尺子是 llvmpipe，而前面几片一直写着「本机是 macOS，取不到」。**这一次真去量了**，
结论比之前写的乐观：

- `python3 -c "import moderngl"` —— **在**（moderngl 5.12、PIL 也在）
- `moderngl.create_standalone_context()` —— **建得起来**，`GL_RENDERER` 是
  **`Apple M1`**、`GL_VERSION` 是 `4.1 Metal - 90.5`。也就是说本机取得到**真 GPU 的 GL**，
  而且 4.1 core 正好收 `#version 330 core`。
- `docker` 的 CLI 在，但 daemon（OrbStack）**没起** —— llvmpipe 那条路还是断的。

于是这条线上多了一台**能用的尺子**：硬件 GL。它不是 llvmpipe，但**规范规定的那些格上
它一样管用**：覆盖判定、填充规则、插值、透视、`gl_FragCoord` 的原点、缓冲行序、
8 位量化。只有 `sin`/`cos`/`smoothstep` 那种实现自由度上两者才可能分岔 ——
而那正是决策二要量的「容差」。

**「取不到尺子」这句话是我没量就写下的。** 记在这儿，因为它耽误了好几片
（前九片全是自证，本来第一片就能有外部 oracle）。

## 落地：第一刀第十片 —— 与真 GL 比像素，**最大差 0**

`tests/glsl/gl_ref.py`（尺子那一侧：moderngl 渲一份 vert/frag，逐像素印 `x y r g b`）
+ `tests/glsl/oracle.js`（比）。

**结果：三份用例、16×16、最大逐通道差 `0`。**

- `bench-simple`（第一档）
- `bench-complex`（第一档，30 个 SDF、两个 `for`、两个自定义函数）
- `pretty`（第二档，varying + `mat2` + `hsv2rgb` + 色调曲线 + `pow`）

也就是说这一整条 —— 顶点着色器、裁剪空间到窗口坐标、三角形 setup、透视校正插值、
覆盖判定、边上的归属、quad 扫描、8 位量化，以及 `sin`/`cos`/`pow`/`smoothstep` 的数值 ——
与 Apple M1 的 GL **逐字节相同**。

顺带把两件之前「写在明处的不确定」定下来了：

- **`gl_FragCoord` 的原点与缓冲行序对了**：差一个翻转的话 16×16 上会有大片不同（图上下颠倒）。
- **填充规则与 GL 同侧**（第九片写着「差一个整体翻转的可能性留着」）：全屏三角形上
  斜边不在画布里，所以这一条严格说还只是**弱证据**；强证据要一个斜边穿过画布的三角形，
  记在待办里。

### 容差为什么定 1 而不是 0

门里 `TOL = 1`。第十二片把画布加大之后，这个 1 **不是保险了，是真的会用到**（量出来的）：

- 64×64（4096 像素 / 12288 通道）：`bench-simple` 0 差、`half` 0 差、
  `bench-complex` **2 个通道差 1**、`pretty` **1 个通道差 1**
- 128×128 `bench-complex`（16384 像素 / 49152 通道）：**3 个通道差 1**，其余全同

16×16 上量到全 0，是**样本太少没踩到** —— 这一条本身就是「小画布的绿是弱绿」的证据。

差 1 的来历有两层，都写下来：

- 8 位量化把 `round(v*255)` 的边界放大 —— `v` 差 `1e-9` 也可能让整数差 1；
- 超越函数（`sin`/`cos`/`smoothstep` 里的乘除）在 GPU 与 libm/V8 之间差 1 ULP 是常态
  （`src/runtime/omni_math.c` 头注里那 51.1 万个位不同的量就是这件事）。

所以 `TOL = 1` 是「量出来的 0/1 + 一格已知的实现自由度」，不是拍的。门每次把**实测最大差**
与**差 1 的通道数**都印出来 —— 这两个数往上走的那一天会被看见。

没有 `python3 + moderngl` 的机器上整组**跳过**（印 skip 并说明），不假过。

## 落地：第一刀第十一片 —— 填充规则的方向，量出来了（而且是反的）

第九片实现了「边上的样本归一个三角形」，并明写着「与 GL 差一个整体翻转的可能性留着」。
第十片用的三份用例都是**全屏三角形**（斜边在画布外），所以那个可能性一直没被碰到。

这一片加了一份**斜边穿过画布**的用例（`half-vert.vert` + `half.frag`，clip
`(-1,-1) (1,-1) (-1,1)`，16×16 上斜边正好经过 16 个像素中心）。第一趟就红了：

```
超差 48 个通道（共 408 个），最大差 191
最坏那一处 15,0 通道2：尺子 0 / 我们 191
```

48 = 16 个像素 × 3 通道 —— **正好是斜边上那 16 个**。GL 判它们**在外**，我们判在内。
于是把判据翻过来：`tl = (sdy < 0) || (sdy == 0 && sdx > 0)`。

三件事因此同时成立：

- `oracle` 四份用例全部 **最大差 0**（含这一份 120 个像素）；
- `raster` 那五条**照旧全绿** —— 判据仍然是**奇函数**，所以「不重不漏」不受方向影响
  （方块拼接从 `36 + 28` 变成 `28 + 36`，和还是 64）；
- 第九片那句「留着的可能性」被量掉了。

**这一格对齐的是本机那台 GL**（Apple M1）。GL 规范只要求「边上的样本恰好归一个三角形」，
没规定归哪个 —— 所以 llvmpipe 那边要再量一次。写在 `lower.js` 的注释里与这儿。

值得记的是这一片证明了第九片那句自我怀疑是对的：**当时没有把「与 GL 同侧」当成已知**，
而是明写「还没量」。三片之后量到的结果正是反的。

## 落地：第一刀第十二片 —— 把画布加大，容差从「保险」变成「量出来的」

第十片只比 16×16，全 0 差。**那是弱绿** —— 样本太少。这一片把 oracle 提到 64×64

结果（也就是上面那节容差的来历）：

- 64×64：`bench-simple` 0 差、`half` 0 差、`bench-complex` **2 个通道差 1**、`pretty` **1 个**
- 128×128 `bench-complex`：**3 个通道差 1**，其余全同

门现在把**最大差**与**差 1 的通道数**都印出来。整门 1.4 秒（我们那一侧 128×128 要印
8 万行，再往上就是在量 `print` 而不是量像素了 —— 那是第五片那条 bench 路的事）。

## 落地：第一刀第十三片 —— 第一张性能对照表

`tests/glsl/gl_bench.py`（GL 那一侧，照 `benchmark.py` 的口径：warmup 一帧 + N 帧，
**每帧含 `fbo.read()`**）+ `tests/glsl/perf.js`（我们这一侧 + 印表）。
**这不是门**（不判快慢），是一支可重复的尺；默认不进 `run.js`。

**怎么把「进程启动 + 编译」摊出去**：两趟差值 `t(2N) - t(N) = N 帧的净渲染时间`。
固定开销（node 启动、方言降级、C 腿那边 clang 编译）在两趟里一样，减掉就没了 ——
比「跑一趟然后猜编译占多少」诚实。另外还核对「校验和成倍数」，不成倍数就说明两趟画的
不是同一件事，那个差值不能用。

本机（Apple M1）量到的第一组数，`bench-complex.frag`（30 个 SDF）：

- **128²**：我们 JS `26.0ms`（0.6 MPix/s）、我们 C `11.3ms`（1.5 MPix/s）、
  真 GL `0.419ms`（39.1 MPix/s）
- **256²**：我们 JS `186.3ms`（0.4 MPix/s）、我们 C `93.7ms`（0.7 MPix/s）、
  真 GL `0.646ms`（101.4 MPix/s）

三条读法：

1. **C 腿比 JS 腿快约 2 倍。** 同一份方言、同一套算术 —— 差的是后端。
2. **真 GL 快 60～280 倍。** 这是预期的：我们是**标量、一次一个片元**（决策一），
   而对面是硬件光栅化器。这张表的用处不是比大小，是**以后每一步优化能不能量出来**。
3. **一处待查的异常**：像素数 4 倍（128²→256²），我们 JS 的时间涨了 **7.2 倍**（超线性），
   C 腿 8.3 倍。真 GL 只涨 1.5 倍（它在 128² 上根本没吃饱）。超线性那一格得查 ——
   可能是 GC、可能是我这个差值法在 `N=3` 时噪声太大。**记下来，不猜。**

## 落地：第一刀第十四片 —— 那处「超线性」是量法的噪声，不是实现的问题

第十三片记了一处待查：像素数 4 倍而我们的时间涨 7～8 倍。**去量了，不是实现的事。**

### 怎么量出来的

把帧数**钉成同一个数**再跑（`OMNI_GLSL_N`），同一档在不同帧数下的值：

- 128² JS：`26.0` / `31.7` / `39.5` ms（N=8 / 3 / 6）—— 波动 **50%**
- 256² JS：`186.3` / `165.7` / `173.7` ms —— 波动 12%
- 而且 N=3 时 C 腿量出 **−49.0ms**（负数）

负数是决定性的一条：`t(2N) - t(N)` 里两趟的**固定开销抖动**（进程启动、V8 预热、
clang 那一趟）比净渲染时间还大。128² 一帧才十几毫秒，而抖动有几十毫秒 ——
**小画布上这个差值法根本不成立**，量出来的斜率是噪声。

### 修法与修完的数

两处：

- **每趟跑 3 次取最小**。噪声是**单向**的（别的进程、GC、频率调节只会让某一趟变慢，
  不会让它变快），所以最小值最接近「没被打扰的那一趟」。取平均会把噪声算进斜率。
- **帧数加大**（128² 从 8 提到 24），让净时间远大于抖动。

修完（同一台机器、同一份 `bench-complex.frag`）：

- **128²**：我们 JS `34.9ms`（0.5 MPix/s）、我们 C `24.6ms`（0.7 MPix/s）、真 GL `0.391ms`（41.9）
- **256²**：我们 JS `141.5ms`（0.5 MPix/s）、我们 C `96.8ms`（0.7 MPix/s）、真 GL `0.593ms`（110.5）

**MPix/s 两个尺寸完全一样**（JS 0.5/0.5、C 0.7/0.7），时间比 `141.5/34.9 = 4.05`、
`96.8/24.6 = 3.93` —— 像素数正好 4 倍，**是线性的**。超线性不存在。

整趟 37 秒（3 次 × 两趟 × 两个尺寸 × 两条腿），所以 `perf.js` 不进 `run.js`。

### 记下来的教训

第十三片那张表**结论没错**（C 快 2 倍、GL 快两个数量级），但它**多说了一句**
「有一处超线性」——而那句是量法的产物。写下「待查、不猜」是对的；如果当时顺手解释成
「大概是缓存」，就会留下一条假知识。

## 落地：第一刀第十五片 —— 量出「框架 vs 着色器」，于是分层加速**现在不值得做**

待办里排着「分层加速」（llvmpipe 的 `do_block_16`/`do_block_4`）。动手之前先量一件事：
**框架占多少**。办法是加一份 `trivial.frag`（一行算术都没有，只写一个常数），
它的时间就是「扫画布 + 覆盖判定 + 插值 + 8 位量化 + 调用」——**框架那一半**；
`bench-complex` 减掉它就是**着色器那一半**。

量到的（Apple M1）：

- **128² JS**：`trivial` 1.3ms、`bench-complex` 39.1ms —— 框架占 **3.3%**
- **256² JS**：`trivial` 7.0ms、`bench-complex` 156.0ms —— 框架占 **4.5%**
- **128² C**：`trivial` 1.0ms、`bench-complex` 24.5ms —— 约 **4%**

**于是分层加速最多能省 3～5%。现在不做。** 它在 llvmpipe 那边值，是因为那边的片元是
SIMD（一次 8 个像素），框架占比高得多；在我们这个**标量**实现里，时间几乎全在着色器里。
要提速就得动着色器那一半 —— 也就是决策一里那条「等有了基线再定」的 SoA/向量化。
**基线现在有了，那条路的理由也有了。**

### 一处不可信的数，写在明处

`trivial` 在 **C 腿 256²** 上量出 `0.1ms`（524 MPix/s）—— 那是 1.5ns/像素，不可能。
原因是 `trivial` 的结果与像素**无关**，而校验和累加的是常数，所以 clang 大概把整个
循环折成了闭式（常数 × 像素数）。**JS 腿那两个数（1.3 / 7.0ms）是可信的**（V8 没做这一步），
上面那个「框架占 3～5%」的结论就是拿 JS 腿算的。

这也提醒一件事：第五片给 bench 加校验和是为了防止死代码消除，但「校验和本身可被折叠」
是另一回事 —— 真正与像素相关的着色器（`bench-complex`）不会被折，所以那一档的数没问题。

<!-- ADR-0019 第十五片-END -->

## 量：SoA 要方言长出什么（下一刀的入口）

第十五片量出「时间 95% 以上在着色器里」，于是下一步是 SoA（一次算 4 或 8 个片元）。
动手之前**先量方言那一格的边界**（`sexpr/lower.js` 的 `vecExpr` 与 `binExpr`，
注释里写得很清楚，是刻意的「第一阶段」）：

**有的**：

- `(vec elem N)`，`elem` 只能 `int`/`real`，`N ∈ {2, 4, 8}`
- `(splat T E)`、`(vlit T E…)`、`(lane E N)`（`N` 必须是字面量）、`(hsum E)`
  （`hsum` 的求值顺序**写死成严格左到右**，因为浮点加法不结合）

**没有的**（源码里明着挡住，注释说「要先在六个执行器上定好语义，第一阶段不做，
所以在这里挡住而不是给错答案」）：

- 向量上只有 `+ - * /`；**比较、select、shuffle 都没有**
- `rmath` **只收 `real`**，不收向量
- `print` 不收向量（要看就 `(lane v k)` 逐道印）

### 于是 SoA 要三样，而且优先级分得开

1. **向量比较 → 掩码类型**（`vec<bool,N>`）。GLSL 侧 `min`/`max`/`clamp`/`step`/
   `smoothstep`/三元/`if` 全都要它 —— 在 SoA 下这些不能再落成 `if` 语句
   （四个片元的分支可能不同），必须变成掩码。**绕不过去。**
2. **`select`**（`(vsel mask a b)`）。与 1 是一对：有了掩码才能选。**绕不过去。**
3. **`rmath` 的向量版**。这一样**可以先绕**：拆成 `lane` 取四道、各调一次标量
   `rmath`、再 `vlit` 重组。收益打折（`sin`/`cos` 是 `bench-complex` 里的大头），
   但它不阻塞 SoA 的骨架。

所以下一刀的形状是：**先给方言加 1 与 2**（那是动六条腿的事，要单独一刀、单独的门），
再回来把 `glsl_frag` 的参数与返回值从 `real` 换成 `(vec real 4)`。

决策一当时写的「SoA 化就是把这个循环的内核换掉」——现在能说得更准：**换内核之前，
方言得先有掩码与 select**。这一句是量出来的，不是估的。
