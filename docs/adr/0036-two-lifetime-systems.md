# ADR-0036：两套寿命并存 —— `lifetime` 栏五格取值，GC 与算出来的释放点不许抢

## 决定

**`lifetime` 那一栏从三格取值扩到五格，且每格值只由一套机制管，不混：**

```
owns             图算释放点（ADR-0033 §3.5 第 4 条：最后一次可达使用 + 所在 region）
borrows(in-port k) 不管释放；**可带一格附属"延长"**（cpp 的临时量绑 const& —— 见 §3）
static           不释放
managed          **GC 管**。图不给它算释放点，只给 GC 两样东西：根集与 trace 边
untracked        谁都不管（FFI 与裸指针的口子；mojo 的 MutUntracked/UnsafeAny 那一族）
```

**判据（静态）：一格值不许同时被两套管。** 每个出端口的 `lifetime` 恰好一个取值；
`managed` 的值上不许出现释放点，`owns` 的值不许进 trace 边。

## 为什么现在做

这是十份规格里**三门语言独立指出来的同一笔账**（`docs/design/node-graph-contract.md`
附录 A.5 第 2 条）：

- `ext/lua/SPEC.md` §六第 3 条：`__gc` 与弱表要 `gc-lifetime` 能力，
  与"释放点靠图上最后一次使用算"**冲突**。
- `ext/nim/SPEC.md` §六第 4 条：ORC 的 `=trace`（环检测）同上。
- `ext/vlang/SPEC.md` §六第 6 条：autofree / ARC 那条线同上。

外加两门指出取值不够：

- `ext/mojo/SPEC.md` §3.1 第 2 条：要一格 `untracked`，
  **不加的后果是所有 C 互操作都得撒谎说自己 `owns` 或 `borrows`**。
- `ext/cpp/SPEC.md` §3.1 第 2 条：临时量绑到 `const&` 会**延长所有者的寿命** ——
  借的一方能改被借者的寿命，这是 `borrows` 上的一格新情况。

五门语言。这一格不改，`scope-exit` 那台机器（8 个提供者，清单上最稳的一格）
会在第一门带 GC 的语言上失效。

## 冲突到底在哪儿（说清才好判）

ADR-0033 §3.5 第 4 条的释放点计算是**线性的**：一格值的最后一次可达使用 + 它所在的
`region` ⇒ 释放点。这套算法有一个前提：**寿命是图上可判定的**。

GC 的前提正相反：**寿命不可判定**（所以才要 GC）。`__gc` / `=trace` / 弱表
要的是"到某个不确定的时刻，宿主发现它不可达了，那时候跑一段代码"。

**两套机制的输入都是"可达性"，但一套算的是图上的静态可达，一套算的是运行期堆上的动态可达。**
把它们混在同一格取值里，结果是每格值都要问一句"这次算的是哪种可达" ——
那就是 ADR-0033 §0 第 4 个问题（重复代码）的原样重演。

## 决定的三个后果

### 1. `managed` 的值，图只出两样东西

- **根集**：图上哪些端口是 GC 的根（栈上的、静态区的、寄存器里的）——
  这是图**已经知道**的信息（`region` + `lifetime`），免费。
- **trace 边**：一格 `managed` 值内部指向别的 `managed` 值的那些字段。
  nim 的 `=trace`、lua 的表遍历、chez/sbcl 的 GC 都要它。
  在图上它是**一块可参数化子图**（ADR-0033 §3.4），由 `record` 的 `layout` 算出来。

**图不出释放点，也不出"什么时候跑 `__gc`"。** 那是宿主的事，
落在 `node-graph-contract.md` §8 那条纪律里（宿主 IO 与运行时走封闭 ABI）。

### 2. 跨界要一格显式节点

`owns` 与 `managed` 之间来回，是真实语料里的常事（lua 的 userdata 装一格 C 结构、
nim 的 `ref T` 里放 `ptr T`、V 的 autofree 与手动 `free` 混用）。**不许隐式跨界**：

```
hand-to-host  : owns → managed    "交给宿主管"（此后图不再算它的释放点）
pin           : managed → borrows  "在这段区间里别动它"（GC 不许搬、不许收）
```

两格节点，**不是能力**（现在只有 lua / nim / vlang 三家，够两家门槛，
但它们要的是同一件事，所以做成两格骨架节点更省）。
`untracked` 与前两格之间**不给**跨界节点：进了 `untracked` 就是出了系统，
回来要显式声明（这是有意的摩擦）。

### 3. `borrows(k)` 上加一格附属：`extends`

cpp 的规则（临时量绑到 `const&`，寿命延长到引用结束）与 mojo 的第三条规则
（"若有引用存在，延长所有者的寿命"，`ownership.mdx:26-33`）是同一件事的两种说法。

落法：`borrows(k)` 那格值上挂一格附属 `extends`。有它 ⇒ 释放点计算时，
被借者的"最后一次可达使用"**取借用者的最后一次使用**。
—— **仍然是同一套计算，只是可达性图上多一条边**。不新增机制。

## 为什么不是别的做法

- **不做统一的寿命理论**（把 GC 表达成"某种 region"）：试过的人不少，
  代价是每一格 `owns` 的值也要走那套抽象。我们要的是"释放点算出来"这件**便宜**的事，
  不是理论统一。
- **不做借用检查**（ADR-0033 §10 已经写死：寿命只用来算释放点，检查是另一格特性的事）。
  `managed` 这一格更是明确不检查。
- **不给 GC 留"默认"**：一格值的 `lifetime` **必须显式**。
  没写就是构建期错误 —— 与 `unordered` 那格"想让调度器自由得显式说"（ADR-0033 §10）
  同一条纪律。
- **不做增量/并发 GC 的建模**：那是宿主运行时的实现，图上看不见。
  能看见的只有根集与 trace 边（§1）。

## 代价

1. **五格取值要写满**。十门语言的每个节点声明都要答这一格，而"答错"的代价是
   泄漏或双重释放 —— 比效应栏答错更直接。对策：`managed` / `untracked` 这两格
   **只许出现在明确来源**（GC 语言的分配点、FFI 边界），别处出现即错。
2. **`pin` 会传染**：一段 `pin` 区间里调的每一格函数都要能容忍"这格值不许搬"。
   这是真实约束（JNI / Python C API 都有），不是我们引入的。记账。
3. **弱表与终结器（`__gc`）的语义仍然不在图上**。这一格明确**不做** ——
   它是宿主的语义。判据只能是"同一份语料在参考实现与我们这边的终结器调用次数一致"，
   而这条判据要等有 GC 后端才跑得起来。

## 判据（可执行）

- **L1**：每个出端口的 `lifetime` 恰好一格取值，且不缺 —— 构建期检查。
- **L2**：`managed` 的值上没有释放点、`owns` 的值不进 trace 边 —— 构建期检查。
  **这两条就是"不许抢"的全部内容。**
- **L3**：`owns` 的释放点数 + `managed` 的对象数 = 全部分配点数（每份语料一次统计）。
  差出来的就是漏掉 `lifetime` 声明的那些。
- **L4**：跨界只经 `hand-to-host` / `pin` 两格节点 —— 静态检查。
- **L5**：`extends` 那格附属在 cpp 的 [class.temporary] 条款上逐条对表；
  对不上的条数记账（与 ADR-0035 的 S3 同一种做法）。

## 一句话

**`owns` 归图算，`managed` 归宿主管，`borrows` 不管但可延长，`static` 不释放，
`untracked` 出了系统；跨界只有两格节点，一格值不许被两套机制同时管。**
五格取值，两格新节点，一格新附属 —— 释放点那套计算本身一个字不改。
