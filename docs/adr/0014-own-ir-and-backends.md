# ADR-0014：自有 IR 与多后端（C 后端降为备选）

状态：提议
日期：2026-08-26
取代：本文件同日的早先一稿（那稿只谈解释器与 JIT，把问题问小了，见背景）
相关：ADR-0013（执行引擎分层与 C-FFI 契约）、ADR-0006（值与容器）、ADR-0011（JS 降级）

## 背景：上一稿错在哪

上一稿的论据是「clang 编 3.83MB 生成码要 21s，所以要 JIT」。这个论据站不住，因为
它有更便宜的解：接上 tcc，全量自构建从 clang -O2 的约 50s 降到 **1.80s 冷启动 /
0.99s 热启动**，不动点逐字节成立（实测数据在附录）。

但这个答案回答的是「怎么让现在这条 C 路径快起来」，不是「后端架构该是什么」。
三件事决定架构，而它们**全都过不了 C 这一关**：

1. **增量编译**。走 C 就是「序列化成文本 → 重新分词 → 链接」。编译单元是文件，
   C 里没有「这一个函数变了」这个概念；链接是全程序步骤，它给增量时间设了地板。
   拆成多 TU 也只到文件粒度，链接那一步还在。
2. **SIMD**。C99 没有可移植向量。要么按目标写 intrinsics（`arm_neon.h` /
   `immintrin.h`，等于把 SIMD 后端在发射器里写三遍），要么靠自动向量化 —— 不可预测，
   而 tcc 完全不做，于是「备选路径静默丢掉全部 SIMD」。两条都不能接受。
3. **GLSL / GPU**。这条直接判死 C 中心的设计。SPIR-V 要求结构化控制流
   （`OpSelectionMerge` / `OpLoopMerge`）、显式地址空间、无递归、无函数指针、
   uniform 与 varying 分离。这些性质过一趟 C 文本之后全部丢失，没法在下游重建。

所以本 ADR 的第一条决定是定位的改变：**C 后端从主路径降为备选**，主路径是我们自己的
IR 加自己的代码生成。C 留下来干三件它擅长的事：可移植性兜底、调试期可读产物、
以及作为差分测试的 oracle。

## 决策 1：新增 MIR —— 它是真 IR，不是「摊平的 OIR」

上一稿说 SEXPR 是「把 OIR 摊平成定长记录数组」。方向错了：那只服务解释器。
MIR 要同时喂原生代码生成、SPIR-V 和 C，所以它必须携带下游需要而 OIR 没有的信息：

- **显式类型，含向量**：标量（`i8..i64`、`f32`/`f64`、`bool`）、`vec(T, N)`、
  `ptr(T, addrspace)`、聚合。`omni_dyn` 在 MIR 里就是一个 16 字节的聚合类型，
  不是特例 —— 于是 JS 域和 Omni 域降到同一份 IR，后端只认 MIR。
- **SSA**：每个值定义一次。寄存器分配、向量合法化、公共子表达式都需要它。
  OIR 是带作用域的语句树，做不了这些。
- **结构化终结子**（见决策 2）。
- **每条指令带类型**，不做隐式转换 —— 转换是显式指令。

OIR 保持不动。`hir/` 与现有两个后端零改动，MIR 是新增的一层：`OIR → MIR → 各后端`。

## 决策 2：结构化控制流保留到后端内部才拆

三个消费方都要结构：SPIR-V 要 merge 块，wasm 要块结构，闭包解释器要树。
只有原生代码生成想要平的跳转表。所以 **MIR 保留结构化控制流，拉平只发生在原生后端
内部**，不进 IR。

这不是新增约束，是别在中途丢掉它：OIR 现在就是结构化的（`If` / `While` / `For` /
`Block` / `Break` / `Continue`，没有 goto）。上一稿倾向的「字节码 + 计算 goto」
恰恰会把它丢掉 —— 那条路一旦走了，GPU 后端就再也接不上。这是否决字节码路线的
真正理由，比「少一层机制」有力得多。

## 决策 3：编译单元 = 函数，按内容哈希寻址；链接我们自己做

这是增量的答案，也是本 ADR 最实质的一条。

- **每个函数一个哈希** = `hash(它的 MIR 字节 + 它调用的那些函数的**签名**哈希)`。
  是签名，不是函数体 —— 所以改一个被调用者的实现**不会**让调用者失效。
- **内联是显式依赖**：内联了谁，就把谁的体哈希记进这个函数的依赖集。只有内联过的
  情况才连带失效。tier 1 不做跨函数内联，于是 tier 1 的失效集恒为「改动的函数本身」。
- **缓存条目** = 机器码块 + 重定位表 + 元数据，按哈希存盘。改一个函数 →
  一次未命中 → 重编一个函数（微秒到毫秒）→ 回填它在代码映像里的入口。
- **同一份缓存同时服务 JIT 与 AOT**：JIT 填的是内存映像，AOT 填的是我们自己写出的
  最终映像。两条路共用缓存，所以「跑过一遍再构建」几乎是免费的。

**不能用外部链接器**，理由和不能用 C 是同一个：链接是全程序步骤。Go 的快不是
「编译器快」，是「按包增量 + 自有链接器」；这两条我们都得自己有。这也意味着
产物格式要自己定（Mach-O / ELF 的最小可执行子集），这是决策 6 tier 2 的一部分成本。

## 决策 4：向量是 MIR 的一等类型，SIMD 靠目标合法化 pass

- 类型 `vec(T, N)`，N 任意；向量运算就是 MIR 指令，不是 intrinsic 调用。
- **每个目标一个合法化 pass**：`vec(f32,8)` 在 NEON 上拆成两条 `vec(f32,4)`；
  在 AVX2 上原样；在 C 备选路径上标量化成循环。合法化是 IR 级的 pass，
  这正是「必须有自己的 IR」的具体原因之一 —— 挂在 C 发射器上做不到。
- 真正的 SIMD 收益要求向量值能**跨指令留在向量寄存器里**。copy-patch 一层做不到
  （桩之间不做寄存器分配），所以 **SIMD 是 tier 2 的功能，不是 tier 1 的**。
  这一条要写在验收门槛里，避免以后拿 tier 1 的数字自欺。

语言表层怎么写 `vec<f32, 4>`（字面量、swizzle、与 list 的关系）属于 ADR-0006 的地盘，
另开一条，不在这里定。

## 决策 5：SPIR-V / GLSL 是一等后端，它的约束反过来钉住 MIR

不是「以后再说」，而是现在就把约束写进 IR 的形状，否则以后接不上：

- **`kernel` / `shader` 函数属性 + 一个验证 pass**：递归、函数指针、任意指针算术、
  动态分配、异常在这类函数里**编译期报错**，不是生成出来跑不了。错误信息落在源码
  span 上（ADR-0013 说的那套编译期诊断）。
- **地址空间进类型**：`ptr(T, addrspace)`。CPU 上恒为 0，零成本；GPU 上区分
  buffer / uniform / workgroup / private。
- **uniform 与 varying 作为参数属性**，入口点签名显式。
- 输出两种形态：SPIR-V 二进制（计算与 Vulkan）与 GLSL 文本（兼容旧管线）。
  GLSL 文本后端和 C 后端共享「结构化控制流 → 源码」的那套发射逻辑。

## 决策 6：原生代码生成分两层，各有明确目标

- **tier 1：copy-patch**。桩由我们自己的 C 后端在构建期生成：每个 MIR 指令的语义写成
  一个小 C 函数，构建期编一遍，从目标文件里抠出机器码与重定位点做成桩表。
  运行期只 `memcpy` 加回填。**目标是延迟** —— 编一个函数是微秒级，这是 REPL、
  `run`、以及决策 3 的增量循环要的东西。这一层不写汇编器、不写寄存器分配、
  不写 ABI 分类。
- **tier 2：自有发射器 + SSA 上的线性扫描寄存器分配**。**目标是吞吐**，
  也是 SIMD 唯一能真正兑现的地方，以及自有产物格式的落点。
- **老实说代价**：tier 2 就是写机器码发射器。按 tinycc 的量级，每目标约 2.3k 行
  加约 350 行 ABI 实参分类（`x86_64-gen.c` 2313 行、`arm64-gen.c` 2209 行）。
  copy-patch 买的是时间，不是免票。先 arm64 一个目标，x86-64 随后。

## 决策 7：解释器 = 闭包编译，跑在 MIR 上，兼作差分 oracle

保留早先那稿的两条，只是底座换成 MIR：

- **闭包编译**：装载期把每个 MIR 指令编译成一个函数值（ADR-0013 决策 3 的闭包记录，
  第一个字段是 `omni_fnptr fp`），执行是 `n->fp(n, frame)`。分派只付一次。
- **调用帧是值栈上的窗口**：实参写在槽位里，读形参是一次数组访问，不再每次调用
  分配一条 `omni_list`。帧布局照 Cyber（固定槽 0..4，实参从槽 5 起）。

它的第二个身份更重要：**所有后端的正确性都对着它比**。解释器是唯一不涉及机器码的
执行路径，所以它是 oracle。

## 决策 8：LLVM 出局 —— 这次有实测，不是偏好

- 生成的 C 在 clang 上：`-O0` **2.51s** / `-O1` **18.13s** / `-O2` **21.13s**。
  `-ftime-report` 的分布是**平的**：AArch64 指令选择 21.7%、InstCombine 8.8%、
  Inliner 6.3%、Greedy 寄存器分配 5.4%、SROA 4.2%、DSE 3.5%。前端（parse + sema +
  IRGen）只占 2.5s。**那 19 秒就是 LLVM 自己的 pass 管线。**
- ORC JIT 跑同一批 pass、同一份 IR，进程内只省掉约 0.2s 的进程启动与文件 I/O。
  要它快只能把管线降到 -O0，那就等于 clang -O0 的 2.5s —— 同时背上几百 MB 的 C++
  依赖，并丢掉「运行期不需要 cc」。用 LLVM 换 LLVM，什么也没换到。
- **LLVM 也不解决增量**：它的编译单元是 module；ORC 的惰性是按符号触发，
  不是按内容寻址的缓存。决策 3 那套函数级内容哈希在 LLVM 上得自己另建一遍。
- SIMD 与 GPU 上 LLVM 确实有东西（向量类型、SPIR-V 后端），但那是拿整个依赖换的，
  而合法化 pass 与 SPIR-V 发射本身并不难 —— 难的是我们自己 IR 的设计，那部分
  无论如何都得做。

## 决策 9：tcc 是止血，明确标为过渡

接上 tcc（`cli.js:108` 的搜索顺序本来就是 tcc 优先，只是没装），因为它把自举链从
约 50s 变成 1.8s，而 MIR 那一大摊活期间需要这个循环转得动。实测：tcc 编出来的编译器
`emit-c` 与 C0 逐字节相同，`emit-js` 与 node 逐字节相同。

但它**不解决增量、不做 SIMD、没有 GPU**，编出来的码慢 5.8 倍。它是过渡期的止血，
不进架构。

## 验收门槛

分四步，每步都有可测的门槛，且都不许放宽既有的逐字节比对：

1. **MIR 落地**：`OIR → MIR` 是纯函数，进快照轴；MIR 上的验证 pass 拒绝所有
   非法形状。闭包解释器跑在 MIR 上，`js-exec` 从四方扩到五方逐字节相同。
2. **增量**：改一个函数体，重编只发生在那一个函数上（用缓存命中/未命中计数断言，
   不是靠计时）。全量冷构建时间不回退。
3. **tier 1 JIT**：六方比对；同一进程内解释与 JIT 混合执行（同一函数在阈值前后
   各跑一遍）结果一致；单函数 JIT 延迟有上界断言。
4. **tier 2 + SIMD**：向量合法化在 NEON / AVX2 / 标量三条路上结果逐位相同
   （浮点要按 IEEE 语义固定求值顺序，不许用 fast-math）；SIMD 加速比对着 tier 1
   有下界断言。
5. **GPU**：`kernel` 的 SPIR-V 输出与 CPU 上同一份 MIR 的执行结果一致（有 GPU 时跑，
   没有则只验证 SPIR-V 通过官方 validator）。

## 借鉴与对照

三份本地快照量过，行号是这些快照里的。**wasm / SPIR-V / SBCL / Chez 本地没有源码
快照**，引用的是其公开规范或做法（结构化控制流要求、类型驱动特化、编译成闭包），
落地前需各自找一份核对。

- **Cyber**（`reference/cyber`）：它的 "JIT" 不是分层 JIT，是构建期 `CL_JIT` 选中的
  整程序 copy-patch 后端，与解释器不共存 —— 没有 OSR、没有计数器、没有 deopt。
  可抄的是 copy-patch **形态**与**帧布局**（`src/vm.h:203` 的 `CALL_ARG_START 5`，
  `CallInfo` 打包进一个 `Value`：`src/fiber.zig:543..559`）。它的值是 8 字节
  NaN boxing（`src/value.zig:44..56`），我们不抄 —— 16 字节 `omni_dyn` 按值传是
  ADR-0013 决策 3 的 C-FFI 前提。ARC 为主 + 只对可能成环的对象标记清扫
  （`src/arc.zig:222..241`），根靠编译期 unwind 表走栈找（`:329..355`），
  **没有 write barrier、没有 handle scope** —— 印证了非移动式收集器 + 编译期元数据
  这条路。
- **TinyCC**（`reference/tinycc`）：证明了 tier 2 的量级下限。发射原语是 `g()`/`o()`
  （`x86_64-gen.c:172..190`；arm64 上直接写 32 位指令字，`arm64-gen.c:115..124`）。
  寄存器分配只有 38 行（`tccgen.c:1489..1527`），拿值栈当占用表线性扫。
  前向跳转把待回填位移串成链表、链表就存在代码缓冲区那些还没填的字段里 —— 零额外
  分配，桩间跳转正好用这个。它的内存内执行骑在一整个 ELF 链接器上（`tccelf.c` 4116 行），
  这部分我们不要：决策 3 要的是自己的重定位表，不是目标文件。
- **Jancy**（`reference/jancy`）：ORC 集成本身只 345 行（`jnc_ct_OrcJit.cpp` 266 +
  头 79），但代价在别处 —— `createBareJITDylib` 不挂进程符号解析，于是 `memset` /
  `memcpy` / `__divdi3` 每个 libcall 都要手工登记（`jnc_ct_Jit.cpp:94..143`）；
  十六个手写调用约定类在 IR 层重做 sret/byval/coerce（`jnc_ct_CallConv.h:27..44`），
  这块比 JIT 集成重得多；还要 `setOpaquePointers(false)` 背上游债
  （`jnc_ct_Module.cpp:201..211`）。**可抄的一条**：JIT 回调宿主用「显式注册的
  字符串→函数指针哈希表」（`jnc_ct_Jit.h:26..28`，查表 `jnc_ct_Jit.cpp:74..92`）。
  我们的桩重定位需要同一张表，但可以在构建期从 `JS_ALL` 生成，不需要运行期注册。

## 后果与代价

- **要写机器码发射器**。这是本 ADR 最大的一笔。copy-patch 把它推后，但推不掉：
  SIMD 和自有产物格式都压在 tier 2 上。先 arm64。
- **要写产物格式**。不能用外部链接器（决策 3），所以最终映像要自己写。
  先只支持「可执行文件」，不做动态库、不做调试信息（后者用 sideband 元数据补）。
- **语义仍然只有一份**。MIR 的各后端不重新实现语义，它们发的仍然是对 `omni_js_*`
  的调用（ADR-0013 决策 5 原样成立）。所以后端多了不会增加语义分叉点，只会增加
  执行机制的 bug —— 而那种 bug 逐字节比对当场抓。
- **C 后端不删**。它是 oracle、是新目标的兜底、是产物可读性。但它不再决定架构，
  也不再是性能路径。
- **arena 回收要单独一条 ADR**。当前解释器在整个自编译上被 OOM 杀掉；决策 7 的值栈
  只解决「每次调用一条 list」，堆本身的回收策略是独立问题。

## 附录：实测数据（M 系列 macOS，本机）

生成的自编译器 C：3831922 字节 / 61483 行 / 单 TU。

编译这份 C（含运行时 14 个 .c）与编出来的编译器跑 `link + lower cli.js` 的耗时：

- clang `-O2`：编 24.6s，跑 0.86s
- clang `-O0`：编 3.5s，跑 2.39s
- tcc（本地快照 0.9.28rc，现编）：编 **0.41s**，跑 4.97s

走完整 CLI 的端到端全量自构建：tcc 冷启动 1.80s（前端 200ms + 降级 170ms +
发 C 146ms + 运行时 .o 660ms + 代码生成链接 298ms），热启动 0.99s。
正确性：tcc 编出来的编译器 `emit-c cli.js` 与 C0 逐字节相同。

这些数字说明的是「C 路径的上限在哪」，不是「架构该怎么定」—— 见背景。
