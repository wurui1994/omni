# ADR-0034：`.y` 直接收（bison/yacc 与我们那份混合方言）

## 决定

**`.y` 转成 `(grammar …)` 文本，再走同一条路。** 不新开解析器、不新开构表器：
`src/core/glr/yacc.js` 只做「一份 `.y` -> 一段 `.grammar` 正文」，往下仍然是
`readSexpr -> readGrammar -> buildTable`（`src/core/glr/load.js:34` 那一格）。

三条后果，都是**要**的：

- 语法的语义（终结符 / 优先级级序 / `%prec` / 空产生式 / 起始符号）只有 `glr/grammar.js`
  那一份说法。`.y` 这一支不可能与 `.grammar` 那一支走散 —— 它们不是两条路。
- 构表的内容寻址缓存照旧生效，键是**转出来的**那段文本：`.y` 改一个字符键就变，
  转换器改了口径文本也变。
- 中间那段文本是人能读、能 diff、能进快照的。这就是这一格唯一诚实的判据
  （`tests/glr/run.js` 第 5 节）。

## 为什么现在做这件事

`target.md` 要问的是「特性原子化 / 组合 / 分层 / 特性 DAG / 可删除性」。那些问题的前提是
**手上先有一批真语法**：参考树里躺着 go / vlang / nim / mojo / freebasic / sbcl / chez / c++
八棵源码树，而它们的语法多半已经写成 `.y` 或与 `.y` 一对一的形状。

如果每加一门语言都要先手抄一遍语法，那么「加一门语言 = 一份语法 + 一份映射标注」这句话
是假的 —— 手抄一遍就是手抄一遍的错，而那种错的症状是"某一份源码少了一个 token"，
没有根因可查。所以这一步排在特性代数（ADR-0033）之前：先把**别人已经写对的那一半**收进来。

## 收两种方言，同一个读入器

| | 真 bison | 混合 `.y`（我们早期半成品定下的） |
| --- | --- | --- |
| 词法 | 在 `.l` 里 | `%skip NAME 正则` / `%lex NAME 正则` 就写在同一份文件里 |
| 动作 | C 代码 | `{ 标签 }` |
| 转出来的语法 | **没有** `(lex …)`：能建表、能吃现成的 token 表 | 带 `(lex …)`，当场能吃源文本 |

认得的指令：`%{ … %}`、`%union`、`%token` / `%term`（含 `<标签>`、记号编号、`"别名"`、
`_("i18n 别名")`）、`%type` / `%nterm`、`%left` / `%right` / `%nonassoc` / `%precedence`、
`%start`、`%prec`、`%dprec`（落成我们的 `(prefer N)`）、`%merge`、`%empty`、`%expect` /
`%expect-rr`、`%define`、`%code` / `%destructor` / `%printer` / `%param`（含一条上挂几段
`{…}`）、`%glr-parser` 与那一批只影响生成代码的开关、字符字面量 `'+'`、命名引用 `exp[left]`、
中段动作、`;` 省掉的候选式、第二个 `%%` 之后的尾声。**不认识的 `%foo` 当场报错**，不跳过。

## 三处定义（不是猜）

1. **动作只留名字，不解释语义。** `{ append }` 出 `(append $1 $2 …)`；C 代码那种整段丢掉，
   标签取产生式左部的名字。于是转出来的树是一棵**具体语法树**：一条产生式一个节点、
   子节点按 RHS 位置排。
   理由：`.y` 里那段 C 代码说的是**别人的** AST（asymptote 的 `ASTNode*`、mini.y 的
   Chevrotain 形状）。照搬过来等于把别人的数据结构搬进来，而「映射标注」那一层本来就是
   我们自己要定的东西 —— ADR-0031 的契约在那一层，不在这一层。
2. **正则里的 `^` 与 `$` 是普通字符。** 词法器永远从一个记号边界起扫，行首/行尾锚点在这里
   没有意义（`%lex XOR_ASSIGN ^=` 要的就是那个尖角）。
3. **`word\b` 落成一条 `(punct …)`，`\b` 不另外实现。** 我们的词法器是「最长匹配优先、
   同长则声明在前的赢」（`glr/lex.js`），于是 `in` 与 `index` 之争由长度定胜负 —— 与 `\b` 同解。
   前提是这门语言有一条吃得下整个标识符的规则；没有那条规则的话 `index` 本来也扫不出来。

## 正则的子集是刻意小的

封闭 ABI 里没有 `new RegExp(str)`（ADR-0011 决策 2），模式必须在**转换期**折成 `glr/lex.js`
那套词法项。收：字面量与转义、`.`、`[…]` / `[^…]`（范围会尽量折成 `alpha` / `alnum` / `hex` /
`digit` 这些类名，折不动才摊成字符集）、`\s` `\d` `\w`、`(…)` / `(?:…)`、`|`、`* + ?`。
另收一个形状：`前缀 [任何]*? 后缀` 认成 `(block-comment 开 关)` —— 非贪心是我们那个
贪心不回溯的匹配器唯一表达不了的东西，而"扫到第一个后缀为止"正好就是块注释。

**别的一律当场报错**：`{n,m}`、`(?=…)`、反向引用、`\B`、字符类里的 `\S` / `\D` / `\W`、
块注释以外的非贪心。折成一个"近似"的模式才是真正的坑 —— 那种错会在某一门语言的
某一份源码上突然表现成"少一个 token"。

## 量到的覆盖

- 本机 `~/Documents/Lang` 下的 **11 份 `.y` 全部转出并建表**：`mini.y`（213 状态）、
  `omni.y` / `omni_noat.y` / `docs/omni.y`（544 状态，118 终结符 90 非终结符 280 条产生式）、
  `omni_blob.y`（574）、`omni_block.y`（377）、`omni_dict.y`（133）、`expr.y`（17，零冲突）、
  asymptote 的 `parser.y`（426 状态，215 条产生式，46 处冲突交给 GLR 驱动）。
- bison 自带 examples 的 **10 份全部转出**（c / c++ / d 三档，含 `%glr-parser` 那一份
  `c++-types.y`、`%param {a}{b}` 那一份 `reccalc/parse.y`、`_("…")` 那一份 `bistromathic`、
  嵌套 `<::std::vector<std::string>>` 那一份 `variant.yy`）。
- 端到端：`omni glr parse mini.y prog.txt` 与 `omni glr parse omni.y prog.txt` 当场出树。

## 门槛（`tests/glr/run.js` 第 5 节）

`tests/glr/y/` 三份夹具，一条比一条硬：

- `ymini.y`（混合方言）：转出来的文本进快照；表建得出来且第二遍**命中同一格缓存**；
  跑 `ymini.cases` —— 与第 2 节**同一个函数**（`caseFailures`），判据只有一处说法。
- `ycalc.y`（真 bison）：同上两条，第三条反过来 —— 它没有词法段，`glr parse` 必须
  **明说**这件事。那不是失败，那是这一支该有的样子。
- `ybad.y`：正则里写了 `{n,m}`，转换必须当场报"不支持"，退出码非零。

## 这一条**没有**决定什么

- 没有决定 CST 怎么变成某门语言的 AST。那是「映射标注」那一层（ADR-0029 / ADR-0031）。
- 没有决定特性原子化、特性 DAG、可删除性（ADR-0033 在谈）。`.y` 只是把语法这一半的
  输入成本降到零，让那些问题能在**一批真语法**上问，而不是在自己挑的片段上问。
- 没有碰 `.grammar` 的形状。手写语法仍然是首选：`(lex …)` 那套字符类原语比正则表达得清楚，
  而 `.y` 这条路是给**别人已经写好的**那些文件用的。
