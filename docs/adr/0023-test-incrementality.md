# ADR-0023：测试系统的增量、依赖图与日志

状态：进行中（S1 已落，S2/S3 在做）

## 背景：量出来的浪费

这套东西有 21 条测试轴，一趟 `test:all` 23 分钟。拆开看，钱花在哪儿是清楚的：

- 一条 jnc 轴有 157 条判据，每条判据在**六条腿**上各跑一次 —— 一趟 **570 次子进程**，每次
  `node src/core/cli.js …` 都把整份编译器（十来兆 JS、几百个 ESM 模块）重新装一遍。
- 最贵的几条：asy 374s、bootstrap/run 325s、js-exec 214s、jnc 124s、js-roundtrip 62s。
- 而真实的一次改动只碰一两个文件（一个前端、一个后端），**很多时候只是加了一份固件**。
  可是每次都全量重跑：同一份编译器被装载了几千遍，算出来的答案与上一趟一个字节都不差。
- 更糟的是**没有日志**：输出只在终端里。`tail` 看不够就再跑一遍换 `head` —— 一次"看清楚
  上一趟到底报了什么"的代价，是上面那些分钟。

这不是"某条轴慢"，是**机制缺了三样**：内容寻址的缓存、真实的依赖图、可回读的日志。

## 决策

### 1. 子进程级缓存（内容寻址）

贵的那一步是子进程，而它是个**纯函数**：给定命令行、给定读进去的文件、给定装载的那些模块，
输出的 `{code, stdout, stderr}` 是确定的。所以把它缓存起来：

```
键 = sha256(命令行 + cwd + 实参里那几份文件的内容哈希)
值 = { deps: [装载过的模块路径…], depsHash, code, out, err }
```

查的时候先按键找到记录，再**把记录里那份模块清单重新哈希一遍**：对得上才算命中。这一步解开了
"要先知道依赖才能查、可依赖是跑完才知道"这个环 —— 键里只放跑之前就有的东西，依赖放在值里当
**校验**。

落点：`.omni-cache/test/verdict/<轴>.json`。

### 2. 依赖不是猜的：用装载钩子收

`node --import tests/lib/deps-hook.mjs …` 在子进程里注册一格 `module.registerHooks`
（Node 22.15+ 的**同线程**钩子，开销近零），把 `load` 过的 `file:` 模块路径写成清单。于是：

- 改 `frontend-jnc/lower.js` 只让**装过它**的用例失效（jnc、glr 那些），别的轴一格不动；
- 只加一份固件时，别的用例全命中；
- 依赖集是**观测出来的**，不是按 import 静态图猜的 —— 懒加载（`cap()` 那一套）之后静态图与
  真实装载差得很远，猜出来的图会漏。

### 3. 轴级跳过

`tests/all.js` 在派子进程之前先算这条轴的**指纹**：轴目录（固件 + 那份 run.js）的内容，加上
该轴依赖集里每份模块的内容。与"上一趟**绿**"的指纹一致就整轴跳过，并把上一趟的日志路径印出来。

红的轴**不入册** —— 下一趟照旧重跑。绿了才记指纹，这条规矩保证"跳过"只会跳过已经绿过的东西。

### 4. 日志：每一趟都留下来

每条轴的完整输出落 `.omni-cache/test/log/<轴>.log`（上一趟挪成 `<轴>.prev.log`）。要看细节就读
文件，不再"为了看清楚而重跑一遍"。跳过的轴把上一趟那份日志指出来。

### 5. 钩子收不到的那一格：数据文件

`imports/`、`incdirs/`、`.grammar`、`.tab`、`.expected` 这些是**数据**不是模块，装载钩子看不见
它们。三条办法叠着用：

- 命令行里出现的路径自动进键（`inputsOf`：实参里凡是存在的文件/目录都哈希）；
- 命令行上看不见的（57 那条 `import` 进来的兄弟文件、`mod_*.asy`、用例旁边的 `.h`），由轴
  **显式登记** `extra`；
- 编译器自己要读的那一批数据（语法表、内建绑定表、`lib/`、`runtime/`、`jit/`）**不另立一张表**：
  `src/core/plugin-set.js` 里每格插件的 `data` 与 `CORE_DATA` 就是那张表（它本来的用途是
  `omni plugins` 往 `dist/share/` 抄哪些东西）。`incr.js` 把它们整份哈希成一格指纹，混进
  **每一个**键与每一条轴的指纹里。保守（改 `runtime/omni.h` 让所有轴失效 —— 而那是对的，每条
  C 腿都读它），整趟只算一次。

规矩写在这儿：**新加一类数据目录，就要在那条轴的 `extra` 里登记一格**（或者，如果它属于编译器
自己的数据，加进 `plugin-set.js` 那张表 —— 那本来就是必须做的事）。漏登记的后果是"改了数据却
命中旧结果"，所以这一条不是可选的。

还剩一处量不到：**系统头**（macOS SDK 里的 `stdio.h` 一族）不在任何一格输入里，tests/c 的
`sys/` 那组因此会在换 SDK 之后拿旧结果。判断是：换 SDK 是件大事，那时 `FORCE=1` 跑一遍。

### 6. 不进这一层的

- 靠时间 / 随机 / 环境的用例 —— 它们本来也不该在"六条腿逐字节相同"的轴上；
- 有**外部副作用**的步骤：`bootstrap/run.js` 会往 `dist/` 写整套产物、`glsl` 会落图片、
  `c-obj`/`link` 会落 `.o` 与可执行文件、`omni incr --cache` 的整件事就是那份缓存。
  **凡是"产物是磁盘上的文件"的命令都不许进**：缓存会把副作用一起跳过去，下一步就找不到文件。
  那种轴只做**轴级跳过**；
- **判据本身是"第二次调用与第一次不同"的那些**。tests/glr 的 1b 节跑同一条
  `glr-table --brief --verbose` 两遍，要求第二遍报 `cache hit`（测的是编译器自己的构表缓存）。
  走这一层的话两遍的键一模一样，第二遍会把第一遍的 stderr 交回来，于是这一节永远红 —— 所以那
  两遍走原始 `spawn`（`tests/glr/run.js` 的 `runRaw`）；
- **超时的那一次不入册**。超时不是这份输入的"结果"，是这台机器这一刻的状态（别的轴在并行、机器
  在换页）。记下来就把一次偶然的卡顿钉成永久的红。`RunCache.run/spawnAsync` 收 `timeout`，
  超时回 `{code: 124, timedOut: true}` 并**跳过写盘**（tests/asy 的 30s 上限走这条）。

### 7. 开关

- `FORCE=1`：全部重跑（缓存照旧更新）；
- `NOCACHE=1`：完全不读不写；
- 缓存目录跟着 `OMNI_CACHE_DIR`（与编译器那边同一个含义）。

## 分步与判据

- **S1 子进程缓存 + 依赖钩子**（已落）。判据：jnc 轴二次跑 `子进程 570 次：命中 570、真跑 0`，
  157 passed 不变。
- **S2 日志 tee + 轴级跳过**（已落）。判据：什么都不改时 `node tests/all.js jnc` 印
  `skip 输入没变、上一趟绿`，**0.3s** 走完；日志留在 `.omni-cache/test/log/jnc.log`。
- **S4 轴内并行预热**（已落）。判据：`FORCE=1 JOBS=6` 冷跑 jnc **35.2s**（原来顺序 100-124s），
  157 passed 不变 —— 六路并行没有撞出假红。
- **S3 把 RunCache 接到别的轴**（在做）。已接四条，判据都是"二次跑命中率 100%、passed 数不变"：
  - **asy**：`子进程 458 次：命中 458、真跑 0`，263 passed。冷跑 **374s → 183s**（并行预热），
    二次跑 **11.1s** —— 剩下那 11s 是判分的**真 asy**，外部工具，不进缓存。
  - **sexpr**：`260 次：命中 260`，83 passed。**17.3s → 0.12s**。
  - **c**：`177 次：命中 177`，103 passed（这台机器没建 tcc，191 条 skip —— 所以这条轴只量到了
    不靠 tcc 的那一半）。**28.7s → 0.14s**。
  - **glr**：6.9s → **1.7s**。剩下的 1.7s 是 1b 节那 20 次**故意不缓存**的调用（见 §6）。
  剩下的那些是**故意不接**的一类居多，理由记在 §6：`llvm`/`jit`/`mir`/`js-exec`/`js262` 的贵步
  是外部工具（clang / qjs / node 跑生成出来的 .mjs）与**落文件**的那几步（`.ll`、`.o`、可执行
  文件），缓存它们等于把副作用跳过去；`incr` 那条轴测的就是编译器自己的缓存；`bootstrap` 往
  `dist/` 写整套产物。这几条只靠**轴级跳过**（S2）拿收益。
- **S5 整体判据**：什么都不改的一趟 `test:all` ≤ 30s（现在 23 分钟）；只改一处前端时只重跑受
  影响的轴；任何一趟的完整输出都能从日志回读。

### 量出来的两条教训（都踩过）

1. **`spawnSync` 不能用在并行的 worker 里**：它把整条事件循环堵住，几条 worker 于是一条接一条
   地跑。第一次这么写，冷跑从 100s 变成 197s（还慢了一倍 —— 因为 `FORCE=1` 让预热与顺序判定
   各跑了一遍）。现在预热走异步 `spawn`，`FORCE=1` 只越过"上一趟留下的"记录、认这一趟自己写
   进去的（`fresh` 那一格）。
2. **依赖集有多胖，决定了增量有多值**。量出来：jnc 轴 569 条记录，依赖并集 **112 个模块**，
   而**每一条记录的依赖都是同一份 112 个** —— 因为 `cli.js` 把语言/后端那张表整张装进来
   （里头有 10 个 asy 前端的文件、glsl、wat、spirv…）。所以：
   - 只改固件 → 精确命中（这是日常最常见的一种，也是这一层最大的收益）；
   - 改任何一份 `src/core/` 里的源码 → 几乎每条轴都得重跑。这不是机制的错，是**核心太胖**：
     真要让"改一个前端只重跑一条轴"，得先有 ADR-0021 那个薄核心（前端/后端按需装）。
     在那之前，源码改动的那一头靠 S4 的并行（35s）与 S3 的覆盖面顶着。


## 代价

- 缓存说谎的两种可能，都记在明处：输入没进键（靠 §5 那条规矩）、用例本身不确定（靠 §6 那条
  边界）。两种都会表现成"明明改了却还是绿" —— 所以 `FORCE=1` 必须一直好用，而且发版前那一趟
  该用它。
- 磁盘：一条轴几百条记录的 out/err 文本，jnc 那条约 1MB 量级。`.omni-cache/` 本来就在
  `.gitignore` 里。
- 多了两份基础设施（`tests/lib/incr.js`、`tests/lib/deps-hook.mjs`）与每条轴几行接线。
