# ADR-0043: 从图到 IR——第三次中间表示转向

## 0. 三次转向

这个项目在中间表示上做了三次选择，每次都有量出来的理由，每次都碰了墙。
这份文档先说清三次的经过与失败原因，再说为什么引入 IR 和逆向能力。

### 第一次：核心方言 sexpr + OIR/MIR（commit 1c648518 → 09ffc758）

**做了什么。** 项目从 stage0 自举开始，中间表示是一门 S 表达式核心方言
（`src/core/sexpr/`），降到 OIR（结构化控制流 + 操作码），再降到 MIR
（SSA + 槽位 + 8 字节指令）。后端有五条腿：sexpr 解释器、JS 降级、
C 代码生成、LLVM IR 文本、WAT。自举闭环走通（C0→C1→C2 不动点）。

**碰了什么墙。** 这套 IR 是为 omni 自己的语言设计的。当十门外部语言
（go/lua/nim/vlang/cpp/awk/chez/sbcl/mojo/freebasic）接进来时，
每门语言要先降成核心方言文本，再 parse 回 OIR。这条路有三笔不可接受的账
（`node-graph-contract.md` §5.2）：

1. **文本没有端口。** 拼出来的 `(let $f7 (call f))` 里，"这一格是借还是夺"
   没地方写。释放点只能靠约定。
2. **文本要被解析回来。** 降级写文本、后端读文本，中间那次 parse 是纯损耗，
   且它会默默接受图上不合法的东西。
3. **文本没法做接口检查。** 子图替换前后端口逐格对上——对文本能对的只有字符串相等。

**根因。** 核心方言是一门**具体语言**，它有自己的类型系统、自己的关键字、
自己的语义约束。十门外部语言降到它，等于要做十次**跨语言翻译**。
而这十门语言的类型系统、内存模型、并发模型各不相同——把它们全塞进一门方言，
那门方言要么膨胀到不可维护，要么丢信息。

### 第二次：28 格节点图（commit 5166b503 → 225623fe）

**做了什么。** 引入节点图（`src/core/graph/`）：28 种节点，五栏声明
（sort/ins/outs/effects/lifetime），四种边（value/effect/bind/region），
四条后端腿（eval/js/c/wat/core）。十门语言各一份 `tograph.js`。
映射层的公共零件（`fromtree.js`）九门共用。eval.js 是默认解释器。
contract.js 回答后端的五问。

图的设计原则是对的：节点从十门规格里量出来（不是设计出来的），五栏声明
是可检查的，合并判据是"五栏逐格相同"。go 编译器 52/52 包的 tograph 走通了。
lua 上验证了两层变换模型（mapping + rewrite）。

**碰了什么墙。**

1. **复杂度是乘法级的。** 28 格节点 × 十门语言 × 四条后端 × 两层变换。
   每加一个特性（并发、错误处理、类型），四条后端腿都要各自实现一遍。
   go 的 `tograph.js` 膨胀到 1917 行 switch-case，反复尝试用 mapping DSL
   降低复杂度但始终无法收敛到足够简洁的模型。

2. **并发从未从纸面进入代码。** `node-graph-contract.md` §7 设计了三层模型
   （suspends → spawn/join → channel），但实际代码里一行都没有。
   nodes.js 的效应栏声明了 `suspends` / `synchronizes`，没有任何节点使用。
   go-rt.js 的 `__goSpawn(fn)` 是 `fn()`——同步调用。

3. **类型层一直是 pending。** 图上没有类型，但四条后端腿都需要类型信息。
   types.js 是推导器，不是声明式的覆盖层。task #40（typed overlay）
   从创建起就没有推进。

4. **错误处理缺失。** 28 格里没有 try/catch/throw。go 的 panic 降成
   `prim print`，recover 完全没接。JS 降级阶段做了 throw/try/catch
   （OIR 层），但图层没有。

5. **图与 OIR 之间的桥是脆弱的。** `backend-core.js` 把图降到核心方言再进
   OIR，但这条桥要推类型（图上没有，core 有），推类型的代码散在
   types.js/contract.js 里，不是形式化的。

6. **闭包捕获没有显式化。** func 节点没有 captures 栏。eval.js 靠 JS 宿主
   的闭包兜着，c 后端需要显式捕获列表但是从 types.js 推的。

**根因。** 图的抽象级别太高。28 格节点试图覆盖从 Scheme 的 datum 到 C++ 的
RAII 的全部语义，但它没有类型、没有内存模型、没有并发原语——这些东西
要么在图上方（各门语言的 tograph.js 里手写），要么在图下方（各条后端腿里
手写）。图成了一层**不够厚的中间层**：上面够不着语言的语义，下面够不着
机器的能力。

每次试图在图上加一个特性（并发/类型/错误），都面临同一个问题：
图没有足够的结构来表达它，于是要么在 tograph.js 里堆 if-else（上移复杂度），
要么在后端里堆特例（下移复杂度）。两头堆，两头失控。

### 第三次：IR（本文档）

从两次失败里提取的教训：

- **核心方言的问题是"太具体"**——它是一门语言，外部语言要翻译成它。
- **节点图的问题是"太抽象"**——它没有类型和内存模型，一切都要在别处补。
- **两者的共同问题是"没有分层"**——一层试图解决所有问题。

IR 的方向：**多层、有类型、可扩展**。不是一层 IR，是一串 IR，每层解决一类问题，
层与层之间的 lowering 是形式化的。这正是 MLIR 的核心思想。

## 1. 为什么引入 IR

### 1.1 MLIR 的方向

MLIR（Multi-Level IR）的核心不是某个具体的 IR 格式，是**方言机制**：

- 每个方言定义自己的操作（operation）、类型（type）、属性（attribute）
- 方言之间的 lowering 是一串 pass，每个 pass 消除一种方言、引入更低级的方言
- 同一个模块里可以混合多个方言层级的操作（progressive lowering）
- 验证器（verifier）保证每层的不变式

对我们的项目，方言的划分大致是：

```
源语言方言（per-language）
  ↓  lowering pass
高级 IR 方言（控制流 / 函数 / 闭包 / 并发 / 错误处理）
  ↓  lowering pass
中级 IR 方言（SSA / 类型化的内存操作 / 结构体布局）
  ↓  lowering pass
低级 IR 方言（寄存器 / 栈帧 / ABI）
  ↓  lowering pass
目标方言（LLVM IR / C / WASM / JS）
```

每一层都有类型。每一层的操作集是有限的、声明式的。层与层之间的 lowering
是可验证的。**这是图那条路缺的东西——分层和类型。**

### 1.2 先走 MLIR，但不一定是最后形态

我们会先用 MLIR 的设计思路（可能直接用 MLIR C++ 基础设施，也可能
参考它实现一个轻量版），原因是**确定性**：MLIR 的 pass 基础设施、
pattern rewrite、方言转换、验证器都是成熟的，不用自己造轮子。

但 MLIR 依赖 LLVM，而我们不可能完全依赖 LLVM：
- 我们有自己的 C 前端和链接器（第九刀的 2501 行 ELF/PE/Mach-O）
- 我们有自己的 MIR（SSA + 8 字节指令）
- 自举链要求不依赖外部 C++ 库
- WASM 和 JS 后端不经过 LLVM

所以最终形态是**我们自己的 IR**，它吸收 MLIR 的分层思想和方言机制，
但实现上是自包含的（JS/C，与自举链一致）。MLIR 是学习和验证阶段的工具，
不是永久依赖。

### 1.3 IR 与现有代码的关系

**保留的：**
- GLR 语法层（十门语言的 grammar + 驱动器）——这是输入，不变
- OIR/MIR——可以作为低级 IR 方言的基础
- C 后端/链接器——目标后端，不变
- eval.js——作为高级 IR 方言的解释器重生

**替换的：**
- 28 格节点图——被高级 IR 方言替代
- tograph.js × 10——被 CST → 高级 IR 的 lowering pass 替代
- backend-core.js（图→core sx）——被 IR 层间 lowering 替代
- types.js 的推导——被 IR 层的类型系统替代

**新增的：**
- IR 的方言定义与验证器
- lowering pass 框架
- 逆向路径（见 §2）

## 2. 为什么引入逆向能力

### 2.1 正向编译只是一半

到目前为止项目只做正向：源码 → IR → 目标。但"程序变换平台"需要双向：

```
正向：  源码 → CST → IR → ... → 目标（ELF/WASM/JS）
逆向：  目标（ELF/WASM） → IR → ... → 源码（C/伪码）
```

逆向能力不是附加功能，它是 IR 设计的**验证器**：如果一个 IR 不能从低级
表示提升回来，说明它丢了信息；如果提升回来的东西不能再降下去得到等价的
目标，说明 lowering 不正确。**正向和逆向是同一套 IR 的两个方向。**

### 2.2 具体的路径

**ELF → LLVM IR（binary lifting）：**
- 解析 ELF 格式（我们的链接器已经有 ELF 读写）
- 反汇编（arm64/x86_64，我们的代码生成器已经有指令编码表）
- 提升到 LLVM IR 或我们的中级 IR（控制流恢复 + 类型推断）
- 参考：retdec、mctoll、remill

**LLVM IR → C 或其他（decompilation）：**
- 从 IR 恢复结构化控制流（递归下降还原）
- 类型推断与变量命名
- 输出可读的 C 代码或其他语言

**ELF → WASM（binary translation）：**
- 从一个目标格式翻译到另一个
- 经过 IR 中转，不是直接翻译指令

### 2.3 IR 到源码的递归下降还原

这是逆向路径的关键技术：从 IR 的控制流图恢复出 if/while/for/switch
等高级结构。算法核心是**结构化分析**（structural analysis）：

1. 识别 IR 控制流图中的区域（region）：循环、分支、序列
2. 递归地把每个区域折叠成高级控制流语句
3. 不可归约的控制流（goto）保留为 goto——不硬凑结构

这与 MLIR 的 region-based IR 天然契合：MLIR 的 `scf` 方言（structured
control flow）的 `scf.if` / `scf.while` / `scf.for` 就是这种还原的
目标形式。

## 3. 路线

### 阶段 A：学习与验证

- 读 mojo/modular 的 MLIR 使用方式，理解方言划分
- 用 MLIR 工具链试跑：C → LLVM IR → MLIR → lowering → LLVM IR → ELF
- 确定我们需要哪些自定义方言

### 阶段 B：高级 IR 方言

- 定义高级方言的操作集（替代 28 格节点图）——有类型、有并发原语、有错误处理
- 写 CST → 高级 IR 的 lowering（先在 lua 上验证，替代 tograph.js）
- 写高级 IR 的解释器（替代 eval.js）
- 判据：lua 的尺子全过（106 一致 / 0 分歧）

### 阶段 C：逆向路径

- ELF 反汇编（复用指令编码表）
- 控制流恢复（结构化分析）
- 提升到中级 IR
- IR → C 的递归下降还原

### 阶段 D：自包含 IR

- 把 MLIR 依赖替换为自己的实现
- 方言定义、pass 框架、验证器用 JS/C 写
- 与自举链对齐

## 4. 不做什么

- **不丢掉 GLR 语法层**——十门语言的语法是量出来的，它是输入端，与 IR 无关
- **不丢掉 C 后端/链接器**——那是目标端，第九刀的 2501 行不重写
- **不丢掉 OIR/MIR**——它们可能成为低级 IR 方言的基础
- **不在图上继续加特性**——并发、错误处理、类型都在 IR 层做，不在图层补
- **不把 MLIR 当永久依赖**——它是学习工具，最终形态是自包含的

## 5. 动态语言那一层：量出来的几条

这一节记的是 lua → MLIR 这条腿上**由基准逼出来的设计决定**（代码在
`src/core/ir/emit-mlir.js` 与 `src/core/ir/lua-rt.h`）。判据一律是
「与 luajit 的输出逐字节相同」+ 墙上时间，例子在 `bench/ir/suite/`
（21 个，横跨数值 / 数据结构 / 算法 / 串 / 闭包 / 对象 / 动态特性七组）。

- **数只有 double，没有 int 那一格**。原来有 32 位 int payload，`1..1e7`
  求和到 5e13 每轮溢出、每轮掉进慢路（61ms 里 53ms 是这么来的）。
- **算子发两条路**：一次 tag 检查选快路（`fadd`）或慢路（调运行时）。
  判据不是"开关收下了"，是汇编里热循环还有没有 `bl _omni_val_*`。
- **类型覆盖层两刀**：块内局部量 + 形参/返回值的乐观不动点。判不出来只是多发
  一次检查，答案不变 —— 这条性质让它可以逐步加强。
- **协程自己切栈，不用 ucontext**。同一个 200k yield 的例子：`swapcontext`
  338ms（每次切换都走一趟 `sigprocmask`），自己切 20 个 callee-saved 寄存器
  7.7ms，**44 倍**。cyber / luajit 的 fiber 也是自己切，理由相同。
- **短串驻留 + 哈希缓存**，长串（>40B）懒散列。字段名那一族（`self.x`）于是
  只读一格数；`btree` 0.35x→0.91x、`list` 0.26x→0.68x。
- **串字面量在模块里只造一次**。原来每处用到都发 `omni_str_new`，`self.x`
  在 20 万次循环里就是 20 万次 malloc（method 那个例子 150ms→47ms）。
- **整数键要能摊进数组部分**（照 lua 的 rehash：找最大的 `2^i` 使 `[1,2^i]`
  里的整数键超过一半）。`for i = 2, N` 的第一个键是 2，没有这一步时两百万个键
  全躺在哈希里 —— sieve 427ms，luajit 21ms。补上之后 41ms。
- **分配走 arena，不走 malloc**。没有 GC，free 一次都用不上，剩下的只有开销：
  `Point.new` 20 万次从 27.9ms 降到 16.1ms。代价是**这一版不回收** —— GC 是
  下一刀，登记表的下标天然是根集。
- **宁可响，不要静默的错答案**。实参个数不符、捕获栈上的量、`...` 用在非变长
  函数里，一律在编译期或运行期报错退出。这一轮里有三个 bug 正是"静默的错答案"：
  `break` 没接（mandel 印 90000）、多重赋值的求值次序（qsort 排不动）、
  重散之后丢写（queens 少数一大半）—— 弱例子一个都抓不到。

剩下的账（与 luajit 比，同机同时段）：多数例子在 0.5x–1.25x，最差的一格是
`method` 0.16x，根已经定位到**每个对象的分配开销**（80ns，luajit ~17ns）
与**元表分派**（48ns/次）两处，不是"动态语言就这样"。
