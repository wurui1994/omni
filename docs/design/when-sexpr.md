# 什么时候该引入一格 s-expr / DSL（以及什么时候不该）

这棵树里 s-expr **已经引入过四次**。每一次都是对的吗？不是。
这一份把判据写下来，为的是下一次不靠感觉决定。

## 已有的四次

| 形式 | 份数 | 描述的是什么 | 读它的机器 | 判据 |
|------|------|-------------|-----------|------|
| `.grammar` | 20 | 一门语言的语法 | 建表器（LALR(1)） | 语料通过率 |
| `.sx`（序列化） | — | 一张图的写法 | `fromSx` | **读回来逐字节相同** |
| `.sx`（核心方言） | 541 | 中间语言 | `sexpr/lower.js` | 四条腿跑出同一份输出 |
| `.omni` | 104 | 主语言 | 主前端 | 自举 |

四次里**只有前两次是「引入一格 DSL」这个决策**。后两者是"这门语言长这样"，
不是"我们要不要为这件事造一种写法"。

## 判据：五问

要引入一格新的 s-expr / DSL，五问**全部**要能答上：

### 一问：被描述的东西有**统一的形状**吗

`.grammar` 有：每条产生式都是「左边一个非终结符 → 右边一串记号 + 一格构造」。
334 条产生式，形状一样。

反例：`tograph.js` 的 48 个 case 里，`num` / `str` / `bin` / `if` 有统一形状
（模式 → 构造），而 `call` 那一格有 **11 层分支**（print / format / make / append /
conv 表 / 方法分派三条路 / 包名点函数 / field-get 兜底）。那一格不是模式，是**分析**。

**形状不统一就先分层**：把统一的那部分抽出来做 DSL，不统一的留在代码里，
并且**明说边界在哪儿**。

### 二问：实例数**够多**吗

`.grammar` 20 份。如果只有 2 份，手写两个解析器比造一格 DSL 便宜。

门槛按"抄第三遍"算：**同一段逻辑要写第三遍的时候**，DSL 才开始赚。
写第二遍时抄一份、留个注释指回第一份，是更便宜的答案。

### 三问：读它的机器**只有一台**吗

`.grammar` 只有建表器读。`.sx`（序列化）只有 `fromSx` 读。

两台以上就要问：它们对同一份文本的理解会不会分叉？
分叉的成本是"改一处忘另一处"，那笔账在这棵树上已经烂过（`js_rt.js` 与 `eval.js`
的印法要靠 `tests/graph/js-artifact.js` 钉住，才不分叉）。

### 四问：**判据**是什么

没有判据的 DSL 是装饰。

- `.grammar` 的判据是语料通过率（go 754/754）。
- `.sx`（序列化）的判据是 `toSx(fromSx(t)) === t` **逐字节相同**。
- 一格 `.mapping` 的判据必须是：**换成 DSL 之后，语料的通过数不降**。

判据要能**当场红**。"看起来更干净"不是判据。

### 五问：逃逸口开在哪儿，**怎么封住**

这是最要紧的一问，也是最容易糊过去的一问。

任何 DSL 都覆盖不了 100%。剩下的那部分要有逃逸口（写代码）。
**逃逸口不封，所有东西都会漏进去** —— 半年后 DSL 文件里剩 20 条规则，
逃逸口里有 1700 行代码，回到起点还多了一层间接。

封法有三种，按强度排：
1. **数量上限**：逃逸口里的条目数写进判据，超了就红。
2. **命名隔离**：逃逸口的每一条要有名字与一句"为什么它不是模式"。
3. **定期回收**：逃逸口里的条目过一遍，能变成模式的搬回 DSL。

## 三条反面教训（这棵树上真发生过的）

### 教训一：为了通用而 s-expr 化，会把"复杂"搬到另一层

`.sx` 那份核心方言是**中间语言**，它的存在有独立理由（四条腿的汇聚点，ADR-0014）。
但如果当初的理由是"s-expr 通用，以后好扩"，那就是把复杂搬到了另一层 ——
复杂度不会因为换成括号而消失，只会换个地方住。

**判据倒过来问**：如果这格 DSL 只有一个消费者、只有两份实例、没有判据，
那它是"代码换了个写法"，不是抽象。

### 教训二：形状不统一硬塞进 DSL，规则会长出条件分支

一旦 DSL 的规则里开始出现"如果……就……否则……"，那格 DSL 已经变成一门语言，
而**造语言的成本远高于写代码**。那时应该退回去：把那一族留在代码里。

判法：**规则里不许有条件**。规则是「模式 → 构造」，一对一。
要判断的东西（"这个名字是 map 吗"、"这个接收者的类型知道吗"）属于**分析层**，
分析层的结果作为 DSL 规则的输入（一格查询），而不是 DSL 里的 if。

### 教训三：先写机器再写内容，会照着机器的能力裁内容

正确的次序是**先写内容**（把 go 的 48 个 case 照实翻成规则，卡住的地方标出来），
再看机器需要什么能力。反过来做的话，机器能表达的那部分会被当成"全部"，
表达不了的那部分会被悄悄降级 —— 而降级是"答案错而不报"。

## 这一次：`.mapping` 过不过这五问

| 问 | 答 |
|----|-----|
| 一·形状统一 | **部分**。48 个 case 里约 32 个是「模式 → 构造」，16 个带分析（call / sel / assign / for-range / switch / tswitch / lit / index / …） |
| 二·实例够多 | **够**。11 门语言 6499 行，`if → branch` 写了 11 遍 |
| 三·一台机器 | **是**。一格 mapping 解释器 |
| 四·判据 | **有**。go 754/754 parse + 46/52 单包不降；11 门语言的例子矩阵不降 |
| 五·逃逸口 | **要设计**：`(native <name>)` 指回 JS 函数，条目数上限写进判据 |

结论：**做，但只做那 32 格**，16 格带分析的留在代码里、用 `(native …)` 点名。
先写 `go.mapping` 的内容（照实翻），再写解释器。
