# ADR-0045：自己那台 JIT（仿 `kasm87`，全平台）

状态：**D1 与 D2 已落地**（2026-09-25 立；2026-09-28 接线完成，见 §8。判据 `tests/ownjit/run.js` 21/21）

## 1. 为什么

实时性那一轴的**主要基准是 jit 那一档**（§32、用户 2026-09-25 定）：这门语言是"改一个字
就要看见画面"的，出成品那条 cc 路的整趟时间不重要。现在那一档跑在 **LLVM ORC** 上，
`balls2k` 已经做到 0.6~0.7ms/帧、与 clang -O2 同档。**性能这一格已经够了**，
剩下的两件事 LLVM 给不了：

1. **它是一坨 100MB 级的外部依赖**。`omni-jit` 要 `llvm-config` 找头与 `libLLVM`；
   没装 LLVM 的机器上这一档直接不存在 —— 而"不存在"对主要基准是致命的；
2. **启动延迟里有一段是它的**。`default<O2>` 那趟管线在 `balls2k` 上把启动从
   ~0.4s 推到 1.8s（冷缓存那一趟，§32.2）。原版 polydraw 那台 x87 JIT 编同一份脚本是
   **几毫秒**级，而且整个 `polydraw.exe` 只有 300KB。

Ken 的 `kasm87` 是一个存在性证明：**一千多行 C 就能把这门语言的每帧函数编成机器码**，
没有任何外部依赖。我们要的是同一件事，只是要跨平台（arm64 / x86-64，macOS / Linux /
Windows），而且接在我们已有的 MIR 上。

## 2. `kasm87` 到底是什么（照 `559ed7a:polydraw_src/eval.c` 读的）

读的是 `origin-bench` 那棵工作树（`~/Documents/polydraw-bench`，见那儿的 `bench/README.md`）
—— `master` 上那份被后来的提交去掉了 x87 汇编，不能当正本。

**它不是"AST 直接吐字节"**。中间有一层**线性三地址 IR**，形状与我们的 MIR 惊人地接近：

* `gasmtyp`（`eval.c:362`）：`{ f 操作码, g 附加信息, n 入参个数, r[3] 操作数, rxi 溢出索引 }`，
  整份程序是一个 `gasm[]` 数组（`eval.c:370`）。超过两个入参的走 `rxi` 指到 `rxi[]` 里
  （`MAXPARMS (1+2)`，`eval.c:355`）—— 与我们 MIR 的 `argsOf` 是同一招；
* `rtyp`（`eval.c:356`）：**一个 long 就是一个操作数** —— 高 4 位是"位置族"
  （`KECX` 临时槽 / `KEDX` 静态区 / `KIMM` 外部变量 / `KGLB` 全局常量 /
  `KFST` FPU 栈位 / `KPTR` 间接 / `KSTR`、`KARR` 串与数组区），低 28 位是偏移。
  这就是"值住在哪儿"的完整描述，**没有第二套寄存器模型**；
* **峰孔优化在那一层**（`kasmoptimizations`，`eval.c:3982` 挂，`kasm87optimize` 开关）：
  合并相邻的 op、把被合掉的那个入参从链表 `gnext[]` 里摘掉（`eval.c:2540` 附近）；
* **发射是两遍**（`putwrite`，`eval.c:2548`）：第一遍只累加 `kasm87leng` 量长度，
  第二遍才往 `compcode` 里写。`put1byte`/`put2byte`/`put4byte`（`eval.c:2549-2551`）就是全部；
* **ModRM/SIB 那一格是一个函数**（`putsib`，`eval.c:2553`）：按 `rtyp` 的族选寻址形式，
  8 位偏移能装就用 8 位；FPU 栈位那一档顺手改上一个字节（`eval.c:2581` 那句
  `compcode[kasm87leng-1] -= 0x04; //Nasty hack!!!`）—— 这是"栈顶隐含操作数"的代价；
* **绝对地址走一张补丁表**（`patch[]`，`eval.c:2597`）：发的时候先填偏移、记下位置，
  最后统一回填。跳转回填是另一张（`jumpback[]`，`eval.c:4106` 等）；
* **产物是一整块 malloc**，头上 `FUNCBYTEOFFS` 个字节存长度与帧大小
  （`eval.c:5029-5034`），代码**可整块搬走**（那段注写着唯一的例外，`eval.c:153-156`）。

一句话：**`gasm[] + rtyp` ≈ 我们的 MIR，`putsib + put*byte` ≈ 我们的 `encode.js`。**
它没有的东西我们也不该急着有（SSA、支配树、真寄存器分配）。

## 4. 缺口清单（这一版要做的准备工作）

1. **可执行内存那一格落成公共件**（C 侧）：`malloc + mprotect(RX)` 为主、
   `mmap(RW)+mprotect(RX)` 为备、`MAP_JIT` 为最后一档，写成一道梯子，
   一个都不成就报真话。**arm64 上刷 icache 不是可选项**；macOS 上 `.text` 单独占页。
   事实与 tcc 的出处都记在 memory 里，别重新调研；
2. **运行期重定位**：`from_mir.js` 现在发的是"给链接器看的重定位项"。JIT 这一档要的是
   **发完就地回填绝对地址**（照 `kasm87` 的 `patch[]`）：调用运行时符号、取全局地址、
   跨函数调用三类。这一格是两条腿共用的，不该各写一份；
3. **一个入口**：`omni run x.pss --backend ownjit`（名字待定）。它不碰 `llvm-config`、
   不写临时文件、不起子进程；
4. **判据先行**（见下节）—— 在写第 1 条之前就要有，不然没法说"它对不对"。

## 5. 判据（三把尺子，缺一不可）

1. **答案逐字节**：同一份 `.pss`，`--backend ownjit` 出的 PNG 与 c 腿**逐字节相同**
   （现在 LLVM 那一档就是这么验的，§32.3 每一刀都验过）。这是硬线，不许"够近"；
2. **每帧 ms**：对 `origin-bench` 那根尺子（x87 JIT，`balls2k` 0.636ms/帧）。
   **目标是平齐，不是超过**；LLVM 那一档（0.6~0.7ms）是我们自己的第二个参照；
3. **启动 ms**：这是这台 JIT 存在的理由之一。线就用判据里那条（≤1000ms），
   但真正要看的数是**它比 LLVM 那一档快多少** —— 原版是几毫秒级，那是天花板。

再加一条工程判据：**没有 LLVM 的机器上这一档必须能跑**。
判据脚本里要有一格"假装没有 llvm-config"的路径。

## 6. 分档（每一档都要能单独交付）

* **D0（这一版）**：文档 + `origin-bench` 工作树 + 判据骨架。不改运行时；
* **D1**：可执行内存公共件 + "发一条 `mov w0,#42; ret` 跳进去拿到 42"的最小判据。
  两条腿各一份（arm64-osx 先走通，x86_64-linux 跟上）；
* **D2**：运行期重定位 + 只支持"一个函数、只调运行时符号"的 `--backend ownjit`，
  跑 `tests/eval` 里最小的那几份 `.pss`（`01-arith` 一族）；
* **D3**：整份 `.pss` 走通（含 GL 那一族的 `gfxcall`）—— 判据是四份 HEAVY 的
  逐字节 + 每帧 + 启动三栏；
* **D4**：Windows / Linux 两个平台补齐（自己的链接器已经会写 PE 与 ELF，
  可执行内存那一格换成 `VirtualAlloc` + `FlushInstructionCache`）。

## 7. 明确不做的事

* **不做 SSA、不做支配树、不做图着色寄存器分配**。`kasm87` 没有，我们现在的两条腿也没有
  （"每个 MIR 值一个八字节栈位，算之前取进来、算完写回去"，见 `x64/from_mir.js` 头注）。
  真要动寄存器那一层，那是 MIR 上的事（ADR-0039 的管线），不是这台 JIT 的事；
* **不撤 LLVM 那一档**。它是我们的第二把尺子（"同一份 IR 给成熟后端能跑多快"），
  而且 `emit-llvm` 那条路还有别的用处。两档并存，靠判据比；
* **不抄 x87**。目标是"仿它的**做法**"（线性 IR + 两遍发射 + 补丁表 + 零依赖），
  不是仿它的指令集 —— 我们这两条腿是 SSE2/NEON 的双精度，栈式 FPU 那套连它自己都嫌烦
  （那句 `Nasty hack!!!` 就是证据）。

## 8. 现状（2026-09-28）

**D1 与 D2 都落地了，而且 D2 比这份文档原来设想的省一大截。**

原来的设想是"D2 要写运行期重定位"。真去接线才发现 **那一格早就在**：

| D2 要的 | 现成的那一份 | 谁在用 |
| --- | --- | --- |
| MIR -> 机器码 | `arm64/from_mir.js` / `x64/from_mir.js` | `omni build`（**默认就是它**，外部 cc 要明说） |
| **发完就地回填绝对地址** | `link/flat_image.js` 的 `flatImage` | `ffiInject`（ADR-0038 第二刀） |
| 可执行内存 + 刷 icache + 跳进去 | `src/jit/omni_ffi_host.c` 的 `mem`/`protect`/`calli` | 同上 |

所以 D2 的后半是**一格接线**（`cli.js` 的 `cJitRun`，约 30 行）：与 `ffiInject` 比，
换掉的只有**入口的约定** —— 那一路跳 `napi_register_module_v1`，这一路跳 `main`。

### 落地的两个动词

* `omni c jit x.c`（别名 `omni c-jit`）：那份 C -> 我们自己那台后端的机器码 ->
  **就在这个进程里跑**。不写可执行文件、不起子进程、一个外部 cc 或 LLVM 都不借。
* `main` 必须是 `int main(void)`：`calli` 按 `int64_t (*)(void)` 调，带形参的话
  x0/x1 是上一趟留下的垃圾。整份 `.sx` 程序（生成的 `main` 带两个形参）要先补一格
  入口包装 —— 那是 D3 的事，现在明着拒。

### 判据（`tests/ownjit/run.js`，21/21）

三节，每一节都踩在上一节上：

1. **D1**：发 `movz w0,#n; ret` 跳进去拿到 n（三个常量）+ W^X 来回切一趟（验刷 icache）；
2. **D2 前半**：在 JS 里发一段**真会调别人**的机器码 —— 装实参、`blr x16`、带栈帧返回。
   编码逐条拿 `clang -c` + `otool -t` 对过。`llabs(-1234567890123)` 同时验了高 32 位没被截；
3. **D2 后半**：四份整程序（递归 / 串 / **结构体按值 + `sqrt`** / 循环与退出码），
   **stdout 逐字节 + 退出码都与 `clang -O0` 相同**。

**尺子为什么是 clang 而不是 `omni c run`**：后者是 **MIR 解释器**，它连 `sqrt` 都拒
（原话 `interp: C ABI call 'sqrt' is not supported by the interpreter`）。
尺子必须比被判的那条路更全，不然判不动 —— 这一格顺手说明了 `c jit` 已经比 `c run` 能跑。

`sqrt` 那一份**没有借 `-lm`**：它是 `dlsym(RTLD_DEFAULT, …)` 在这个进程里找着的，
那正是这条路的立场（外部符号一律问本进程，与 `omni_jit.c` 的 `--lib`/`--dl` 同一格）。

### 量到的两个数

* 整趟 **1.6s（暖）/ 2.4s（冷）**，其中约 0.7s 是编那份 `.o`；剩下的是 node 起步 +
  `import('./cli.js')`。**故意不缓存那份 `.o`**：键要正确就得覆盖用户自己那几份
  `#include "…"`，只哈主文件的键会在改了头之后照旧命中 —— 那是"一个会跑错程序的缓存"。
  要缓存等发射按单元切开（ADR-0047 §6）。
* 铺出来的映像与段数由 `-v` 印（`c-jit  <n> 字节铺在 0x…，<k> 段`）。

## 9. D3 的头两步也落地了（同一天）

那两步本来估的是"下一刀"，接下来才发现也只是接线：

1. **入口那一格**：宿主多一个口子 `calln(addr, a0..a3)` —— 把那个地址当
   `int64_t (*)(int64_t, int64_t, int64_t, int64_t)` 调。**四格是刻意的**：arm64（x0-x7）
   与 x86-64（rdi/rsi/rdx/rcx）上头四个整数实参都在寄存器里，于是这一格不必知道调用约定的
   任何别的事；递多了的那几格照 C 的规矩是"被调方不看"。`argv` 是我们自己在一块 `mem`
   里摆出来的 `{ "omni-c-jit", NULL }`。
   **浮点实参故意没有** —— 那要另一组寄存器（v0-v7 / xmm0-7），而到现在没有一个调用方要它。
2. **运行时那二十来份 `.o` 一起铺**：`omni c jit x.c --rt`。同一份清单、同一格暖存
   （`runtimeObjectsSelf`），与 `buildSelf` 链的是同一批字节。不默认带上：纯 C 程序一个
   都用不着，多铺二十份是白花的时间与地址空间。

于是**整份程序在本进程里跑起来了**，判据（`tests/ownjit/run.js` 23/23）多两格：

* `tests/cases/01_basics.omni` —— 与 `omni run` **stdout 逐字节相同**；
* `ext/polydraw/examples/01-arith.pss` —— 同上。**这就是 §6 里 D2 那句
  "跑 `01-arith` 一族"**。

诊断那一格也验过了：不给 `--rt` 时报的是
`flat: 这 6 个符号在这个进程里找不着：_omni_print_int _omni_print_string _omni_host_init …`
—— 名字齐、一次报全，不是"SIGBUS 然后自己猜"。

### 出图那一族也过了（同一天，第三刀）

先按"下一刀"的办法量了一趟"哪些符号找不着" —— **一个都没有**。`02-gl.pss`（GL 立即模式）
直接跑通，出的那张 PNG 与正路**逐字节相同**（307528 字节）。设备那一层本来就在运行时那
二十来份 `.o` 里，`--rt` 一带上就齐了。

着色器那三份（`04/05/06`）一开始报的是
`这格设备（CPU 备选）上没有 'glsetshader'` —— **看着像方言缺一格能力，其实是那份
`libomnigl` 没挂上**。`cJitRun` 补一句与 `runNative` 逐字同一手的
「顺手编好 + 把绝对路径放进 `OMNI_GL_LIB`」就通了；哪台设备是**跑的时候**由 `OMNI_GFX` 定的，
所以着色器那一族要 `OMNI_GFX=gl`（与 `omni run --gfx gl` 同一格）。

判据现在 **25/25**，出图那两格判的是**图的字节**不是 stdout：那一行 `#gfx png <路径>`
里的名字按"程序叫什么"取，两条路上本来就不同名（`frame.png` / `02-gl.png`）——
那是判据自己的取名差，不是代码生成的差。

顺手堵掉一格**会白拿绿**的地方：被判那一边的产物名固定是 `.omni-cache/gfx/frame.png`
（两份例子写同一个文件）⇒ 跑第二份之前必须先删，不然第二份压根没画时读到的是第一份那张。
